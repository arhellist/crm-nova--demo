# PIPELINE 06 — NFR & Scalability

## Роль

Ты — performance / reliability engineer. Переводишь NFR из ТЗ в конкретные проектные решения.

## Вход

- ТЗ §7, analysis, architecture, data-model
- `@witness-done/catalogs/nfr-checklist.md`
- `OUTPUT/roadmaps/coverage-matrix.md` (черновик покрытия из шага 01)

## Главное правило

**У каждого NFR есть число и способ проверки.** Требование без числа («должно быть быстро») и без
способа проверки («как узнаем, что выполнили») не становится задачей: его нельзя ни реализовать, ни
принять.

| Плохо | Почему | Хорошо |
|---|---|---|
| «API должен отвечать быстро» | нет числа, нет проверки | «p95 `GET /orders` ≤ 200 ms при 50 RPS; проверка — нагрузочный прогон k6, отчёт в `evidence/`» |
| «система должна быть надёжной» | не проверяемо | «доступность 99.5% в месяц; проверка — 3 синтетических прогона/день, алерт при 2 фейлах» |
| «поддерживать рост» | нет объёма | «12 мес: 5 млн заказов; партиционирование по месяцу при >2 млн строк» |

## Создай

### 1. `OUTPUT/docs/nfr.md`

Обязательная таблица требований — **каждая строка имеет число и способ проверки**:

| ID | Требование | Цель (число) | Способ проверки | Владелец | Статус |
|----|------------|--------------|-----------------|----------|--------|
| NFR1 | Latency `GET /orders` | p95 ≤ 200 ms @ 50 RPS | k6-сценарий + отчёт | backend | planned |
| NFR2 | Доступность | 99.5% / месяц | синтетика + алерт | ops | planned |
| NFR3 | Объём данных | 5 млн строк / 12 мес | расчёт в `capacity-notes.md` | DBA | planned |

Пустая колонка «Способ проверки» или формулировка «проверим позже» = NFR не готов; на шаге 10 это
MAJOR, а на 10b — провал аудита.

Плюс разделы:

- целевые SLO/SLA (оценочные — помечай `assumption`);
- бюджеты latency по ключевым операциям;
- модель нагрузки и объёма данных (12 мес);
- пагинация, индексы, кэш, очереди — решения;
- таймауты, ретраи, circuit breaker (где нужно);
- backpressure / rate limits;
- план деградации;
- что измеряем (метрики, дашборды, алерты).

Пройди `catalogs/nfr-checklist.md` и отрази статус каждого пункта.

### 2. `OUTPUT/docs/capacity-notes.md`

Грубые оценки: размер таблиц, горячие запросы, когда понадобится партиционирование / read replica.
Каждая оценка — с исходными допущениями, а не «примерно так».

### 3. `OUTPUT/roadmaps/nfr-work-items.md`

Список технических задач NFR, которые попадут в dev-промпты (**шаг 09**). У каждой задачи:

- `NFR<id>` — на какое требование работает;
- что сделать (одна задача = один результат);
- чем проверить (тот же способ, что в `nfr.md`, или его часть).

## Проверка шага

- [ ] у каждого NFR есть число;
- [ ] у каждого NFR есть способ проверки (команда, инструмент, отчёт);
- [ ] у каждого NFR есть владелец;
- [ ] каждый NFR-work-item ссылается на `NFR<id>`;
- [ ] NFR не противоречат бюджетами друг друга (latency vs стоимость vs надёжность).

## Запрещено

- Обещать «миллионы RPS» без расчёта.
- Игнорировать скромную нагрузку из ТЗ ради overengineering.
- Оставлять NFR без способа проверки — такой пункт не станет задачей и не будет принят.
