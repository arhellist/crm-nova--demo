# PIPELINE R02 — Propose Change (Формирование предложения изменения)

## Роль

Ты — архитектор изменений Witness Done в режиме **Brownfield**. Твоя задача: спроектировать пакет атомарного изменения функционала системы, формализовать дельту спецификаций, разработать технический дизайн и сформировать проверяемый чеклист задач в изолированном каталоге `spec-state/changes/<id>/`.

Код реализации на этом шаге **не писать**.

## Вход (обязательно изучи)

- Действующий baseline спецификаций: `spec-state/baseline/<domain>/spec.md`
- Конфигурация спецификаций: `spec-state/config.yaml`
- Шаблоны пакета изменений:
  - `@witness-done/TEMPLATES/change-proposal.md`
  - `@witness-done/TEMPLATES/change-delta-spec.md`
  - `@witness-done/TEMPLATES/change-design.md`
  - `@witness-done/TEMPLATES/change-tasks.md`
- Бизнес-запрос или тикет с описанием желаемого изменения.

## Правила

1. **Изолированный пакет изменения:** Каждое изменение оформляется в отдельной папке `spec-state/changes/<id>/`, где `<id>` — краткий понятный идентификатор (например, `add-user-avatar`, `refactor-jwt-refresh`).
2. **Формат дельты (Delta Format):** Изменения в `spec-state/changes/<id>/specs/<domain>.md` описываются строго в трёх секциях:
   - `## ADDED Requirements` — новые требования со сценариями;
   - `## MODIFIED Requirements` — замена существующих требований целиком;
   - `## REMOVED Requirements` — удаление устаревших требований с обязательным указанием причины.
3. **Правило полной замены (Full Replacement) для MODIFIED:** Запрещены частичные правки или diff-патчи. Требование в секции MODIFIED формулируется целиком: текст требования (MUST/SHALL) и все сценарии (GIVEN/WHEN/THEN). При архивации старое требование в baseline будет полностью заменено новым.
4. **Валидность ссылок:** Для каждого требования в `MODIFIED` и `REMOVED` обязательно существование требования с ровно таким же названием в `spec-state/baseline/<domain>/spec.md`.
5. **Два сценария на требование:** Каждое ADDED/MODIFIED требование содержит **минимум два** сценария — `happy path` и `negative / boundary`. Требование только с happy path не принимается: про отказ не подумали.
6. **Изменение начинается с проблемы, а не с решения:** в `proposal.md` §1 — что не работает сейчас (наблюдаемо); §6 «Что не делаем» — явные non-goals; §5 — обратная совместимость с формулировкой `breaking` / `compatible` / `no impact`.
7. **Чеклист реализации:** `tasks.md` обязан содержать конкретные задачи с понятными acceptance-критериями в синтаксисе `- [ ] task`, и **каждая задача привязана к утверждению** (`Axx.k` из ACCEPTANCE или `Rxx` — требование baseline/дельты). Задача без ссылки на утверждение не принимается: непонятно, что именно проверено.
8. **Связь с входом:** `id` изменения берётся из записи входа `journal/intake/<ID>.md` (`kind: change`), а `proposal.md` содержит поле `| Intake | <ID> |`. Изменение без записи входа не принимается: `sp doctor --strict` вернёт провал по трассируемости. Если записи нет — сначала `sp intake "<запрос дословно>"`, потом этот шаг.

## Сделай

1. Возьми идентификатор `<id>` из записи входа (`sp intake` возвращает `next:` с уже предложенным id). Если записи нет — создай её и вернись к чтению.
2. Создай директорию `spec-state/changes/<id>/` и поддиректорию `spec-state/changes/<id>/specs/`.
3. Создай `spec-state/changes/<id>/proposal.md` по шаблону `TEMPLATES/change-proposal.md`:
   - Опиши проблему (наблюдаемо, а не «давайте добавим»), контекст, бизнес-обоснование и затрагиваемые домены;
   - §5 обратная совместимость: явно `breaking` / `compatible` / `no impact`;   - §6 «Что не делаем»: non-goals;
   - §8 трассировка: какие требования baseline/дельты затрагиваются;
   - поле `| Intake | <ID> |` — ссылка на запись входа `journal/intake/<ID>.md`.
4. Создай дельту спецификаций `spec-state/changes/<id>/specs/<domain>.md` для каждого затрагиваемого домена по шаблону `TEMPLATES/change-delta-spec.md`:
   - Заполни секции `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`;
   - Убедись в наличии ключевых слов `MUST`/`SHALL` и **двух** сценариев `GIVEN / WHEN / THEN` (happy + negative/boundary).
5. Создай `spec-state/changes/<id>/design.md` по шаблону `TEMPLATES/change-design.md`:
   - Зафиксируй изменения в модели данных, эндпоинтах, контрактах и зависимостях файлов;
   - Опиши сохранение обратной совместимости.
6. Создай `spec-state/changes/<id>/tasks.md` по шаблону `TEMPLATES/change-tasks.md`:
   - Декомпозируй реализацию на атомарные шаги с acceptance-критериями;
   - Каждая задача — со ссылкой на утверждение (`Axx.k` / `Rxx`).
7. Проверь синтаксическую корректность пакета изменения через инструмент верификации:
   ```bash
   node witness-done/SEED/sp-tools/sp-verify.mjs --change <id> --gate change
   ```
   *(На этапе R02 допускается незавершённость чеклиста tasks.md, но структура дельты и ссылки на baseline обязаны быть корректными).*
8. Зафиксируй событие в `OUTPUT/docs/00_run_log.md`.

## Формат ответа в чате

```text
PROPOSE_CHANGE: OK | BLOCKED
Change ID: [id]
Затрагиваемые домены: [список доменов]
ADDED требований: [число]
MODIFIED требований: [число]
REMOVED требований: [число]
Предварительная валидация дельты: PASS | FAIL
Следующий шаг: PIPELINE/R03_apply_change.md
```
