# ТЕХНИЧЕСКОЕ ЗАДАНИЕ — NOVA CRM

> Единственная действующая редакция документа.
> Источники: требования бизнеса, дизайн-референс `INPUT/design/Design.html`, канон `catalogs/*`.
> Документ описывает продукт **в состоянии, готовом к промышленной эксплуатации**: полный функционал домена, обязательные требования безопасности, эксплуатационные процедуры и критерии приёмки. Продукт поставляется одним полным релизом — промежуточных, урезанных или «поэтапных» состояний не предусмотрено: всё описанное ниже входит в поставку и проверяется на приёмке.

## 0. Бизнес-цели и успех

- **Цель бизнеса (12–24 мес):** заменить Excel и мессенджеры в оперативном учёте задач по стройобъектам: руководитель в одном месте видит, что сделано и что ждёт приёмки; исполнитель видит только свою зону; любое изменение статуса восстанавливается по истории и не может быть переписано.
- **Кто платит vs кто пользуется:** платит строительная компания; пользуются руководитель (постановщик) и прорабы/инженеры (исполнители). Покупатель и основной пользователь совпадают — руководитель.
- **Ценность для пользователя:** «я вижу статус каждой задачи по объекту и знаю, кто и когда его поменял»; для исполнителя — «я вижу только свои задачи и не тону в чужих».
- **KPI успеха (измеримые):**
  1. Доступность интерфейса ≥ 99.9% в месяц по данным внешнего монитора; все простои ≥ 5 минут фиксируются инцидентом.
  2. Латентность p95: чтение списков ≤ 400 мс, мутация статуса ≤ 600 мс, вход ≤ 1 000 мс.
  3. 100% разрешённых переходов матрицы §5.3 выполняются; 100% запрещённых отклоняются БД, а не интерфейсом.
  4. 0 успешных обходов RLS при прямом обращении к PostgREST/RPC с любым доступным клиенту ключом.
  5. 0 возможностей вставки, изменения или удаления записей истории статусов вне триггеров БД.
  6. 0 вхождений `service_role` и строк подключения к основной БД в бандл, образы и git-историю.
  7. Лаг логической репликации p95 ≤ 5 с; при превышении 30 с срабатывает алерт.
  8. RPO ≤ 5 минут (PITR), RTO ≤ 60 минут; восстановление подтверждено учебным прогоном.
  9. Каждый релиз проходит staging и smoke-набор; откат ≤ 15 минут.
  10. Security-гейты CI зелёные: 0 high/critical уязвимостей, 0 находок `gitleaks`, чек-лист ASVS L2 закрыт.
  11. Time-to-first-value: от входа до смены статуса задачи ≤ 3 клика и ≤ 30 секунд.
  12. Развёртывание полного контура с нуля по README ≤ 15 минут.
- **Монетизация / экономика:** продукт не монетизируется — это внутренний инструмент компании. Тарифов, биллинга и платёжных интеграций нет.
- **Go-to-market:** отсутствует в классическом смысле — система закрытая и внедряется внутри компании; канал один — прямая демонстрация и обучение пользователей.
- **SEO / контент / маркетинг:** нет. Система закрытая, лендинг не нужен, SSR/SEO не требуются → SPA без серверного рендера.
- **Конкуренты и отличие:**
  - Excel + WhatsApp/Telegram — бесплатно, но нет модели статусов, прав и аудита; продукт даёт жёсткий цикл и неизменяемую историю.
  - Bitrix24 / YouGile / Asana — мощные, но избыточные; отличие — минимальный интерфейс под один процесс и защита прав на уровне БД, а не только в UI.
  - Самописные CRM — отличие — воспроизводимые миграции, декларативные RLS-политики и read-реплика для отчётности.
- **Анти-цели:** продукт не является ERP, сметным или документным ПО; не является универсальным таск-трекером; не заменяет мессенджер и файлохранилище; не претендует на realtime-доску, BI-платформу и мультитенантный SaaS; не создаёт второго пути записи данных.

## 1. Название и суть

- **Название проекта:** NOVA CRM (по дизайн-референсу), имя репозитория `nova-crm`.
- **Одной фразой:** закрытая веб-CRM, в которой руководитель ставит задачи по строительным объектам, исполнители ведут их до приёмки, а каждый переход статуса фиксируется в неизменяемой истории.
- **Для кого:** постановщик (руководитель/менеджер строительной компании) и исполнители (прорабы, инженеры).
- **Проблема:** задачи по объектам живут в чатах и таблицах; нет единого статуса, не видно загрузки исполнителей, а историю можно переписать или удалить.
- **Связь с §0:** продукт закрывает KPI 1–12. Защита данных — не «галочка», а основное свойство продукта: права, переходы и история обеспечиваются БД.
- **Архитектурный акцент:** BaaS-контур (Supabase + RLS) как единственный путь записи плюс собственный backend (Node.js/TS) с read-only API поверх логической реплики PostgreSQL. Реплика не является вторым источником правды и не участвует в авторизации.

## 2. Границы

### 2.1. Состав продукта

1. Вход по email/паролю с MFA (TOTP), выход, восстановление сессии после перезагрузки; открытая регистрация отключена, учётные записи выдаются администратором компании. (KPI 1)
2. Две роли из `profiles`: `manager` (постановщик) и `executor` (исполнитель). Роль определяет и UI, и права в БД. (KPI 3, 4)
3. Объекты: список доступных, создание, редактирование, архивирование, карточка объекта со списком задач и статусами. (KPI 11)
4. Задачи: создание с обязательными полями, редактирование, архивирование, назначение исполнителя, карточка задачи с историей. (KPI 3, 5)
5. Цикл статусов из 5 состояний и 5 разрешённых переходов; проверка перехода, роли и назначения — в БД. (KPI 3)
6. Неизменяемая история статусов: кто, когда, из какого в какой, комментарий. (KPI 5)
7. Экраны: вход, список объектов, карточка объекта, карточка задачи, «Мои задачи», отчёты, 404.
8. RLS на всех таблицах + RPC для смены статусов и архивации; прямой доступ в обход UI закрыт. (KPI 4)
9. Стартовые данные: 1 постановщик, 2 исполнителя, 3 объекта, ≥ 8 задач во всех пяти статусах.
10. Собственный backend (Node.js + TypeScript): read-only API — сводка по объектам, загрузка исполнителей, сроки по статусам, `GET /health`, `GET /health/replication`. Write-эндпоинтов нет.
11. Логическая репликация Supabase → вторичный PostgreSQL: publication/subscription, контроль лага, сверка расхождений, подъём одной командой.
12. Безопасность по OWASP ASVS L2: JWT-правила, RBAC-матрица, CSRF-модель, security-заголовки и CSP, артефакты `docs/security/threat-model.md` и `docs/security/asvs-l2-checklist.md`. (KPI 10)
13. Эксплуатация: staging и production контуры, мониторинг и алерты, ежедневные бэкапы с PITR, runbooks инцидентов и восстановления, журнал релизов. (KPI 1, 7, 8, 9)
14. Документация: README, `docs/design-notes.md`, `docs/decisions.md`, `docs/security/*`, `docs/runbooks/*`.

### 2.2. Продуктовые границы (осознанные решения, а не незавершённость)

- **Нет файлообмена и фотоотчётов.** Вложения живут в корпоративном файловом хранилище; продукт хранит статус и историю.
- **Нет переписки.** Обсуждение фиксируется комментарием к переходу статуса; оперативная связь — в корпоративном канале.
- **Нет уведомлений.** Доставка сообщений — вне продукта; система является единственным источником статуса, а не каналом связи.
- **Нет управления пользователями из интерфейса.** Провижининг выполняется администратором по регламенту в Supabase с журналом операций; это осознанное ограничение поверхности атаки.
- **Нет мобильного приложения.** Продукт — адаптивное веб-приложение, работающее с телефона без установки.
- **Нет мультитенантности.** Одна инсталляция обслуживает одну компанию; вторая компания получает отдельное развёртывание.
- **Нет универсального поиска и BI.** Поиск по объектам — клиентский фильтр с индексами Postgres; отчётность — фиксированный набор серверных агрегатов.

### 2.3. Архитектурные границы

- Единственный путь записи — Supabase (PostgREST + RPC). Backend не имеет прав записи ни в один контур.
- Источник правды по правам — БД (RLS, гранты, триггеры). Интерфейс не является средством защиты.
- Реплика не участвует в авторизации и не принимает записи; её деградация влияет только на отчёты.
- Схема накатывается только миграциями из `supabase/migrations/`; ручных правок в production нет.

## 3. Стек

- **Frontend:** React 18.3 + TypeScript 5.5 (`strict: true`), сборка Vite 5, Node.js 20 LTS. Маршрутизация React Router 6, серверное состояние TanStack Query 5, формы react-hook-form 7 + Zod 3, иконки lucide-react, тосты sonner.
- **Стили UI:** Tailwind CSS 3.4 с дизайн-токенами из `INPUT/design/Design.html` + примитивы Radix UI (доступность) в стиле локальных компонентов. Тяжёлые UI-киты (MUI, Ant Design, Bootstrap) не используем — они конфликтуют с референсом и раздувают бандл.
- **Backend:** собственный сервис Node.js 20 LTS + TypeScript 5.5 (`strict: true`) на Fastify 4: **только чтение** — `GET /health`, `GET /health/replication`, `GET /metrics`, `GET /api/reports/objects`, `/api/reports/workload`, `/api/reports/status-ages`. Доступ к данным — `pg` (node-postgres), параметризованные SQL, Zod на параметры и ответы, pino (JSON-логи без PII), graceful shutdown, Docker-образ с непривилегированным пользователем. Write-эндпоинтов нет ни в одном маршруте.
- **БД OLTP (два контура):**
  - **Primary** — PostgreSQL 15 в Supabase Cloud (регион eu-central-1): источник правды, Auth, PostgREST, RPC, RLS, триггеры, PITR и ежедневные бэкапы. Запись и права — только здесь.
  - **Secondary** — PostgreSQL 16 в production-контуре: **логическая реплика** (подписчик), режим только чтения. Схема накатывается теми же миграциями `supabase/migrations/` — DDL логической репликацией не передаётся.
- **Репликация:** publication `nova_pub` (`profiles`, `objects`, `tasks`, `task_status_history`) на primary → subscription `nova_sub` на secondary: `wal_level = logical` (включён в Supabase), плагин `pgoutput`, `copy_data = true`, `create_slot = true`. Передаются `INSERT`/`UPDATE`; `DELETE` в схеме не используется (архивирование), поэтому `REPLICA IDENTITY` по PK достаточно. Лаг = `pg_current_wal_lsn()` − `confirmed_flush_lsn`, состояние — `pg_stat_subscription`.
- **Аналитика / OLAP:** отдельной СУБД нет; агрегирующие запросы отчётов выполняются по реплике, разгружая primary.
- **Кэш:** нет. Клиентский кэш — TanStack Query (in-memory, инвалидация после мутаций); отчёты backend кэширует не более 30 с в памяти процесса.
- **Очереди / MQ / streaming:** нет. Логическая репликация — механизм БД, а не очередь приложения.
- **Observability:** pino (JSON, redact) + метрики Prometheus (`/metrics`, только из внутренней сети) + дашборды и алерты Grafana Cloud + Sentry для ошибок frontend и backend + внешний uptime-монитор (2 региона, интервал 1 мин). Алерты: доступность, доля 5xx, p95, лаг репликации, ошибки подписки, заполнение диска, неуспешные входы.
- **Хостинг / облако:** frontend — Vercel (static SPA, SPA-rewrite, security-заголовки); primary — Supabase Cloud (план с PITR и ежедневными бэкапами); backend + secondary PostgreSQL — изолированный production-контур (VPS с Docker Compose либо managed PaaS), доступ к API только по TLS и токену. WAF и TLS-терминация — на edge-провайдере (Cloudflare/Vercel).
- **Архитектурный стиль:** CQRS-lite. Запись и авторизация — только Supabase (UI ходит напрямую в PostgREST/RPC, права решают RLS + триггеры). Чтение аналитики — с вторичной реплики через тонкий read-only backend. Реплика не участвует в авторизации, никогда не принимает записи и не является источником правды; её отставание или падение деградирует только отчёты.
- **Причина выбора:** минимальная операционная сложность и предсказуемая безопасность → Supabase даёт Auth, Postgres, RLS и RPC «из коробки», а права проверяются прямыми запросами к API. Второй контур (Fastify + реплика) разгружает primary на отчётах, **не создавая второго пути записи**. Альтернатива «полный API поверх Supabase» отклонена: она удваивает поверхность атаки и операционную сложность.

## 4. Ключевые сценарии

1. **Провижининг учётной записи.** Администратор по регламенту создаёт пользователя в Supabase Auth, задаёт `profiles.full_name` и `role`, выдаёт временный пароль по защищённому каналу и требует включить MFA при первом входе. Операция фиксируется в журнале провижининга.
2. **Вход.** Анонимный пользователь открывает `/login`, вводит email/пароль, при включённой MFA — одноразовый код. Успех → редирект на `/objects` (постановщик) или `/my-tasks` (исполнитель); профиль (имя, роль) загружается из `profiles`. Ошибка → единое сообщение без раскрытия существования аккаунта.
3. **Создание объекта (постановщик).** «Новый объект» → название + адрес → объект появляется в списке; в карточке пустой список задач с приглашением создать первую.
4. **Создание задачи (постановщик).** В карточке объекта → «Новая задача»: название, описание, исполнитель (только пользователи с ролью `executor`). Сохраняется в статусе «Новая», автор = текущий пользователь, в историю попадает запись «создана».
5. **Взятие в работу (исполнитель).** В «Моих задачах»/карточке открывает задачу в статусе «Новая» и жмёт «Взять в работу» → «В работе»; история пополняется.
6. **Отправка на проверку (исполнитель).** «В работе» → «Отправить на проверку» → «На проверке»; задача появляется у постановщика в ожидающих приёмки.
7. **Приёмка (постановщик).** «На проверке» → «Принять» → «Принята»; дальнейшие действия недоступны, кроме просмотра.
8. **Возврат на доработку (постановщик).** «На проверке» → «Вернуть на доработку» → модальное окно с обязательным комментарием → «На доработке»; без непустого комментария операция отклоняется и в UI, и в БД.
9. **Повторный старт (исполнитель).** «На доработке» → «Взять в работу» → «В работе»; комментарий постановщика виден в истории.
10. **Изоляция исполнителя (негативный).** Исполнитель открывает `/tasks/<чужой-id>` → «Задача не найдена или нет доступа»; прямой `GET /rest/v1/tasks?id=eq.<чужой>` → пустой массив; `PATCH`/`DELETE` → 401/403/0 строк, данные не меняются.
11. **Запрещённый переход (негативный).** Попытка перехода вне матрицы (например, `new → accepted`) через UI, RPC или PostgREST отклоняется БД: статус не меняется, запись истории не создаётся.
12. **Архивирование (постановщик).** Архив объекта или задачи после подтверждения; сущность исчезает из списков и карточек у всех, история в БД сохраняется; жёсткий `DELETE` через API запрещён.
13. **«Мои задачи» (исполнитель).** Список только своих задач, сгруппированный по статусам, со счётчиками; клик открывает карточку задачи; объектов без своих задач исполнитель не видит.
14. **Отчёты (постановщик).** Раздел «Отчёты» показывает сводку по объектам, загрузку исполнителей и сроки приёмки; данные читаются с реплики, каждый ответ помечен `source: replica` и `lag_seconds`. При недоступности реплики раздел показывает состояние «данные недоступны» с кодом и не блокирует остальные экраны.
15. **Отставание реплики (негативный).** Если подписка остановлена или лаг превышает порог, `/health/replication` возвращает `503` и причину, срабатывает алерт; запись и вход продолжают работать.
16. **Backend не пишет (негативный).** Любой `POST/PUT/PATCH/DELETE` на backend → `405`; попытка INSERT/UPDATE/DELETE на реплике от роли API → ошибка `25006 read_only_sql_transaction`; в коде и образе нет строки `service_role`.
17. **Инцидент и восстановление (эксплуатация).** При деградации primary включается runbook: проверка статуса Supabase, переключение клиента на резервный регион/статус-страницу, восстановление из PITR при потере данных, сверка реплики после восстановления. Действия и тайминги фиксируются в инцидент-журнале.

## 5. Сущности и данные

| Сущность | Поля | Связи | Заметки |
|----------|------|-------|---------|
| `profiles` | `id` (uuid, PK = `auth.users.id`), `full_name`, `role`, `created_at` | 1:N с задачами (автор/исполнитель) | Роль и имя для UI; email хранится только в `auth.users` и не раздаётся другим |
| `objects` | `id`, `title`, `address`, `created_by`, `created_at`, `updated_at`, `deleted_at` | 1:N `tasks` | Стройка; архивирование через `deleted_at` |
| `tasks` | `id`, `object_id`, `title`, `description`, `assignee_id`, `author_id`, `status`, `created_at`, `updated_at`, `deleted_at` | N:1 `objects`, N:1 `profiles` (assignee, author), 1:N `task_status_history` | Задача по объекту; статус меняется только через RPC |
| `task_status_history` | `id`, `task_id`, `from_status` (null при создании), `to_status`, `changed_by`, `comment`, `created_at` | N:1 `tasks` | Append-only; без `updated_at`/`deleted_at` |

### 5.1. Перечисления

```sql
create type public.user_role as enum ('manager', 'executor');
create type public.task_status as enum ('new', 'in_progress', 'on_review', 'rework', 'accepted');
```

Подписи в UI: `new` — «Новая», `in_progress` — «В работе», `on_review` — «На проверке», `rework` — «На доработке», `accepted` — «Принята».

### 5.2. Детализация таблиц и ограничения

**`profiles`**
- `id uuid primary key references auth.users(id) on delete cascade`
- `full_name text not null check (length(btrim(full_name)) between 1 and 120)`
- `role public.user_role not null default 'executor'`
- `created_at timestamptz not null default now()`
- Email намеренно не дублируется: он есть в сессии Supabase Auth и не нужен другим пользователям.

**`objects`**
- `id uuid primary key default gen_random_uuid()`
- `title text not null check (length(btrim(title)) between 1 and 200)`
- `address text not null check (length(btrim(address)) between 1 and 300)`
- `created_by uuid not null default auth.uid() references profiles(id)`
- `created_at`, `updated_at timestamptz not null default now()`
- `deleted_at timestamptz null`
- Индексы: `(deleted_at)`, `lower(title)` для поиска по названию, `lower(address)`.

**`tasks`**
- `id uuid primary key default gen_random_uuid()`
- `object_id uuid not null references objects(id) on delete restrict`
- `title text not null check (length(btrim(title)) between 1 and 200)`
- `description text not null default '' check (length(description) <= 5000)`
- `assignee_id uuid not null references profiles(id)`
- `author_id uuid not null references profiles(id)`
- `status public.task_status not null default 'new'`
- `created_at`, `updated_at timestamptz not null default now()`, `deleted_at timestamptz null`
- Индексы: `(assignee_id, status) where deleted_at is null`, `(object_id) where deleted_at is null`, `(created_at desc)`.
- Инварианты (проверяются триггером `validate_task_actors`): `assignee_id` — пользователь с ролью `executor`; `author_id` — с ролью `manager`; объект не архивирован; при `insert` статус только `new`; смена исполнителя разрешена только в статусах `new` и `rework` (§13.1).

**`task_status_history`**
- `id bigint generated always as identity primary key`
- `task_id uuid not null references tasks(id) on delete restrict`
- `from_status public.task_status null` (null = задача создана)
- `to_status public.task_status not null`
- `changed_by uuid not null references profiles(id)`
- `comment text null check (comment is null or length(comment) <= 2000)`
- `created_at timestamptz not null default now()`
- `check (from_status is distinct from to_status)`
- `check (to_status <> 'rework' or length(btrim(coalesce(comment, ''))) > 0)` — возврат на доработку без комментария невозможен даже SQL-вставкой.
- Индекс: `(task_id, created_at desc, id desc)`.
- `updated_at`/`deleted_at` отсутствуют: строки не изменяются и не удаляются.

### 5.3. Матрица переходов (источник правды)

| Из | В | Кто | Дополнительное условие |
|----|----|-----|------------------------|
| — | `new` | постановщик | при создании задачи |
| `new` | `in_progress` | назначенный исполнитель | `assignee_id = auth.uid()` |
| `in_progress` | `on_review` | назначенный исполнитель | `assignee_id = auth.uid()` |
| `on_review` | `accepted` | постановщик | роль `manager` |
| `on_review` | `rework` | постановщик | роль `manager`, комментарий непустой |
| `rework` | `in_progress` | назначенный исполнитель | `assignee_id = auth.uid()` |

Все остальные переходы (15 пар из 25 возможных, включая переход в тот же статус) запрещены.

### 5.4. Механика записи (ключевое решение)

- Все изменения статуса — только через `rpc.change_task_status(task_id, target_status, comment)`. Функция `security definer`: блокирует строку `for update`, проверяет актора/назначение/переход по матрице, вызывает `update tasks set status = ...`, кладёт комментарий в транзакционную настройку `app.transition_comment`, после чего триггер пишет историю.
- Триггер `guard_task_status` (BEFORE UPDATE OF status) пропускает изменение только если выставлен транзакционный флаг `app.status_change = 'on'`, который ставит исключительно `change_task_status`. Прямой `UPDATE tasks SET status=...` (в том числе через PostgREST) отклоняется ошибкой `P0403`.
- Триггер `log_task_status` (AFTER UPDATE OF status) вставляет ровно одну строку истории с `changed_by = auth.uid()`; при создании задачи `log_task_created` (AFTER INSERT) пишет строку `null → new`.
- Прямые INSERT/UPDATE задачи разрешены менеджеру (колонки `title`, `description`, `object_id`, `assignee_id`); колонка `status` не входит в грант и дополнительно защищена триггером. `DELETE` не выдан никому.
- Архивирование объектов/задач — только `rpc.archive_object` / `rpc.archive_task`: выставляют `deleted_at`, объект каскадно скрывает свои задачи. История и данные физически остаются, поэтому «удалить историю через API» невозможно.
- Ошибки БД используют стабильные SQLSTATE: `P0403` — нет прав, `P0422` — недопустимый переход/состояние, `P0400` — ошибка валидации. Клиент маппит их в человеческие сообщения.

### 5.5. Реплика и отчётные вьюхи

- **Публикация `nova_pub`** создаётся на primary: в Supabase Dashboard (Database → Replication → Publications) либо SQL `create publication nova_pub for table public.profiles, public.objects, public.tasks, public.task_status_history;` под ролью `postgres`/`supabase_admin` (если SQL-создание запрещено правами — используем Dashboard). `wal_level = logical` уже включён в Supabase. `auth.users` не публикуется — персональные данные входа реплике не нужны.
- **Подписка `nova_sub`** создаётся на secondary скриптом `infra/replica/init.sql`: `create subscription nova_sub connection '…' publication nova_pub with (copy_data = true, create_slot = true, slot_name = 'nova_sub_slot');` Создание выполняется суперпользователем контейнера (`POSTGRES_USER`); адрес primary берётся из `.env.replication`, в git не попадает. В контуре разработки подписка может указывать на локальный Supabase, в production — только на облачный проект.
- **Схема secondary** накатывается теми же `supabase/migrations/` (DDL не реплицируется). Порядок: миграции → подписка → сверка счётчиков.
- **Только чтение:** у `nova_ro` нет DML-грантов; дополнительно `default_transaction_read_only = on`. Запись от подписки идёт через служебного суперпользователя контейнера и не пересекается с ролью API.
- **Отчётные вьюхи** (в миграции, создаются на secondary; на primary не нужны):
  - `report_objects` — объект, всего задач, по статусам (`count(*) filter (where status = …)`), доля принятых, дата последнего изменения;
  - `report_workload` — исполнитель, число задач по статусам, число просроченных (по `created_at`), без email;
  - `report_status_ages` — среднее и максимальное время в статусе `on_review` (по `task_status_history`), для контроля приёмки.
- **Сверка:** скрипт `infra/replica/check.mjs` сравнивает `count(*)` и `max(updated_at)` по 4 таблицам между primary (read-only запрос по `DATABASE_URL_PRIMARY_RO`, отдельная роль `nova_check` с `SELECT`) и secondary; расхождение → exit 1. Запускается по расписанию и в CI; результат виден в дашборде и алертах.
- **UUID-ключи** генерируются на primary (`gen_random_uuid()`), поэтому на реплике не нужны последовательности; `task_status_history.id` — identity, но вставки идут только с primary.

## 6. Интеграции

- **Supabase Auth** (email + пароль + TOTP MFA): вход, выход, refresh-сессия, отзыв сессий. Открытая регистрация и самостоятельный сброс пароля отключены; учётные записи выдаёт администратор по регламенту.
- **Supabase PostgREST + RPC** — единственный канал **записи** данных; отдельного write-API на backend нет.
- **Логическая репликация Supabase → PostgreSQL (backend):** publication `nova_pub` → subscription `nova_sub`, плагин `pgoutput`. Требования: `wal_level = logical` на primary, сетевой доступ с backend-хоста к `db.<ref>.supabase.co:5432` (прямое подключение; для IPv4-only сетей — IPv4 add-on или пулер в режиме session), роль репликации с `REPLICATION` и `SELECT` на 4 таблицы. Учтённые ограничения: DDL и RLS-политики не реплицируются (схема накатывается миграциями на обе стороны), последовательности не реплицируются (реплика read-only — не нужны), слот удерживает WAL и при долгом простое может раздувать диск primary — контролируется алертом по лагу и мониторингом размера WAL.
- **Vercel** — деплой статики, SPA-rewrite на `index.html`, security-заголовки, переменные окружения, атомарные релизы и мгновенный откат.
- **Docker Compose** — production-контур: `postgres:16` (secondary) + `api` (Fastify) с healthcheck'ами, volume под данные реплики, сеть без публикации `5432`.
- **Grafana Cloud / Prometheus** — метрики, дашборды, правила алертинга; **Sentry** — ошибки frontend и backend; **uptime-монитор** — доступность из двух регионов.
- **Cloudflare (или edge-провайдер)** — TLS, WAF, защита от ботов и rate limiting на периметре.
- Иных интеграций (платежи, SMS, SSO, внешние API, продуктовая аналитика) нет: это осознанная граница продукта.

## 7. Нефункциональные требования

- **Нагрузка и ёмкость:** до 500 зарегистрированных пользователей, до 5 000 объектов и 100 000 задач; пиковая нагрузка 30 RPS с трёхкратным запасом по CPU и соединениям. Схема и индексы рассчитаны на этот объём; рост сверх него — повод для ревизии архитектуры, а не «надежды на удачу».
- **Latency (p95):** вход ≤ 1 000 мс; список объектов/задач ≤ 400 мс; мутация статуса ≤ 600 мс; отчёт ≤ 300 мс; `/health` ≤ 50 мс.
- **Доступность:** 99.9% в месяц для интерфейса и API; зависящие от провайдера компоненты Supabase/Vercel покрываются их SLA. При недоступности Supabase приложение показывает экран ошибки, а не пустой список. Недоступность backend или реплики влияет только на отчёты.
- **RTO / RPO:** RTO ≤ 60 минут, RPO ≤ 5 минут за счёт PITR. Учения восстановления проводятся по регламенту (минимум ежеквартально) с записью в журнал.
- **Репликация:** лаг p95 ≤ 5 с; при нулевой нагрузке — до 60 с (heartbeat публикации); расхождение `count(*)` по 4 таблицам = 0 после seed и после контрольной серии мутаций; первичная синхронизация ≤ 60 с для эталонного объёма.
- **Объём данных:** ≤ 1 ГБ/год в primary; история растёт линейно (≤ 10 записей на задачу). Реплика занимает столько же плюс WAL-буфер; размер WAL и лаг под алертом.
- **Резервное копирование:** ежедневные полные бэкапы (retention 30 суток) + PITR (окно 7 суток) на primary; проверка восстановления — часть регламента. Бэкапы реплики не делаются: она восстанавливается из primary.
- **Compliance:** обрабатываются ПДн сотрудников (имя, email, история действий). Хостинг — ЕС (Frankfurt); для работы с ПДн в РФ оформляется правовая оценка (152-ФЗ) и, при необходимости, отдельный контур с локальным размещением. PCI DSS, GDPR-фичи, cookie-баннеры и трекеры не применимы: платёжных данных и рекламного трекинга нет.
- **Браузеры:** последние 2 версии Chrome, Edge, Firefox, Safari; iOS Safari 15+, Android Chrome. IE не поддерживается. Минимальная ширина 360 px.
- **Доступность UI:** WCAG 2.1 AA по контрасту, фокус-стили, подписи у полей, статусы передаются цветом **и** текстом, полная работа с клавиатуры.
- **Безопасность заголовков (OWASP Secure Headers):** `Strict-Transport-Security: max-age=31536000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`. **CSP:** `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' https://*.supabase.co; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. `unsafe-eval` запрещён; `unsafe-inline` допускается только для `style-src` и фиксируется как отклонение в §8.1. CSP проверяется на production-сборке и контролируется автотестом.
- **Rate limiting:** на периметре (WAF/edge) и в приложении — Supabase Auth (`rate_limit_*`), `@fastify/rate-limit` на API, лимит попыток входа и блокировка после серии неудач.
- **Отказоустойчивость:** healthcheck'и и автоперезапуск контейнеров, readiness-проба перед приёмом трафика, graceful shutdown backend, атомарные релизы frontend.

## 8. Безопасность (обязательные требования)

> **Четыре обязательных блока:** OWASP (ASVS L2 + Top 10:2021 + API Security Top 10:2023), **JWT**, **RBAC**, **CSRF**. Каждый блок имеет проверяемые требования, попадает в критерии приёмки (§12) и в `docs/decisions.md`. Безопасность — не «скрыть кнопку в UI»: решение принимается в БД, UI лишь отражает его.

- **Целевой уровень:** OWASP ASVS 4.0.3 **Level 2** (закрытая B2B-система с ПДн сотрудников) — с явно зафиксированными отклонениями (ниже).
- **Auth:** Supabase Auth (email + пароль + TOTP MFA), JWT в заголовке `Authorization: Bearer`, сессия на клиенте; открытая регистрация (`disable_signup`) и самостоятельный сброс пароля отключены. Все страницы, кроме `/login`, закрыты guard'ом.
- **Роли:** `manager` (постановщик) и `executor` (исполнитель) в `profiles.role`; роль нельзя сменить через API (нет грантов, нет экрана). Помощники `public.is_manager()` / `public.current_role()` — `security definer`, `stable`, фиксированный `search_path`.
- **RLS включён на всех таблицах** (`alter table ... enable row level security`); доступ по умолчанию запрещён, права выдаются политиками.

### 8.5. JWT: требования к токенам

**Кто выпускает и кто проверяет.** Токены выпускает Supabase Auth (GoTrue). Проверяют их PostgREST и RPC-функции (`auth.uid()`, `auth.jwt()`). Собственный verifier не пишется: используется `supabase-js`. Backend пользовательский JWT не принимает вообще (там `API_TOKEN`), поэтому риск самописной проверки исключён.

| Требование | Значение / правило | Проверка |
|------------|--------------------|----------|
| Формат | JWS, компактный `header.payload.signature`; только подписанный токен | Логин → в заголовке 3 сегмента |
| Алгоритм | Разрешён только алгоритм проекта: **ES256 через JWKS** (рекомендуется) либо HS256 с JWT-secret. Список алгоритмов жёстко задан, `alg: none` и подмена `HS256↔RS256` отклоняются | `curl` с поддельным `alg:none` → 401 |
| Проверка подписи | Только по ключам проекта (JWKS/секрет); `decode` без `verify` запрещён в коде | Ревью: нет `jwt.decode` / `atob`-разбора payload для решений о правах |
| Обязательные claims | `iss` = `https://<ref>.supabase.co/auth/v1`, `aud` = `authenticated`, `exp`, `iat`, `sub` (uuid пользователя), `role`, `session_id`, `aal` | Тест с чужим `aud`/`iss` → 401 |
| Срок жизни access | **1 час** (`jwt_expiry = 3600`); на клиенте авто-refresh | Настройка проекта + проверка `exp - iat = 3600` |
| Refresh-токен | Один активный на сессию, **ротация включена**, детект повторного использования → отзыв всей семьи токенов | Повторное использование старого refresh → 400/401 и разлогин |
| Tаймбокс сессии | inactivity timeout **7 дней**, time-box **30 дней** | Настройки Auth |
| MFA | TOTP включён; для роли `manager` обязателен, для `executor` — обязателен при первом входе и после сброса | Тест: вход менеджера без второго фактора невозможен |
| Отзыв | `signOut()` чистит сессию клиента; смена пароля, смена роли и принудительный revoke в Supabase инвалидируют refresh | Ручной revoke → запрос с токеном → 401 |
| Claims не для прав | `role` в JWT — это `authenticated`, а **не** `manager/executor`. Прикладная роль читается из `profiles` в БД | Тест: подмена claim `role` не меняет доступ |
| PII в токене | В payload есть `email` — считаем его ПДн: токен не логируем, не отправляем в query/URL, не кладём в аналитику | grep по логам и коду на `access_token` в URL |
| Хранение на клиенте | `localStorage` (дефолт `supabase-js`). Риск XSS компенсируется: строгий CSP без `unsafe-inline` в `script-src`, отсутствие сторонних скриптов, `dangerouslySetInnerHTML` запрещён, минимум зависимостей, SRI не требуется из-за локальных бандлов | Проверка CSP-заголовка и отсутствия сторонних `<script>` |
| Логирование | pino redact: `req.headers.authorization`, `*.access_token`, `*.refresh_token`, `password`; Supabase логи не содержат тел запросов | Ручная выборка 20 строк логов |
| Передача | Только HTTPS; HSTS `max-age=31536000; includeSubDomains` | `curl -I` → `strict-transport-security` |
| Ошибки проверки | Наружу только `401`/`403` без деталей (не раскрываем, истёк токен или подпись неверна) | Тест с истёкшим токеном |
| Утечка | При подозрении — ротация JWT-secret в Supabase (все сессии инвалидируются) + запись в журнал инцидентов | Runbook в README |

**Запрещено:** хранить пользовательский JWT в git, логах и аналитике; передавать токен в URL; использовать `service_role`-токен как «пользовательский»; доверять роли из JWT; отключать проверку `exp` «для отладки»; разбирать payload токена для решений о доступе.

### 8.6. RBAC: роли, права, точки проверки

**Модель.** Ролевая модель с двумя ролями и ресурсным условием владения (RBAC + ownership-проверка). Роль хранится в `profiles.role` (`enum user_role`), читается из БД, **не из JWT**.

| Разрешение | Постановщик `manager` | Исполнитель `executor` | Где проверяется |
|------------|-----------------------|------------------------|-----------------|
| `object:read` | все неархивированные | только свои (есть его задача) | RLS `objects_select` |
| `object:create` | да | нет | RLS `objects_insert` |
| `object:update` | да | нет | RLS `objects_update` + триггер |
| `object:archive` | да | нет | `rpc.archive_object` |
| `task:read` | все | только `assignee_id = auth.uid()` | RLS `tasks_select` |
| `task:create` | да | нет | RLS `tasks_insert` + триггер акторов |
| `task:update` (поля) | `title`, `description`, `object_id`, `assignee_id` | нет | колоночные гранты |
| `task:archive` | да | нет | `rpc.archive_task` |
| `task:transition:start` | нет | да, только своя задача | `rpc.change_task_status` |
| `task:transition:submit` | нет | да, только своя задача | `rpc.change_task_status` |
| `task:transition:accept` | да | нет | `rpc.change_task_status` |
| `task:transition:rework` | да, с комментарием | нет | `rpc.change_task_status` |
| `history:read` | по всем видимым задачам | по своим задачам | RLS `history_select` |
| `report:read` | да | нет | `API_TOKEN` + allowlist `Origin` |

**Три эшелона проверки (все обязательны):**
1. **UI** — скрывает недоступные действия; не является защитой (обход через DevTools ожидаем).
2. **API** — PostgREST/RPC: RLS-политики, колоночные гранты, проверка роли и владельца внутри `security definer`-функций.
3. **БД** — триггеры и ограничения: запрет прямого изменения `status`, проверка акторов задачи, `CHECK` на комментарий, append-only история.

**Правила RBAC:**
- **Deny by default:** RLS включён, политик «разрешить всё» нет; отсутствие политики = отказ.
- **Единый источник правды** — БД. Роль в UI используется только для рендера; любое действие повторно проверяется.
- **Нет эскалации привилегий:** у `authenticated` нет `UPDATE` на `profiles.role`; нет политики self-update профиля; роль меняется только администратором по регламенту.
- **Проверка владельца, а не только роли:** исполнитель может двигать статус только задачи с `assignee_id = auth.uid()`; менеджер — любую видимую.
- **Одинаковые ответы для «нет» и «не существует»** (404/пустой массив), чтобы нельзя было перебором ID выяснить наличие задач.
- **Сервисные роли — вне приложения:** `service_role` не используется в рантайме; `nova_ro` — только `SELECT`; `replicator` — только репликация.
- **Матрица прав — код, а не документ:** соответствие «роль → разрешение» реализовано в функциях/политиках и покрыто тестами (§12).

### 8.7. CSRF: модель угроз и меры

**Почему в текущей архитектуре классический CSRF неприменим — и что всё равно делаем.**

| Сценарий | Аутентификация запроса | CSRF возможен? | Мера |
|----------|------------------------|----------------|------|
| Фронтенд → Supabase PostgREST/RPC | `Authorization: Bearer <access_token>` из JS | **Нет:** браузер не прикладывает заголовок автоматически, сторонний сайт не знает токен | Запрет cookie-аутентификации для API; никаких `credentials: include` к Supabase |
| Чтение данных анонимом с anon-ключом | `apikey` + `Authorization` | Нет | Защита — RLS, а не CORS: anon-ключ публичен по дизайну |
| Backend отчётов | `API_TOKEN` (заголовок) | Нет | Токен только в менеджере секретов, TLS, allowlist `Origin` |
| Любой будущий BFF с httpOnly-cookie | Cookie | **Да, если не защитить** | Полный набор требований ниже — обязателен до включения cookie-режима |

**Обязательные требования (проверяемые):**
1. **Никакой аутентификации по cookie.** Supabase-клиент инициализируется без `credentials: 'include'`; cookies `sb-*` не используются для авторизации запросов к API.
2. **Все мутации — только `POST`/`PATCH`/`DELETE`/RPC.** Состояние не меняется через `GET`; ссылки «удалить»/«принять» отсутствуют.
3. **CORS:** для собственного API — allowlist origin, **никогда** `Access-Control-Allow-Origin: *` вместе с `Allow-Credentials: true`.
4. **Кастомный заголовок = барьер для простых форм:** любой запрос, меняющий состояние, несёт `Authorization` (и/или `X-Requested-With`), что выводит его из категории «simple request» и требует preflight.
5. **Проверка `Origin`/`Referer`** на собственном API (Fastify-хук): при наличии `Origin` он обязан совпадать с allowlist, иначе `403`; для same-origin запросов без `Origin` разрешено только чтение.
6. **Если включается cookie-режим (обязательный чек-лист):** `HttpOnly; Secure; SameSite=Lax (или Strict); Path=/`; префикс `__Host-`; CSRF-токен по схеме double-submit (`X-CSRF-Token` + cookie) или синхронизированный токен; проверка токена на каждом небезопасном методе; отказ при несовпадении `Origin`; CORS строго по allowlist; токен ротируется при логине.
7. **XSS как обход CSRF-защиты:** CSP `default-src 'self'`, `script-src 'self'` (без `unsafe-inline`, `unsafe-eval`), `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`; React-экранирование; запрет `dangerouslySetInnerHTML`.
8. **Тесты на CSRF:** кросс-доменный `POST` к Supabase без `Authorization` → `401`; `POST` на API без `API_TOKEN` → `401`, с чужим `Origin` → `403`; запрос с cookie (эмуляция cookie-режима) без CSRF-токена → `403`.

**Запрещено:** вводить cookie-аутентификацию без пункта 6; использовать `state` в URL для изменяющих операций; отключать `SameSite`; разрешать `Credentials: true` для `*`.

### 8.8. Ключевые инварианты (проверяются в БД, не в UI)

1. Исполнитель читает только свои задачи; запрос чужой строки возвращает пустой результат (без утечки факта существования).
2. Исполнитель не может изменить ни одно поле задачи напрямую — только разрешённый переход через `change_task_status`.
3. Переход валидируется по матрице §5.3 с учётом роли и назначения; запрещённый переход не меняет статус и не создаёт историю.
4. История пополняется только триггерами `security definer`; у `authenticated` нет прав INSERT/UPDATE/DELETE, все операции записи отклоняются.
5. Комментарий обязателен при `on_review → rework`; проверка есть и в RPC, и в CHECK-ограничении таблицы истории.
6. Жёсткое удаление данных запрещено; архивирование сохраняет историю.
7. Создание задачи валидирует роли актора и исполнителя (нельзя назначить менеджера исполнителем).
8. Смена исполнителя разрешена только в `new`/`rework`; в остальных статусах отклоняется (нет UI и проверка в триггере).

### 8.9. Секреты и ключи

- В клиент попадает только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (anon-ключ публичен по дизайну, его защищает RLS).
- `service_role` используется исключительно в локальном `scripts/seed.mjs` при инициализации данных; ключ берётся из менеджера секретов, никогда не имеет префикса `VITE_` и не попадает на frontend-хостинг. **В backend его нет ни в каком виде**: backend читает только реплику.
- Роль репликации (`replicator`, атрибуты `LOGIN REPLICATION`, `SELECT` на 4 таблицы; при фильтрации строк RLS на этапе initial copy — `BYPASSRLS` только этой служебной роли) существует исключительно для подписки. Пароль — в менеджере секретов, ротация по регламенту и при подозрении на утечку; контейнер `api` этой переменной не видит.
- Роль API на реплике (`nova_ro`): `LOGIN`, `CONNECT` на БД, `USAGE` на `public`, `SELECT` на таблицы/вьюхи отчётов, `ALTER ROLE nova_ro SET default_transaction_read_only = on`; прав на запись нет ни у одной таблицы. Проверяется тестом: `INSERT` от `nova_ro` → `25006 read_only_sql_transaction`.
- `.env.example` содержит только имена переменных и плейсхолдеры.
- Перед каждым релизом: `grep -R "service_role\|SUPABASE_DB_PASSWORD\|postgresql://postgres" dist/ backend/ src/ .` и проверка git-истории; при утечке — ротация ключа в Supabase и запись в журнал инцидентов.
- GitHub Actions и Vercel получают секреты через настройки окружений, не через файлы в репозитории. Ротация секретов: по регламенту (квартал) и немедленно при утечке или смене состава команды.

### 8.10. Прочие угрозы и их меры

| Угроза | Мера |
|--------|------|
| XSS через название/описание/комментарий | React экранирует по умолчанию; `dangerouslySetInnerHTML` запрещён; CSP без `unsafe-inline` в `script-src` и без `unsafe-eval` (§8.7 п. 7) |
| CSRF | Cookie-аутентификации нет — токен идёт в `Authorization` и не прикладывается браузером автоматически; мутации только небезопасными методами; при включении cookie-режима — полный чек-лист §8.7 п. 6 |
| Подделка/подмена JWT | Проверка подписи платформой, allowlist алгоритма, отказ `alg: none`, контроль `iss`/`aud`/`exp`; прикладная роль из БД, а не из claim (§8.5) |
| Утечка access/refresh-токена | `localStorage` + строгий CSP; токен не в URL и не в логах (redact); ротация refresh и детект повторного использования; revoke сессий при подозрении (§8.5) |
| Эскалация роли | Нет грантов на `profiles.role`, нет политики self-update, роль меняется только администратором; RBAC deny-by-default (§8.6) |
| SQL-инъекции | PostgREST/параметризованные RPC, никакого динамического SQL |
| Mass assignment | белый список полей в RPC и колоночные гранты; Zod на клиенте |
| Перебор учётных записей | лимиты Supabase Auth + rate limiting на периметре, блокировка после серии неудач, MFA |
| Раскрытие данных в ошибках | единые тексты «Нет доступа» / «Недопустимый переход»; детали только в логах |
| `security definer` и подмена `search_path` | у всех функций `set search_path = public, pg_temp`; `execute` для `anon` отозван |
| Утечка PII в логи | в `console.error` только коды ошибок, без email и текстов задач; pino-логи backend без тел запросов и значений полей; redact-список в конфиге |
| Компрометация backend | backend не имеет credentials с правом записи в primary; максимум ущерба — чтение агрегатов с реплики. `API_TOKEN` обязателен, TLS, allowlist `Origin`, rate limiting |
| Утечка дампа реплики | реплика содержит те же данные, что primary, поэтому защищается как primary: доступ только по приватной сети, без публикации порта `5432`, отдельный пароль роли |
| Подмена источника данных | backend никогда не пишет и не кэширует ответы дольше 30 с; отчёты помечены `source: replica` и `lag_seconds`, чтобы читатель видел актуальность |
| Отказ в обслуживании | WAF и rate limiting на периметре, таймауты запросов, лимиты соединений в `pg`, автоперезапуск контейнеров |

### 8.11. Backend и реплика: границы доверия

1. Backend — **read-only consumer**: нет write-маршрутов, нет `service_role`, нет прямого подключения к primary. Проверяется grep-тестом и отсутствием переменных в окружении контейнера `api`.
2. Реплика не участвует в выдаче прав: RLS-политики копируются миграциями, но backend ходит от служебной роли `nova_ro` и отдаёт только агрегаты (без email, без `description`, без комментариев).
3. API доступен только по TLS и токену; allowlist `Origin`, rate limiting, CORS без `*` с credentials (§8.7). Публичного анонимного доступа нет.
4. Ошибки API не раскрывают SQL и схему: наружу — `500` с кодом `E_INTERNAL`, детали только в логах контейнера.
5. Отключение реплики не влияет на аутентификацию и запись: продукт остаётся работоспособным, отчёты возвращают `503`.

## 9. UX / клиенты

- **Клиенты:** адаптивное веб-приложение (SPA), desktop-first, пригодно с 360 px; отдельного мобильного приложения нет.
- **SSR/SEO:** не нужны (закрытая система) — чистый SPA.
- **i18n:** русский язык интерфейса без i18n-фреймворка; даты `dd.MM.yyyy HH:mm`, часовой пояс отображения Europe/Moscow, в БД — `timestamptz` UTC.
- **Экраны и маршруты:**
  - `/login` — форма email/пароль, шаг MFA-кода, ошибки входа, подсказка «доступ выдаёт администратор».
  - `/objects` — список объектов: название, адрес, прогресс (принято/всего), счётчики по статусам; у постановщика кнопка «Новый объект» и поиск по названию/адресу; пустое состояние.
  - `/objects/:id` — карточка объекта: заголовок, адрес, список задач (название, статус, исполнитель, автор, дата), «Новая задача», редактирование/архивирование объекта; пустое состояние «задач пока нет».
  - `/tasks/:id` — карточка задачи: данные, статус, исполнитель, автор, дата создания, действия по матрице, история статусов с комментариями; модалка возврата на доработку; архивирование задачи.
  - `/my-tasks` — только исполнитель: свои задачи, сгруппированные по 5 статусам, со счётчиками.
  - `/reports` — только постановщик: сводка по объектам, загрузка исполнителей, сроки приёмки; индикатор актуальности (`lag_seconds`).
  - `*` — 404 с ссылкой на список.
- **Оболочка:** верхняя навигация «Объекты», «Мои задачи» (у исполнителя), «Отчёты» (у постановщика), имя и роль текущего пользователя, выход. Пункты, недоступные роли, не отображаются.
- **Действия в карточке задачи:** показываются только разрешённые текущему пользователю в текущем статусе (§5.3); для остальных действий кнопок нет. Дублирующая защита — БД.
- **Состояния:** загрузка (скелетон), пусто (текст + CTA), ошибка (сообщение + «Повторить»), недоступно (404/«нет доступа»), деградация отчётов (баннер «данные недоступны»); оптимистичных обновлений нет — после мутации инвалидируем запросы.
- **Формы:** обязательные поля с Zod-валидацией, ошибки под полем, кнопка блокируется на время отправки, двойной submit исключён.
- **Подтверждения:** архивирование объекта/задачи — диалог с явным предупреждением; возврат на доработку — модалка с обязательным комментарием (до 2000 символов).
- **Доступность:** клавиатурная навигация, `Esc` закрывает модалки, focus trap, `aria-label` у иконочных кнопок, контраст ≥ 4.5:1, статусы подписаны текстом.
- **Адаптив:** таблица задач на < 768 px превращается в карточки; навигация сжимается; горизонтального скролла нет.

## 9c. CI/CD и окружения

- **Окружения:**
  - `local` — Supabase CLI + Docker (frontend, api, secondary PostgreSQL), данные разработчика.
  - `staging` — отдельный проект Supabase и отдельный деплой frontend/backend; эталонные данные, тот же набор миграций; используется для приёмочных и security-прогонов.
  - `production` — Supabase Cloud (primary, PITR), Vercel (frontend), изолированный контур backend + secondary PostgreSQL.
- **Локальный запуск:** `supabase start` → `supabase db reset` (миграции + seed) → `docker compose up -d` (secondary + api + init подписки) → `npm run dev`; переменные из `.env.local` и `.env.replication`.
- **Состав `docker-compose.yml`:** `replica` (`postgres:16`, healthcheck `pg_isready`, порт только во внутренней сети, том `pgdata`), `replica-init` (одноразовый: миграции + `init.sql` + проверка `pg_stat_subscription`), `api` (build из `backend/`, `depends_on: replica healthy`, `API_TOKEN`, `DATABASE_URL` только к реплике, healthcheck `GET /health`, read-only rootfs).
- **CI (GitHub Actions):**
  - `ci` — `npm ci`, `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` (frontend).
  - `backend` — то же для `backend/` (отдельный `package.json`), плюс сборка Docker-образа.
  - `db-test` — `supabase db start` + pgTAP-тесты RLS/переходов.
  - `replication-test` — два контейнера PostgreSQL, публикация/подписка, сверка `count(*)`, запрет записи от `nova_ro`, `/health/replication` = `streaming`.
  - `security` — `npm audit --audit-level=high` (frontend и backend), `gitleaks detect --redact`, проверка security-заголовков и CSP в собранной конфигурации, grep-тест «нет `service_role` в бандле и образе», проверка чек-листа ASVS.
  - `e2e` — Playwright smoke по ключевым сценариям (§4) на staging-контуре.
  - Красный job блокирует merge. CI не деплоит.
- **Релиз:** merge в `main` → CI зелёный → автомиграции применяются в staging (`supabase db push`) → e2e/smoke → ручное подтверждение → миграции в production → деплой frontend (Vercel, атомарно) → деплой backend (Docker-образ с тем же тегом) → проверка `/health` и `/health/replication` → запись в журнал релизов.
- **Кто деплоит:** ответственный разработчик; production-релиз требует явного подтверждения (GitHub Environment с protection rule). Миграции применяются только через CI-пайплайн с сохранённым логом.
- **Откат:** Vercel Instant Rollback для frontend; предыдущий Docker-тег для backend; миграции forward-only (без down-скриптов) — изменения схемы только добавляющие, поэтому откат кода не требует откат схемы. Откат реплики — пересоздание из primary.
- **Секреты:** Vercel env vars (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`); менеджер секретов (GitHub Environments + secrets контура) для `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `DATABASE_URL`, `API_TOKEN`, `DATABASE_URL_PRIMARY_RO`; `service_role` используется только локальным seed и не хранится в CI.
- **Наблюдаемость релиза:** дашборд релиза (ошибки, p95, 5xx, лаг репликации) проверяется в течение 30 минут после деплоя; при отклонении — откат по runbook.

## 10. Инженерные стандарты

- **Язык кода / стиль:** TypeScript strict; ESLint + Prettier; идентификаторы английские, комментарии и документация — русские (`catalogs/code-comments.md`). Никаких `any` и `@ts-ignore` без указания причины.
- **Типизация:** `strict: true`, границы (env, ответы RPC, формы) валидируются Zod + сгенерированные типы БД (`supabase gen types typescript`).
- **Автотесты (обязательны в том же изменении):**
  - unit: чистая матрица переходов и функция доступных действий;
  - SQL/pgTAP: RLS, запрещённые переходы, неизменяемость истории, CHECK-ограничения;
  - backend: unit-тесты SQL отчётов на фикстурах + integration «write-метод → 405», «INSERT от `nova_ro` → 25006»;
  - e2e: Playwright smoke по сценариям §4 на staging;
  - репликация: `infra/replica/check.mjs` в CI;
  - security: набор из §8.5–§8.7 (JWT, RBAC, CSRF) как исполняемые кейсы.
- **Запрещённые библиотеки:** тяжёлые UI-киты (MUI, AntD, Bootstrap), state-менеджеры на весь проект (Redux/MobX) без нужды, ORM поверх PostgREST, любые библиотеки, требующие `service_role` на клиенте, и любые write-клиенты Supabase в backend.
- **Обязательные практики:** только миграции (никаких ручных правок схемы); все изменения статуса — через RPC; RLS на каждой таблице; `security definer` с фиксированным `search_path`; env через Zod; error boundary; проверка бандла и образа на секреты; conventional commits; атомарные коммиты; backend-образ без `postgres`-клиента с правом записи и без build-args с секретами.
- **Безопасность в каждой задаче:**
  - **JWT:** не разбирать токен ради решений о правах, не логировать, не передавать в URL; правила §8.5 — часть INVARIANTS каждой задачи с авторизацией.
  - **RBAC:** каждое новое действие проходит три эшелона (§8.6); новый маршрут/экран без RLS-политики — блокирующий дефект, а не TODO.
  - **CSRF:** никаких cookie для API, никаких изменяющих `GET`; при добавлении cookie-режима — чек-лист §8.7 п. 6 целиком, а не частично.
  - **OWASP:** в PR-описании — строка «OWASP: A01..A10 затронуты/не затронуты»; `npm audit` и `gitleaks` в CI обязательны; CSP-заголовки проверяются на production-сборке.
  - **Артефакты:** `docs/security/threat-model.md` (активы, угрозы, меры, остаточные риски) и `docs/security/asvs-l2-checklist.md` (таблица §8.1 с отметками) поддерживаются в актуальном состоянии.
- **Соглашения:** БД — `snake_case`; TS — `camelCase`; компоненты — `PascalCase`; файлы компонентов — `PascalCase.tsx`, утилиты — `kebab-case.ts`; `backend/` — отдельный workspace с `src/routes`, `src/domain`, `src/db`, `infra/replica`; ветка `main` + короткоживущие ветки, merge только через PR с обязательным review.
- **Документация:** ADR на каждое архитектурное решение (`docs/decisions.md`), runbooks инцидентов и восстановления (`docs/runbooks/`), журнал релизов, актуализация README при изменении контрактов.

## 12. Критерии приёмки

**Функциональность**
- [ ] Вход тремя учётными записями (1 постановщик, 2 исполнителя), проверка MFA, выход, сохранение сессии после F5; неавторизованный редиректится на `/login`; `/login` недоступен авторизованному.
- [ ] Открытая регистрация отключена: прямой `POST /auth/v1/signup` не создаёт пользователя.
- [ ] Постановщик создаёт/редактирует/архивирует объекты; исполнитель видит только объекты со своими задачами и не видит кнопок управления.
- [ ] Постановщик создаёт задачи с назначением исполнителя; исполнитель видит только свои; чужая задача недоступна по прямой ссылке.
- [ ] Все 5 разрешённых переходов работают для правильной роли; 15 запрещённых пар отклоняются БД; статус и история не меняются.
- [ ] `on_review → rework` без комментария отклоняется и в UI, и в БД; комментарий виден в истории.
- [ ] История: строка создания + по одной строке на переход, порядок от новых к старым, актор = реальный пользователь; INSERT/UPDATE/DELETE через API запрещены.
- [ ] «Мои задачи» показывает все свои задачи по статусам; счётчики совпадают.
- [ ] Раздел «Отчёты» доступен только постановщику, показывает три отчёта и индикатор актуальности; при недоступной реплике — понятное состояние деградации без блокировки остальных экранов.
- [ ] Стартовые данные: 1 постановщик, 2 исполнителя, 3 объекта, ≥ 8 задач, покрыты все 5 статусов.

**Безопасность — доступ (RBAC, §8.6)**
- [ ] Исполнитель не читает чужие задачи/объекты через PostgREST (0 строк).
- [ ] Исполнитель не изменяет чужие задачи и не меняет статус напрямую (403/0 строк).
- [ ] `anon` не читает ни одной таблицы и не имеет `execute` на RPC.
- [ ] Жёсткое удаление объектов, задач и истории невозможно ни одной ролью.
- [ ] В `dist/` и git-истории нет `service_role`; в бандле только anon-ключ.
- [ ] `security definer`-функции недоступны `anon`, имеют фиксированный `search_path`.
- [ ] Матрица прав §8.6 проверена построчно тестами: для каждой пары «роль × действие» есть кейс «разрешено» и кейс «отказано».
- [ ] Эскалация роли невозможна: `PATCH /profiles` с `role=manager` → 0 строк / ошибка; подмена claim `role` в JWT не даёт прав менеджера.

**Безопасность — JWT и MFA (§8.5)**
- [ ] Токен с `alg: none` / подменённым алгоритмом отклоняется (`401`).
- [ ] Токен с чужим `iss` или `aud` отклоняется.
- [ ] Истёкший access-токен → `401`, клиент делает refresh и продолжает работу без потери состояния формы.
- [ ] Access-токен живёт 1 час; после ротации refresh старый refresh-токен недействителен (reuse detection).
- [ ] Вход без второго фактора для роли `manager` невозможен; при отключении MFA сессия инвалидируется.
- [ ] `signOut()` и принудительный revoke инвалидируют сессию (`401` на следующем запросе).
- [ ] В логах frontend/backend нет `access_token`, `refresh_token`, `authorization`, пароля; токен не встречается в URL.
- [ ] Роль для UI берётся из `profiles`, а не из JWT-claim.

**Безопасность — CSRF (§8.7)**
- [ ] Кросс-доменный `POST` к Supabase без `Authorization` → `401`; с валидным токеном — успех.
- [ ] Клиент не инициализируется с `credentials: 'include'`; cookie `sb-*` не используется для авторизации.
- [ ] Все изменяющие операции — `POST`/`PATCH`/`DELETE`/RPC; ни один `GET` не меняет состояние.
- [ ] API: запрос без `API_TOKEN` → `401`, с чужим `Origin` → `403`, CORS не отдаёт `*` с credentials.
- [ ] CSP отдаётся в production-сборке, `unsafe-eval` отсутствует, `frame-ancestors 'none'`.

**Безопасность — OWASP (§8.1–8.3)**
- [ ] `npm audit --audit-level=high` — 0 high/critical (frontend и backend); `gitleaks detect` — 0 находок.
- [ ] Инъекции: значения вида `'; drop table tasks; --` в названии/описании/комментарии сохраняются как текст и не влияют на SQL.
- [ ] Supabase Security Advisors: нет critical; RLS включён на всех 4 таблицах.
- [ ] `docs/security/threat-model.md` и `docs/security/asvs-l2-checklist.md` заполнены; отклонения из §8.1 совпадают с фактическим состоянием.
- [ ] Ошибки наружу не раскрывают SQL, имена таблиц и факт существования чужих записей.

**Backend и репликация**
- [ ] `docker compose up -d` поднимает `replica` (healthy) и `api`; повторный запуск идемпотентен.
- [ ] `pg_stat_subscription` → `streaming`; лаг ≤ 5 с; `/health/replication` отдаёт `status`, `lag_seconds`, `last_error`.
- [ ] `count(*)` и `max(updated_at)` по `profiles`, `objects`, `tasks`, `task_status_history` совпадают с primary после seed и после 10 мутаций статуса.
- [ ] `GET /api/reports/objects|workload|status-ages` возвращают агрегаты, совпадающие с SQL на primary; в ответе нет email, `description`, комментариев.
- [ ] `POST/PUT/PATCH/DELETE` на любой маршрут → `405`; `INSERT/UPDATE/DELETE` от `nova_ro` → `25006`.
- [ ] В `backend/`, образе `api` и git-истории нет `service_role`, `SUPABASE_DB_PASSWORD` и строки подключения к primary; контейнер `api` не видит `DATABASE_URL_PRIMARY*`.
- [ ] Остановка `replica` не ломает вход и смену статусов в UI; отчёты возвращают `503` с понятным кодом.
- [ ] Фронтенд-бандл не содержит адресов backend и отчётных данных; в `dist/` только `VITE_SUPABASE_*`.

## 13. Заметки

- **Профиль:** `web-app` + собственный read-only backend. **Решения по модулям:** §11.
- **Дизайн:** `INPUT/design/Design.html` — единственный визуальный источник; бренд NOVA CRM.
- **Контуры:** production (Vercel + Supabase Cloud + изолированный backend/replica), staging (отдельный проект Supabase и отдельные деплои), local.
- **Схема потоков данных:**

```text
Браузер ──(JWT, RLS)──► Supabase PostgREST/RPC ──► PostgreSQL 15 (primary)   [ЗАПИСЬ]
                                                         │ logical replication (nova_pub → nova_sub)
                                                         ▼
                                        PostgreSQL 16 (secondary, read-only)
                                                         │ SELECT (роль nova_ro)
                                                         ▼
                                        Fastify API (read-only, TLS) ──► JSON отчёты / health / metrics
```

- **Главный тезис защиты:** «Права и переходы проверяются в PostgreSQL (RLS + триггеры + security definer RPC). Интерфейс лишь скрывает недоступные кнопки; прямой запрос к Supabase с anon-ключом не даёт ни прочитать чужое, ни обойти цикл статусов, ни подделать историю. Второй контур (backend + реплика) умеет **только читать агрегаты**: у него нет ни `service_role`, ни строки подключения к primary, ни write-маршрутов — компрометация backend не даёт изменить ни одной задачи».

### 13.1. Принятые решения и допущения

| № | Вопрос, не описанный в требованиях | Решение | Почему |
|---|------------------------------------|---------|--------|
| 1 | Жёсткое удаление vs история | Архивирование (`deleted_at`), `DELETE` не выдан никому | Требование удаления несовместимо с неизменяемой историей: физическое удаление задачи уничтожило бы её историю |
| 2 | Кто из постановщиков принимает задачу | Любой `manager`, не только автор | Требование говорит «постановщик», а не «автор»; в примере истории задачу принимает другой менеджер |
| 3 | Когда можно менять исполнителя | Только в статусах `new` и `rework` | В работе/на проверке смена исполнителя ломает ответственность и историю |
| 4 | Комментарий при других переходах | Необязателен; хранится, если передан | Требование обязывает комментарий только для возврата на доработку |
| 5 | Создание задачи в истории | Отдельная запись `null → new` | Иначе история не объясняет, откуда взялся статус «Новая» |
| 6 | Что видит исполнитель в объектах | Объекты, где есть хотя бы одна его неархивированная задача, включая принятые | Требование: «объекты, в которых у него есть задачи» — без ограничения по статусу |
| 7 | Видят ли исполнители чужие имена | Да, только имя и роль (без email) | Нужно отображать автора задачи; email — чувствительнее и не нужен |
| 8 | Может ли исполнитель редактировать поля задачи | Нет, только переходы | Требование не даёт исполнителю права редактировать задачу |
| 9 | Может ли менеджер создать задачу сразу в другом статусе | Нет, только `new` | Цикл начинается с «Новая»; иначе можно обойти историю |
| 10 | Регистрация, пароли, роли | Регистрация и самостоятельный сброс отключены; пользователи и роли создаются администратором по регламенту | Требование бизнеса; провижининг через регламент снижает поверхность атаки |
| 11 | Мультитенантность | Одна компания на инсталляцию | В требованиях нет нескольких компаний |
| 12 | Уведомления | Вне границ продукта | Продукт — источник статуса; доставка сообщений — корпоративный канал |
| 13 | Часовой пояс и язык | ru-RU, отображение Europe/Moscow, хранение UTC | Строительная компания в РФ |
| 14 | Нагрузка и SLA | Ёмкость 500 пользователей / 5 000 объектов / 100 000 задач, доступность 99.9% | Расчёт под профиль компании и трёхкратный запас; выше — ревизия архитектуры |
| 15 | Хостинг данных | Supabase Cloud, eu-central-1 | Управляемый Postgres с PITR и RLS; для ПДн в РФ требуется отдельная правовая оценка |
| 16 | Пароли учётных записей | ≥ 12 символов, передаются по защищённому каналу, не хранятся в репозитории, смена при первом входе | Безопасность и требование «секреты не в репозитории» |
| 17 | Кто может архивировать принятые задачи | Постановщик, в любом статусе, с подтверждением | Требование не ограничивает; данные и история сохраняются |
| 18 | Нужен ли свой backend при Supabase | Да, но **только read-only**: отчёты, агрегаты, health. Запись остаётся в Supabase | Требование «права работают даже при прямом обращении к Supabase» несовместимо с параллельным write-API: два пути записи = два источника правды |
| 19 | Роль вторичной БД | Логическая реплика Supabase → PostgreSQL 16 (subscriber), read-only | Разгружает primary на отчётах, обеспечивает контрольную копию данных и предсказуемую отчётность |
| 20 | Где разворачивается backend | Отдельный production-контур (VPS с Docker Compose или managed PaaS) с TLS, токеном и мониторингом; локальный compose — только для разработки | Эксплуатация требует наблюдаемости и изоляции; публичного анонимного доступа нет |
| 21 | Тип репликации и что не передаётся | Logical (`pgoutput`), публикуются 4 таблицы. DDL, RLS-политики и последовательности **не реплицируются** | Ограничение PostgreSQL: схема на обеих сторонах накатывается одними миграциями, реплика read-only, последовательности не нужны (UUID с primary) |
| 22 | Кто подключается к primary для подписки | Служебная роль `replicator` (`LOGIN REPLICATION` + `SELECT` на 4 таблицы). Пароль — только в менеджере секретов; `api` его не видит | Принцип минимальных привилегий: у backend нет ни `postgres`, ни `service_role`. Если initial copy фильтруется RLS — `BYPASSRLS` только этой роли, с записью в decisions |
| 23 | Метрика актуальности отчётов | `lag_seconds` в `/health/replication` и в каждом ответе отчёта (`source: replica`) | Читатель должен видеть, что данные вторичны; скрытый лаг создаёт ложное доверие |
| 24 | PII в отчётах | Только агрегаты и `full_name`; без email, `description` и комментариев | Минимизация: даже при утечке backend не раскрывает содержимое задач |
| 25 | Что если реплика отстала или упала | Отчёты → `503` с кодом; UI работает; реплика пересоздаётся из primary | Основной продукт не должен зависеть от вторичного контура |
| 26 | Удаление данных и репликация | `DELETE` не используется; архивирование — это `UPDATE`, поэтому реплицируется | Отказ от `DELETE` снимает вопрос `REPLICA IDENTITY FULL` и сохраняет историю |
| 27 | Какой уровень OWASP брать за цель | **ASVS 4.0.3 Level 2** | L3 требует мер (аудит криптографии, усиленный мониторинг), не снижающих риск в закрытой B2B-системе; L2 закрывает актуальные угрозы полностью |
| 28 | Где хранить JWT на клиенте | `localStorage` (дефолт `supabase-js`) при строгом CSP | Cookie-режим требует BFF и полноценной CSRF-инфраструктуры (§8.7 п. 6); принятый риск компенсирован CSP без `unsafe-inline`, отказом от сторонних скриптов и запретом `dangerouslySetInnerHTML` |
| 29 | Позиция по CSRF | **Cookie-аутентификация для API не используется**, поэтому классический CSRF неприменим; меры §8.7 п. 1–8 обязательны, чек-лист cookie-режима действует при его введении | Структурный отказ от cookie честнее формального токена, который нечем проверить |
| 30 | Модель авторизации | **RBAC по двум ролям + ресурсное условие владения** (`assignee_id = auth.uid()`) | Чистый RBAC не выражает «только свои задачи»; полноценный ABAC/PBAC избыточен для двух ролей и трёх сущностей |
| 31 | Источник прикладной роли | **`profiles.role` в БД**, не JWT-claim `role` | Claim `role` в Supabase — это `authenticated`, а не бизнес-роль; права обязаны читаться из таблицы, иначе смена роли не применялась бы мгновенно |
| 32 | MFA | TOTP обязателен для всех учётных записей | Закрытая система с ПДн и историей работ: второй фактор — базовая гигиена, а не опция |
| 33 | Как доказывать безопасность владельцу продукта | Артефакты `docs/security/threat-model.md` + `asvs-l2-checklist.md` + исполняемые тесты | Таблица «угроза → мера → тест» проверяема, в отличие от утверждения «безопасно» |

### 13.2. Остаточные риски и принятые ограничения

- **Размещение данных в ЕС.** Требуется правовая оценка 152-ФЗ до обработки реальных ПДн; при необходимости — отдельный контур с локальным размещением. До оценки продукт используется на данных, не содержащих ПДн третьих лиц.
- **Один регион.** Доступность 99.9% зависит от SLA Supabase и edge-провайдера; мультирегион не заявляется. Реплика — не HA-решение и не автоматический failover.
- **Токен в `localStorage`.** Компенсирован CSP без `unsafe-inline`/`unsafe-eval`, отсутствием сторонних скриптов и запретом `dangerouslySetInnerHTML`; при появлении BFF-слоя переносится в httpOnly-cookie с чек-листом §8.7 п. 6.
- **Провижининг вне интерфейса.** Ошибка администратора при создании учётной записи возможна; компенсируется регламентом, журналом операций и проверкой роли после создания.
- **Криптография делегирована.** Хеширование паролей и подпись JWT обеспечивает Supabase; собственный аудит криптографии не проводится (ASVS L2 этого не требует).
- **Слот репликации удерживает WAL.** При длительном простое подписчика WAL на primary растёт; контролируется алертом по лагу и мониторингом размера WAL, при инциденте слот пересоздаётся.
- **Отчётность с лагом.** Данные отчётов вторичны по определению; каждый ответ содержит `lag_seconds`, интерфейс отображает актуальность.

### 13.3. Открытые вопросы к владельцу продукта (зафиксированы как допущения, не блокируют эксплуатацию)

1. Должен ли принимать задачу только её автор-постановщик или любой руководитель? — принято: любой.
2. Нужно ли показывать архив (архивированные объекты и задачи) отдельным разделом? — принято: скрываются, данные в БД сохраняются.
3. Нужны ли фотоотчёты и уведомления как часть продукта? — принято: вне границ продукта (§2.2); при изменении границ требуется пересмотр модели данных и интеграций.
4. Нужен ли публичный стенд отчётности для внешних подрядчиков? — принято: нет; API отчётности доступен только внутри контура.
