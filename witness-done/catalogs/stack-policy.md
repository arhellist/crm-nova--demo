# Политика стека Witness Done

> Канон для шагов 01–08. **Стек не фиксирован каноном.**
> Ни один язык, фреймворк и СУБД не запрещены и не назначены «по умолчанию». Фабрика не выбирает
> стек за команду: она фиксирует выбор и его причину, а затем проверяет, что на этом стеке есть
> типы, линтер, тесты и исполняемый runtime-план.
> Примеры в `LIBRARY/*/SPEC.md` часто написаны на Node/React — это **референс контрактов**
> (API, модели, инварианты), а не обязательный runtime.

## Принцип: стек — решение, а не default

1. **Стек указан в ТЗ** (`INPUT/TECH_SPEC.md` §3) — он и есть решение. Шаг 03 фиксирует его в ADR
   `0001-backend-stack.md`: язык, версия, ключевые библиотеки, причина выбора.
2. **Стек не указан** — фабрика **не подставляет** вариант по умолчанию. Она предлагает 2–3
   кандидата с tradeoff (навыки команды, NFR, экосистема, эксплуатация, срок) и останавливается
   с вопросом человеку (`needs_human` / `INPUT/ANSWERS.md`). Ответ становится ADR.
3. **Предпочтения команды** (`TECH_SPEC` §10) сильнее общих соображений: если команда умеет
   только один язык, это и есть правильный выбор, даже если он «непопулярен».
4. **Смена стека после фиксации** — новое ADR и оформленное изменение (`R02`→`R05`), а не правка
   по ходу (Decision lock, `catalogs/completeness-policy.md`).

Нет «правильного» языка. Неправилен только необоснованный выбор — или выбор, который нечем
проверить.

## Что обязательно на любом стеке

Требования канона — не про язык, а про свойства. Их надо выполнить независимо от того, что
выбрано.

| Свойство | Требование | Где живёт |
|---|---|---|
| Статическая проверка | typecheck/компилятор в CI и локально; для динамических языков — типизированный слой на границах (`catalogs/typing-and-tests.md`) | `verify-commands.md`, CI |
| Линтер | конфиг в корне, одна команда `lint` | `OUTPUT/tooling/lint-setup.md` |
| Автотесты | раннер под стек, кейсы несут номера `Axx.k` | `catalogs/typing-and-tests.md` |
| Команды приёмки | `lint` / `typecheck` / `test` — реальные команды этого стека, не заглушки | `OUTPUT/tooling/verify-commands.md` |
| Рантайм | план подъёма, готовности, seed, teardown и проверок по фразам | `OUTPUT/runtime/runtime-plan.json` |
| Комментарии | подробные, по-русски, «зачем / контракт / ветки» | `catalogs/code-comments.md` |
| Безопасность | authz, валидация входов, секреты вне кода — по правилам выбранного стека | `OUTPUT/security/*`, INVARIANTS |

Если для выбранного стека чего-то из этого нет в экосистеме — это не повод пропустить проверку,
а повод построить её (компилятор, линтер, contract-тесты, runtime-план).

## Backend

Допустим **любой** язык и платформа, на которых команда умеет эксплуатировать сервис: Node/TS, Go,
Java/Kotlin, Python, PHP, Ruby, Rust, C#, Elixir, Scala — список открыт и в каноне не закрывается.

Что проверяет фабрика (шаги 01–08):

- ADR с причиной выбора и версией языка;
- линтер и тест-раннер именно этого стека в `verify-commands.md`;
- типы на границах (схемы валидации входа/выхода), даже если язык динамический;
- `runtime-plan.json` описывает подъём и проверки на этом стеке;
- security baseline одинаков: валидация входов, отсутствие секретов в репозитории, параметризованные
  запросы, явные коды ошибок — это не зависит от языка.

## Frontend

Фреймворк — по ТЗ и навыкам команды: React, Vue, Svelte, Angular, Solid, HTMX, серверный рендер,
шаблоны — или его отсутствие. Канон не требует React.

Требования не про фреймворк:

- дизайн следует токенам из `INPUT/DESIGN.html` (`catalogs/design-input.md`);
- доступность (клавиатура, контраст, семантика) — часть приёмки, а не «потом»;
- типы на границах компонентов/API, если в экосистеме есть типы;
- критичные пользовательские сценарии покрыты component/e2e-смоуком (`catalogs/contour-smoke.md`).

## Данные и инфраструктура (по нагрузке / NFR)

Подключать **только при необходимости** (YAGNI), фиксировать в `nfr.md` + ADR. Ниже — не
обязательный набор, а примеры классов задач: выбирайте то, что знаете и чем будете управлять.

| Класс | Примеры (не требования) |
|-------|-------------------------|
| OLTP БД | PostgreSQL, MySQL/MariaDB, SQL Server, Oracle, SQLite (для малого), документные/wide-column при явном обосновании |
| OLAP / аналитика | ClickHouse, DuckDB, BigQuery, Snowflake, колоночные расширения своей СУБД |
| Кэш / лимиты / adapter | Redis, Valkey, Memcached, in-process кэш |
| Очереди / MQ | RabbitMQ, NATS, Kafka, SQS-совместимые, PostgreSQL-очереди |
| Jobs | планировщик выбранного стека (BullMQ, Sidekiq, Celery, Quartz, `cron` + воркер) |
| Observability | OpenTelemetry, Prometheus, Grafana, Loki, стек облака |
| Поиск | полнотекстовый поиск своей СУБД → Elasticsearch/OpenSearch при росте |

Не ставить Kafka/ClickHouse/микросервисы «на будущее» без NFR: сложность — тоже стоимость.

## LIBRARY и смена стека

1. Контракты модуля (API, модели, security invariants, CONFLICTS) — переносятся на любой стек.
   `id` модуля (`logging-pino`, `email-nodemailer`, …) — id контракта, а не обязательная библиотека.
2. Примеры реализации в SPEC (Express, Sequelize, Socket.IO, Pino и т.п.) — иллюстрация. В
   `OUTPUT/docs/07_module_plan.md` (блок отличий) указать эквивалент выбранного стека; **не**
   копировать SPEC в OUTPUT; при другом стеке вердикт — `adapt`.
3. Если модуля под выбранный стек нет — `meta-prompt-generator` или `gaps.md`: контракт
   реализуется заново, а не копируется чужой код as-is.

## Стек в ТЗ пуст

Правильного «default» нет, поэтому подстановки тоже нет.

| Шаг | Что делает фабрика |
|---|---|
| 01 | Фиксирует отсутствие стека как вопрос `needs_human`, а не как «возьмём привычное» |
| 01 | Предлагает 2–3 варианта: чем отличаются, что дороже в эксплуатации, что уже знает команда |
| 02–03 | После ответа человека пишет ADR и constitution с выбранным стеком и версиями |
| 08 | Ставит линтер, typecheck, тесты и CI под выбранный стек |

Если человек отвечает «решай сам» — фабрика обязана всё равно назвать вариант и причину в ADR,
а не оставить выбор молчаливым: молчаливый выбор невидим в ревью.

Если ответа нет после трёх попыток (`PIPELINE/01`), допущение записывается явно: ADR с выбранным
вариантом, `defaults_applied: true` в `MANIFEST` и пометка высокого риска в `01_analysis.md`.
Это допущение, а не канон: его меняют оформленным изменением, когда команда ответит.

## Запреты

- Считать примеры из `LIBRARY` обязательным runtime или «правильным стеком».
- Подставлять стек по умолчанию и не писать ADR.
- Объявлять язык вне закона: **в каноне нет запрещённых языков**.
- Выбирать стек, для которого команда не может обеспечить эксплуатацию (деплой, логи, бэкапы).
- Тянуть инфраструктуру «на будущее» без NFR.
- Оставлять `verify-commands.md` с чужими командами (`npm test` в Go-проекте) — гейт исполнит их
  и получит ложный провал или ложный успех.
