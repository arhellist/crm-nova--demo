# Политика полноты документации и D-цепочки

> Канон Witness Done (правило действует с v1.10). Цель: OUTPUT достаточен для **полной** разработки всего IN SCOPE из ТЗ без «додумывания» продукта; при этом каждый D укладывается в **жёсткий SIZE_BUDGET** и содержит HOW / INVARIANTS / ACCEPTANCE (см. `TEMPLATES/dev-prompt.md`).

## Определение «полноты»

Прогон **не** считается качественным, если агент разработки вынужден изобретать:

- **цель бизнеса / KPI успеха** (их нет в ТЗ, ANSWERS и `01_analysis`);
- сущности / поля / статусы, которых нет в `data-model` / openapi;
- экраны и user-flow вне D-промптов;
- SEO/маркетинг «по привычке» без GTM-цели;
- правила деплоя / окружений вне `tooling/`;
- визуальный стиль «от себя», когда передан дизайн.

Полнота **не** оправдывает толстые D: покрытие IN SCOPE достигается **цепочкой** тонких срезов, а не склейкой в один промпт.

## Запрет ярлыков неполноты

Скоуп описывается **полной комплектацией**, а не «степенью готовности». Слова-ярлыки, которые
уменьшают объём молча, запрещены в любом артефакте: `TECH_SPEC`, `01_analysis`, specs, D-промпты,
coverage-matrix, roadmap, комментарии в коде, отчёты.

| Запрещено | Почему | Как писать правильно |
|---|---|---|
| «MVP», «PoC», «proof of concept», «beta», «v0.1» как **объём поставки** | Ярлык режет целевую комплектацию: «потом доделаем» не наступает, а ревью видит «так задумано» | Перечислить, что входит в поставку, и что явно OUT OF SCOPE с причиной |
| «пока без авторизации», «без тестов на первом этапе», «сначала без X» | Отсутствие части выдаётся за план | Либо требование целиком в IN SCOPE, либо OUT OF SCOPE с причиной и записью в `improvement-backlog` |
| «упрощённая версия», «заглушка», «временное решение» без ADR | Скрывает незакрытое требование под видом реализации | ADR с причиной + запись в `improvement-backlog`; в specs — полный контракт |
| «v1 как статус» (готовность) | Смешивает объём и зрелость | `v1` = **объём** (весь IN SCOPE); порядок работ — `S0…S8` и волны |

### Что значит `v1` в этом каноне

- **`v1` — объём поставки**, а не поколение продукта: всё, что в IN SCOPE, делается в `v1` целиком.
- **`S0…S8` и волны (`A`…`C`)** — порядок работ. Порция поставки меньше объёма не делает: первая
  волна не «ранняя версия», а первый шаг к той же полной комплектации.
- **`LATER` / `v2+`** — не «остаток v1», а явно исключённое: только `improvement-backlog.md`,
  без D-промптов «на будущее».
- Сокращения ради срока допустимы **только** как OUT OF SCOPE с причиной, зафиксированной в ТЗ, —
  не как формулировка «MVP» внутри IN SCOPE.

### Где проверяется

- шаг 01 — анализ не описывает объём через ярлыки;
- шаг 02 — пункт попадает в конституцию проекта (`AGENTS.md`, `.cursorrules`);
- шаг 09 — D-промпты: `sp-verify --gate d-prompt-quality` валит промпт с ярлыком неполноты.
  Гейт ловит ярлык **в форме объёма**: «beta-версия», «v0.2-этап» — да; «beta-флаг фичи» из ТЗ — нет
  (это требование, а не срез). Строка, которая сама запрещает ярлык (`MVP запрещён`, `OUT OF SCOPE`,
  ссылка на `improvement-backlog`), нарушением не считается — иначе правило нельзя процитировать.
- шаг 10 — аудит полноты: `partial`/`missing` не маскируются словом «MVP».

## Матрица покрытия (обязательный артефакт шага 09)

Файл: `OUTPUT/roadmaps/coverage-matrix.md`

| Источник | Должен попасть в |
|----------|------------------|
| Бизнес-цели / KPI из ТЗ §0 / analysis | `01_analysis` + трассировка в coverage-matrix / P0 |
| Каждый пункт **IN SCOPE** ТЗ §2 | ≥1 строка D в `progress.md` / coverage-matrix (со ссылкой на KPI) |
| Каждый сценарий P0/P1 ТЗ §4 | ≥1 D + кейсы в `tests/test-plan-Dxx` |
| Каждый критерий приёмки ТЗ §12 | явная привязка к D и/или test-plan **и** KPI |
| SEO / маркетинг / контент | только если GTM/KPI требуют; иначе OUT / later |
| Mobile / платежи / … если в IN SCOPE | отдельные D или явный `blocked` + **запланированные** D после ADR (не молчание) |
| OUT OF SCOPE | **не** создавать D «на будущее» |
| LATER / v2+ | только `improvement-backlog.md` |

Статусы строки матрицы: `covered` | `partial` | `blocked_adr` | `missing`  

Шаг 10: любой `missing` по P0 → **MAJOR** (лучше BLOCKER, если ломает acceptance).  
`partial` по P0 → MAJOR с конкретным дописанием D.

## SIZE_BUDGET (жёсткий лимит размера D)

Каждый D-промпт обязан содержать блок `## SIZE_BUDGET` (см. `TEMPLATES/dev-prompt.md`).  
D **OVER_BUDGET**, если сработало **любое** из условий — тогда сплит **обязателен** до записи тела (или до READY на шаге 10).

| Критерий | Лимит (OK) | Счётчик |
|----------|------------|---------|
| Пути в PRODUCES: код / конфиг / миграции | ≤ **6** | Тесты **не** входят в лимит, но для runtime **обязательны** в PRODUCES |
| Первичные поверхности | ≤ **2** из `{db, api, ui, worker, tooling}` | Только то, что реально меняется в PRODUCES |
| Доменные агрегаты в ЦЕЛЬ | ≤ **1** | Одна сущность/агрегат как фокус |
| API vs UI | ≤ **3** операций API **или** **1** маршрут UI (+ состояния) | Не смешивать «много API + полный экран» без сплита |
| PRIMARY LIBRARY в CONSUMES | ≤ **1** include/adapt | Остальные LIBRARY — только read-only ссылки без PRODUCES модуля |
| ЦЕЛЬ | одна проверяемая фраза | **Без** союза «и» между независимыми deliverable |

`size_ok: yes` только если все строки таблицы соблюдены.

### Обязательный сплит (даже если «почти» в лимите)

- две большие подсистемы в одном D (catalog API **и** SEO SSR; auth **и** payments; …);
- gap-модуль (`07_gap_*`) + чужой домен в одном D;
- platform bootstrap (D01) смешивает lint/CI **и** доменную фичу;
- **`api` + `ui` в одном D** — по умолчанию **резать** на соседние номера или `a`/`b` (выше шанс срезать UI или тесты). Исключение только thin-slice: 1–2 read-only API уже done + один экран, PRODUCES ≤6, явно в SIZE_BUDGET.

### Разрешённый тонкий вертикальный срез (не резать без нужды)

- 1 сущность → migration + 1–2 endpoint + тесты, если PRODUCES (без тестов) ≤ 6 и поверхности ≤ 2 (`db`+`api`);
- UI-D только на уже готовый API (CONSUMES контракт / PRODUCES предыдущего D).

### Алгоритм сплита

1. Кандидат OVER_BUDGET → разрежь в порядке приоритета:
   - по поверхности: db/api → ui (соседние номера или `a`/`b`);
   - по агрегату / user-journey;
   - по LIBRARY: один PRIMARY-модуль на D.
2. Именование: предпочтительно соседние номера `D03` / `D04` с общим `SPLIT_GROUP`; суффиксы `a`/`b` — только для явной пары одного эпика.
3. Связность: `ЗАВИСИТ ОТ` + PRE-CHECK следующего D проверяет PRODUCES предыдущего.
4. Полнота: каждый осколок остаётся в coverage-matrix; сумма срезов покрывает исходный IN SCOPE пункт.

### Lean body (экономия токенов при выполнении D)

- **Не** копировать в D целые specs / ТЗ / LIBRARY SPEC.
- CONSUMES: путь + якорь/операции (`OUTPUT/specs/openapi.yaml` — операции `POST /x`, `GET /y`).
- Доменные правила в ОГРАНИЧЕНИЯХ — только нужные этому PRODUCES, **≤ 12 буллетов**.
- HOW / INVARIANTS / ACCEPTANCE — обязательны, но **сфокусированы** на этом PRODUCES (не простыня ТЗ).
- Запрещено: «сделай остальное по ТЗ», «см. весь openapi», «зафиксировать позже», «если API есть», «на усмотрение» без выбранной схемы (**decision lock** → шаг 09 / specs / `blocked_adr`).

## Правила нарезки D-промптов

1. **Один D = один вертикальный результат**, проверяемый PRE-CHECK следующего D, и **внутри SIZE_BUDGET**.
2. Перед телами D — артефакт **D-cut list** (`OUTPUT/roadmaps/d-cut-list.md`): кандидаты с `surfaces`, `entity`, `est_produces`, вердикт budget.
3. В каждом D обязательно:
   - блок `## SIZE_BUDGET` (`size_ok: yes`);
   - user-visible / API-visible результат в **ЦЕЛЬ**;
   - CONSUMES с реальными путями (+ якоря);
   - PRODUCES полный список файлов/модулей;
   - правила домена, которые иначе пропадут (статусы, ошибки 4xx, идемпотентность) — в капе lean body;
   - ссылка на test-plan;
   - обновление `progress.md`.
4. Запрещено оставлять «сделай остальное по ТЗ» — только конкретные PRODUCES.
5. Gaps (`07_gap_*.md`) должны иметь **свой D** (или явная секция в D), не только абзац в backlog.

## Полнота «требований внутри промпта»

В D для UI/API, где применимо, включи короткие блоки (если данных нет в specs — **STOP** и допиши specs на шаге 04/10, не выдумывай в D):

- **Контракт:** эндпоинты / события из openapi/events (список id операций, не весь файл)
- **Данные:** таблицы/поля из data-model (только затронутые)
- **Права:** роли из authn-authz
- **UI:** маршруты + состояния (loading/empty/error)
- **Дизайн:** если есть `OUTPUT/docs/design-notes.md` — CONSUMES обязателен для UI-D
- **Нефункционал:** релевантные NFR (latency, idempotency)

## Mobile / отложенный стек

Если mobile в IN SCOPE, а ADR стека pending:

- в `progress.md` и coverage-matrix: `blocked_adr`;
- в roadmap — **именованные будущие D** (например D12–D14) с ЦЕЛЬ/CONSUMES-заготовкой «после ADR-000X»;
- вердикт READY допустим для старта web/API, но coverage P0 mobile ≠ `covered` до появления стека + полноценных D.

## Шаг 10 — Definition of Done фабрики

- coverage-matrix: нет `missing` для P0 IN SCOPE (кроме явного `blocked_adr` с перечисленными D-заготовками);
- каждый acceptance §12 трассируется;
- CI/CD + окружения документированы (см. `catalogs/cicd-environments.md`);
- дизайн: обработан или явно `design: none`;
- типизация + автотесты вшиты в AGENTS/`.cursorrules`/D-шаблон (`catalogs/typing-and-tests.md`);
- **SIZE_BUDGET:** нет OVER_BUDGET D (PRODUCES code/config > 6, >2 surfaces без thin-slice, нет блока SIZE_BUDGET → MAJOR, дорезать до READY).
