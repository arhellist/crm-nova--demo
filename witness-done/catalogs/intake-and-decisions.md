# Вход в проект и журнал решений

> Канон Witness Done (правило действует с v1.14). Связан с `TEMPLATES/entry-protocol.md`,
> `TEMPLATES/intake.md`, `TEMPLATES/decision-log.md`, `catalogs/agent-rules.md`.
> Цель: ни один запрос и ни одно принятое решение не проходят мимо Witness Done.

## Зачем

`MANIFEST` отвечает «где мы стоим в прогоне», `progress.md` — «что сделано в коде», `ADR` —
«почему выбрана архитектура». Не отвечено на два вопроса, которые задают в каждом чате:

1. **Откуда взялась эта работа?** Запрос был устным, чат закрыт, через месяц правка в коде
   выглядит самовольной.
2. **Почему решили именно так?** «Давай через Redis» прозвучало в чате и исчезло.

Вход (`intake`) закрывает первый вопрос, журнал решений (`decisions.md`) — второй. Оба —
обычный Markdown: читаются и пишутся руками, CLI только создаёт заготовку и проверяет.

## Два артефакта

| Артефакт | Что внутри | Когда создаётся |
|----------|------------|-----------------|
| `journal/intake/<YYYYMMDD-HHMM>-<slug>.md` | запрос дословно, снимок состояния, классификация, `next:`, `связано:` | на каждый запрос, кроме мелочи L0 |
| `journal/decisions/DEC-###-<slug>.md` | одна запись: контекст, решение, альтернативы, чем подтверждено, статус | на каждый выбор, догадку, компромисс |
| `journal/decisions.md` | оглавление, собирается из `decisions/` командой `sp journal --index` | при каждом решении |

**Журнал коммитится.** `journal/` лежит в корне проекта, рядом с кодом, и попадает в git:
решение, оставшееся только на машине автора, для проекта не существует. Индекс `decisions.md` —
производный вид: конфликт в нём лечится `sp journal --index`, а не разрешением маркеров.

Одна запись — один файл. Две ветки, добавившие решения, не конфликтуют: у каждой свой файл.
`DEC-###` не переиспользуется — номер выдаётся с учётом `origin/main`, дубли ловит
`sp journal --check`.

Записи append-only. Изменившееся решение оформляется новым `DEC-###` со ссылкой `заменяет: DEC-00N`.

## Виды входа

| `kind` | Когда | Что обязано появиться до кода |
|--------|-------|-------------------------------|
| `new` | проект не начат (`last_completed_step: —` или нет `MANIFEST`) | маршрут `PIPELINE/00_bootstrap.md` |
| `change` | меняется поведение действующего продукта | `spec-state/changes/<id>/` (R02) с полем `intake:` |
| `task` | greenfield, есть готовый D-промпт | ссылка на `Dxx` |
| `question` | нужно решение или объяснение, код не меняется | `DEC-###`; закрывается `sp close --ref DEC-###` |
| `bugfix` | дефект в уже принятом поведении | пакет изменения с причиной в `proposal.md` §1 |

**Порядок проверок.** Вопрос распознаётся раньше активного изменения (DEC-031): запрос
«почему это медленно?» при открытом `spec-state/changes/<id>` остаётся `question` и закрывается
решением `DEC-###`, а не новым change-пакетом. Активное изменение притягивает только запросы,
которые меняют поведение; вопрос с глаголом изменения — по-прежнему `exit 3` (нужен человек).

**`bugfix` распознаётся машинно** (DEC-040): признак дефекта («ошибка», «баг», «падает»,
«не работает», `bug`, `crash`, `broken`, …) при уже принятом поведении — есть baseline
(brownfield) или хотя бы одно `done` в `progress.md`. Проверка идёт раньше активного изменения:
причина дефекта должна попасть в `proposal.md` §1, а не раствориться в чужой дельте. Заказ
новой работы дефектом не считается — глагол «добавь/создай/реализуй» перевешивает: «добавь
обработку ошибок» — это `change`/`task`, а «исправь ошибку» — `bugfix`. Если принятого
поведения ещё нет, дефект — это просто не написанная работа, и вид остаётся `task`/`change`;
сомнительный случай всегда можно назвать явно: `sp intake "…" --kind bugfix`.

### Порог: когда intake не нужен

- правка опечатки/форматирования в документации — одна строка в `decisions.md` не требуется;
- ответ на вопрос, ответ на который уже есть в артефактах, — достаточно ссылки, но `intake`
  всё равно пишется, если человек задал вопрос в чате: иначе непонятно, что вопрос был;
- L0-задание (docs/config) в greenfield — `intake` не обязателен, если задание уже существует
  как `Dxx` в `OUTPUT/prompts/`.

Во всех остальных случаях intake обязателен. Порог проверяет `sp doctor`, а не память.

## Правило «решение до кода»

Порядок жёсткий:

```text
intake → next → (вопрос? decide) → код → evidence → close
```

Если по ходу работы возник выбор, которого нет в спецификации — «какой TTL», «какой формат
ошибки», «оставить ли старое поле» — он фиксируется `sp decide` **до** правки. Догадка,
записанная после реализации, — это не решение, а оправдание.

Если выбора нет в спецификации и человек недоступен, `decide` пишет вариант с пометкой
`статус: принято по умолчанию` и причиной. Допущение видно, а не замазано.

## Формат `DEC-###`

```markdown
### DEC-004 — Сессии в Redis, пользователи в PostgreSQL

| Поле | Значение |
|------|----------|
| Дата | 2026-10-28 |
| Intake | 20261028-1512-redis-sessions |
| Статус | принято |
| ADR | ADR-0007 (если решение архитектурное) |
| Заменяет | — |

**Контекст.** Токены живут 15 минут, но нужен refresh на 7 дней; горизонтальное масштабирование
требует общего хранилища.

**Решение.** Сессии — Redis с TTL 7 дней; источник истины по пользователям — PostgreSQL.

**Альтернативы.** Таблица в PostgreSQL (лишняя нагрузка на OLTP), cookie-only (нельзя отозвать).

**Чем подтверждено.** `A05.3`, тест `test/refresh-rotation.test.ts`; `docs/03_architecture.md` §4.
```

`DEC` без «чем подтверждено» не закрывает intake: решение, которое ничем не проверяется,
неотличимо от мнения.

## Связь с change-пакетом

`spec-state/changes/<id>/proposal.md` содержит поле `| Intake | <ID> |`. Идентификатор изменения
берётся из intake, а не придумывается заново: тогда цепочка читается в обе стороны.

```text
journal/intake/20261028-1512-add-avatar.md
  → spec-state/changes/add-avatar/proposal.md (Intake: …)
    → OUTPUT/evidence/CHANGE-add-avatar.json
      → spec-state/archive/2026-11-02-add-avatar/
```

## Портативность

Без CLI всё делается руками:

1. создать `journal/intake/<YYYYMMDD-HHMM>-<slug>.md` по `TEMPLATES/intake.md`;
2. заполнить `kind`, `next:` и `связано:`;
3. решение положить файлом `journal/decisions/DEC-###-<slug>.md` по `TEMPLATES/decision-record.md`
   и пересобрать оглавление: `sp journal --index` (руками — та же таблица).

Проверки `sp doctor` при этом остаются: они смотрят на файлы, а не на историю вызовов CLI.

## Предел

`doctor` видит файлы, но не чат. Если агент вообще не вызвал `sp intake`, записи не появится —
и `doctor` этого не заметит. Поэтому протокол входа стоит в корневых правилах (`AGENTS.md`)
с шага 00, а команда `/sp` дёргает `intake` явно. Дисциплину держит не CLI, а правило,
подкреплённое гейтом на изменённых файлах: правка без intake и без D попадает в отчёт `doctor`.
