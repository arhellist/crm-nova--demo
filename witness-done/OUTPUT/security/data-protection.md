# Защита данных — NOVA CRM

> Сгенерировано Witness Done v1.31.0. Источник: ТЗ §7, §8, §13.2.

## 1. Категории данных

| Категория | Данные | Где | Кому видно |
|-----------|--------|-----|------------|
| ПДн сотрудников | имя (`profiles.full_name`), email (`auth.users.email`) | primary, частично реплика | имя — всем авторизованным; email — только администратору вне приложения |
| Коммерческие данные | объекты, задачи, описания, комментарии переходов | primary, реплика | по RLS: постановщик — всё, исполнитель — свои задачи |
| Аудит | история статусов с актором и временем | primary, реплика | по видимости задачи |
| Секреты | ключи, пароли, токены | менеджер секретов | сервисы-потребители |
| Технические | метрики, логи, request_id | Grafana, Sentry | команда |

`auth.users` (email, хеши паролей, MFA-секреты) **не публикуется** в репликацию: публикация
включает только четыре таблицы `public`.

## 2. Шифрование и транспорт

- In transit: TLS 1.2+ везде (Vercel, Supabase, Cloudflare, приватная сеть Docker между API и
  репликой — отдельный TLS или изолированная bridge-сеть без публикации портов).
- At rest: шифрование дисков Supabase и managed PostgreSQL; бэкапы и PITR шифруются провайдером.
- Хеширование паролей и TOTP-секретов — Supabase Auth (bcrypt/Argon2-совместимая реализация);
  собственный код криптографии отсутствует.
- Секреты в контейнерах — env из менеджера секретов; в образ не встраиваются.

## 3. Минимизация

- Отчётные вьюхи не содержат email, `description`, `comment`; только агрегаты и `full_name`.
- Ответы API не содержат внутренних идентификаторов сессий и SQL-деталей.
- Логи не содержат тел запросов и значений полей; только метод, путь, статус, длительность,
  `request_id`, `user_id` (UUID, не email).
- Аналитика отсутствует; сторонних трекеров нет.

## 4. Логи и ошибки

- pino: `redact` для `authorization`, `cookie`, `apikey`, `password`, `access_token`,
  `refresh_token`, `set-cookie`.
- Sentry: `sendDefaultPii: false`, `beforeSend` вырезает заголовки и query; в событиях только
  `request_id` и код ошибки.
- Клиентские сообщения об ошибках — только коды `P040x`/`E_*` и человеческий текст; stack trace
  и SQL не показываются.
- Ошибки БД логируются на сервере с `request_id`, но без параметров запроса.

## 5. Retention и удаление

| Данные | Срок | Механизм |
|--------|------|----------|
| Задачи и объекты | бессрочно (архив), удаление недоступно | `deleted_at`, `restrict` |
| История статусов | бессрочно | append-only |
| Логи приложения | 30 дней | ротация на стороне провайдера |
| Метрики | 90 дней | retention Grafana Cloud |
| Sentry-события | 30 дней | настройки проекта |
| Бэкапы | 30 дней + PITR 7 дней | Supabase |
| Учётные записи после увольнения | блокировка сразу, удаление по регламенту компании | Supabase Auth + журнал |

Право на удаление ПДн реализуется администратором: удаление пользователя в Auth каскадно удаляет
`profiles`, но задачи сохраняются (ссылки `restrict` на `profiles` требуют предварительной
переназначенности или анонимизации — регламент фиксирует порядок).

## 6. Правовой контекст

- Данные размещаются в ЕС (Supabase region eu-central, Vercel EU).
- До правовой оценки 152-ФЗ система не используется для ПДн третьих лиц; это ограничение
  эксплуатации, а не «недоделанная функция».
- Согласие сотрудников на обработку имени и email — зона ответственности компании-заказчика.

## 7. Проверки перед релизом

- [ ] Публикация репликации не включает `auth.users`.
- [ ] Отчётные вьюхи не содержат email/текстов задач (тест на ключи JSON).
- [ ] redact-конфиг покрывает все секретные поля; тест на строку лога.
- [ ] Sentry не отправляет PII (проверка тестовым событием).
- [ ] Retention настроен у провайдеров, значения совпадают с таблицей §5.
- [ ] Бэкап и PITR включены, учения восстановления проведены и записаны.
