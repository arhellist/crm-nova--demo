# Чек-лист стыковки FE ↔ API ↔ БД

> Сгенерировано Witness Done v1.31.0. Каждый пункт — обязательство, проверяемое на шаге 09
> (test-plan) и на приёмке. Если пункт нарушен, задание не принимается.

## 1. Контракты данных

- [ ] Названия колонок в `specs/data-model.md` совпадают с типами, сгенерированными
      `supabase gen types typescript` (snake_case в БД, camelCase только на границе FE).
- [ ] Enum-значения статусов и ролей не дублируются строковыми литералами в коде: используется
      единый словарь (`shared/lib/status.ts`), значения — из сгенерированных типов.
- [ ] Каждый ответ PostgREST/RPC валидируется Zod-схемой до попадания в состояние компонента.
- [ ] Даты приходят ISO-строками (`timestamptz`), отображаются через единый форматтер
      `dd.MM.yyyy HH:mm` (Europe/Moscow).

## 2. Права и ошибки

- [ ] Для каждой пары «роль × действие» из `OUTPUT/security/authn-authz.md` есть кейс «разрешено»
      и кейс «отказано».
- [ ] UI не является защитой: скрытая кнопка не считается мерой; запрос всё равно проверяется БД.
- [ ] `P0400/P0403/P0422` маппятся в один и тот же текст в любом экране (`shared/api/mapDbError`).
- [ ] Чужой ресурс отдаёт «нет доступа/не найдено» одинаково — без раскрытия существования.
- [ ] Любой write-запрос к Fastify возвращает `405`, это покрыто integration-тестом.

## 3. Списочные экраны

- [ ] Каждый список имеет явную пагинацию (`limit` ≤ 100, курсор по `(created_at, id)`).
- [ ] Сортировка задана явно (`order=created_at.desc`), а не «как вернёт БД».
- [ ] Реализованы четыре состояния: загрузка (скелетон), пусто (текст + CTA), ошибка (сообщение +
      «Повторить»), нет доступа (404).
- [ ] Счётчики статусов в списке объектов совпадают с данными карточки объекта.

## 4. Мутации

- [ ] После успешной мутации инвалидируются все затронутые запросы: задача, история, список задач
      объекта, «Мои задачи», счётчики объектов.
- [ ] Кнопка блокируется на время отправки; повторный submit невозможен.
- [ ] Возврат на доработку требует непустого комментария и в UI, и в БД (проверка в RPC и CHECK).
- [ ] Смена исполнителя доступна только в `new`/`rework`; в остальных статусах действия нет и
      запрос отклоняется `P0422`.

## 5. Реплика и отчёты

- [ ] Отчётный экран читает только Fastify, а не Supabase напрямую.
- [ ] Каждый ответ содержит `source: replica` и `lag_seconds`; UI отображает актуальность.
- [ ] При `503` раздел отчётов показывает деградацию и не блокирует остальные экраны.
- [ ] В ответах отчётов нет `email`, `description`, `comment` — проверяется тестом на ключи JSON.
- [ ] Остановка реплики не влияет на вход, создание задач и смену статусов.

## 6. Безопасность и окружение

- [ ] В бандле только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`; `service_role` отсутствует.
- [ ] В контейнере `api` нет строки подключения к primary и нет `SUPABASE_DB_PASSWORD`.
- [ ] CSP и security-заголовки из `specs/` отдаются production-сборкой; проверка — автотестом.
- [ ] Ошибки наружу не содержат SQL, имён таблиц и полных stack trace.
- [ ] Логи не содержат токенов, паролей и PII; redact-список покрывает `authorization`, `cookie`,
      `access_token`, `refresh_token`, `password`.

## 7. Совместимость и миграции

- [ ] Приложение не читает колонку, которой нет в применённых миграциях (порядок: миграции → код).
- [ ] Изменения схемы только добавляющие; удаление колонки — отдельный релиз после отказа кода.
- [ ] Отчётные вьюхи создаются только на вторичной БД и не ломают primary-миграции.
- [ ] Повторный прогон миграций идемпотентен (`create or replace`, `if not exists`).

## 8. Доменные правила

Domain rules зафиксированы в `specs/domain-rules.md`: машина состояний (6 разрешённых пар),
обязательный комментарий при `rework`, только архивирование вместо удаления, лимиты полей,
порог деградации реплики 30 с, кэш отчётов 30 с, rate limit 60/мин. Отдельного файла дубля нет.
