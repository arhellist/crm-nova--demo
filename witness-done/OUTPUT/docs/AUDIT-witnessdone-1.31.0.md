## Короткий ответ

1. **Волны 00–09 канон держит.** Задания, паки, покрытие, журнал и правила прошли формальные
   проверки; содержательных провалов в проектных артефактах нет.
2. **Шаг 10b в greenfield неразрешим по правилам самого канона.** Он запрещает писать код, но
   требует зелёных `acceptance`, `product-smoke` и `runtime` — гейтов, которые без кода не могут
   быть зелёными. Значит, `SELF_AUDIT: PASS` не достигается, а переход в Brownfield (`R01`) не
   открывается никогда. Это не дефект прогона, а замкнутый контур канона.
3. **Семь гейтов зелёные без доказательства**: `self-audit`, `runtime-plan`, `progress --check`,
   `exit-criteria`, `coverage-matrix`, `CONTEXT_PACK validation_ok` и
   `product-smoke --skip-commands`. В сумме «зелёный 10b» может означать «ничего не проверено».
4. **Четыре инструментальных дефекта** делают проверку канона невоспроизводимой: selftest
   `validate.sh` негерметичен, `doctor --strict` считает файлы канона «кодом вне PRODUCES»,

## 2. Блокеры: 10b нельзя пройти по правилам канона

### C-01. `acceptance` требует тестов, которых на 10b не существует

- `PIPELINE/10b_self_audit.md:8` — «Код продукта не писать».
- `10b:117` — чек-лист требует `--gate acceptance` → `tax_pass: true`.
- `acceptance-bind.mjs:289-317` берёт **существующие файлы** из `PRODUCES` задания; тесты
  появляются только при выполнении D01–D14, то есть **после** 10b.
- Факт: 14/14 заданий падают, `src/` и тестовых файлов нет.
- `ORCHESTRATOR.md:72` повторяет ошибку для C3: «после пачки — `--gate acceptance`», когда
  тест-планы только созданы, а тестов ещё нет.

**Следствие:** гейт не может стать зелёным, пока не написан код. Написать код внутри 10b
запрещено. Это логический тупик, а не «недостаток доказательств».

### C-02. `product-smoke` не умеет «n/a»

- `10b:104` разрешает «явное `n/a`, если контура ещё нет», но у гейта **нет** флага `n/a`.
- Честный скрипт возвращает 2 → `tax_pass: false`.
- `--skip-commands` даёт `tax_pass: true` при `commands: []` — то есть «зелёный» без единого
  исполнения. Проверено: акт `RELEASE-product-smoke.json` с `commands_skipped: true`.
- При этом `pre_release` **отвергает** такой акт (`sp-verify.mjs:1835-1838`). Один и тот же
  артефакт одновременно «проходит 10b» и «недействителен для релиза».

### C-03. `runtime` требует поднятого контура до появления кода

- `10b:106` требует `--gate runtime` → `tax_pass: true` и `RELEASE-runtime-verify.json`.
- `executePlan()` поднимает `up[]`, ждёт `ready`, гоняет `verify[]`; без реализации проверять
  нечего, а `up` (Supabase/Docker) на 10b ещё нечем наполнять.
- Чек-лист не отделяет «план» от «исполнения», хотя в каноне это разные акты.

### C-04. Ось «Базовая линия» замкнута сама на себя

- `10b:20` подаёт на вход `spec-state/baseline/`.
- `10b:61` требует, чтобы baseline покрывал домены.
- `spec-state/baseline/` создаётся **только** шагом `R01` (`PIPELINE/R01:шаг 1`).
- `R01` разрешён **только** после `SELF_AUDIT: PASS`, который требует этой же оси.
- При этом `verifySelfAudit()` **вообще не смотрит** в `spec-state/`; ось проверяется вручную.

**Итог по разделу:** greenfield-прогон не имеет легального выхода в Brownfield. Канон требует
доказательств, которые производит следующий этап, доступ к которому закрыт этими же требованиями.

## 3. Ложные зелёные и слабые гейты: «зелёный» ≠ «доказано»

### C-05. `self-audit` не проверяет ни промпты, ни приёмку

- `sp-verify.mjs:101` в справке: «self-audit: 10b audit — coverage, exit-criteria, **prompt
  quality**, evidence for done D».
- `verifySelfAudit()` (`sp-verify.mjs:1546-1628`) проверяет только: строки coverage-matrix,
  наличие строк `E<n>` с непустой последней ячейкой, строки progress и акты `done`.
- Промпты не читаются, `acceptance` не вызывается, `product-smoke` не вызывается.
- Факт: `self-audit` = 0 при `acceptance` = 2 (14/14 провалов). Два гейта противоречат друг другу,
  и «self-audit pass» в отчёте 10b ничего не говорит о качестве заданий.

### C-06. `runtime-plan` «покрывает» ноль принятых фраз

- `runtime-plan.mjs:36-57`: множество «принятых» фраз строится **только** из актов `Dxx.json`.
- На 10b ни одного `Dxx.json` нет → множество пусто.
- `runtime-plan.mjs:193-207`: полнота считается относительно этого пустого множества → на 10b
  `uncovered: []` **всегда**.
- Акт (`sp-verify.mjs:2414-2421`) не содержит `accepted_count`, поэтому вакуумность не видна.
- Факт: `planned: 29`, `na: 3`, `uncovered: 0`, `executed: false`, `tax_pass: true`.

### C-07. `exit-criteria` проверяет текст, а не доказательство

- `sp-verify.mjs:1580-1592`: строка `E<n>` проходит, если последняя ячейка непустая и не
  `—/todo/tbd`. Существование файла не проверяется.
- Наши `E1–E28` имеют статус `pending` и «ожидаемый артефакт» — гейт всё равно зелёный.
- Значит, «exit-criteria pass» означает «таблица заполнена», а не «критерии подтверждены».

### C-08. `CONTEXT_PACK validation_ok` — самодекларация

- `sp-verify.mjs:1389-1400`: проверяются только наличие файла пака и слово `yes` в поле
  `validation_ok`. Файл `*.validation.json` не открывается, якоря не сверяются.
- Наши паки имеют валидационные файлы, но гейт этого не знает; «паки валидны» — утверждение
  автора, а не машины.

### C-09. `coverage-matrix` — регулярка на наличие `Dxx`

- `sp-verify.mjs:1560-1570`: каждая строка должна содержать `D\d+`. Что именно этот D покрывает
  требование, не проверяется.
- Матрица со ссылкой на любой D проходит, даже если его `ACCEPTANCE` не содержит фраз требования.

### C-10. `progress --check` зелёный при отсутствии фрагментов

- `sp progress --check` → 0 и «фрагментов нет — сверять нечего».
- Чек-лист 10b требует «exit 0» как доказательство согласованности. Ноль строк — тоже ноль.

### C-11. `d-prompt-quality` не проверяет Given/When/Then

- `10b:51-52` обещает «у фразы есть текст Given/When/Then».
- `parseAcceptancePhrases()` извлекает `given/when/then`, но `verifyDPromptQuality()` проверяет
  только `phraseMissing` (`sp-verify.mjs:1367-1370`).
- Двухколоночная таблица `| ID | фраза |` проходит: три поля не обязательны.

### C-12. `product-smoke --skip-commands` — зелёный акт без прогона

- Доказано: `commands: []`, `commands_skipped: true`, `tax_pass: true`.
- Гейт не различает «проверено» и «не проверялось»; различие появляется только в `pre_release`,
  то есть на шаг позже, чем нужно аудиту.

## 4. Инструментальные дефекты канона

### C-13. Selftest `validate.sh` негерметичен, а проверка артефакта в `OUTPUT` — мёртвый код

Воспроизведено на двух одинаковых копиях канона. Сценарий selftest: `OUTPUT/.gitkeep` →

не из-за артефакта, а из-за незаполненного ТЗ, которое даёт вторую ошибку. На реальном проекте
он падает, и `validate.sh` нельзя использовать после шага 00.

**Это ошибка теста и ошибка ветвления одновременно:** негативный кейс не изолировал причину,
поэтому проверял не то, что заявлено.

## 5. Что канон сделал правильно

- **Пломбы актов** (`evidence_hash`, `code_hash`, `script_sha256`) — акт нельзя подменить текстом.
- **`acceptance-bind`** — связь «фраза ↔ тест» через `@acceptance` и digest фразы, а не «тест
  зелёный, значит всё хорошо».
- **`pre_release`** ловит `commands_skipped`, устаревший скрипт и акт без `code_hash`.
- **`d-prompt-quality`** реально режет размер, префиксы, число фраз, плейсхолдеры, ярлыки
  неполноты.
- **Журнал и intake** — запрос, решение и закрытие связаны; `journal --check` ловит дубли.
- **`sp rules --sync`** — 13 адаптеров из одного источника, без рассинхрона.
- **Разделение `runtime-plan` / `runtime`** (DEC-035) — правильная идея; проблема только в том,
  что 10b принимает план за доказательство.
