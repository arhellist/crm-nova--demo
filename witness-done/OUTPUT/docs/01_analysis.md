# Анализ ТЗ — NOVA CRM

> Сгенерировано Witness Done v1.31.0

## Краткое резюме продукта

NOVA CRM — закрытая веб-система строительной компании: руководитель ставит задачи по объектам,
прорабы и инженеры ведут их по жёсткому циклу из пяти статусов до приёмки, а каждый переход
фиксируется в неизменяемой истории. Ключевое свойство — права, переходы и история обеспечиваются
PostgreSQL (RLS, триггеры, `security definer` RPC), а не интерфейсом. Второй контур — собственный
backend, который умеет только читать агрегаты с логической реплики БД и не имеет пути записи.

## Бизнес-цели и успех

- **Цель бизнеса (12–24 мес):** заменить Excel и мессенджеры в оперативном учёте задач по
  стройобъектам; сделать статус задачи и его автора единственным источником правды.
- **Плательщик vs пользователь:** платит строительная компания (внутренний инструмент), пользуются
  руководитель (постановщик) и прорабы/инженеры (исполнители). Покупатель и основной пользователь
  совпадают — руководитель.
- **Ценность для пользователя:** руководитель видит статус каждой задачи по объекту и знает, кто и
  когда его менял; исполнитель видит только свои задачи и не тонет в чужих.
- **KPI:** доступность 99.9%; p95 чтения ≤ 400 мс, мутации ≤ 600 мс; 100% запрещённых переходов
  отклоняются БД; 0 обходов RLS; 0 возможностей подделать историю; 0 `service_role` в бандле и
  образах; лаг репликации p95 ≤ 5 с; RPO ≤ 5 мин / RTO ≤ 60 мин; откат релиза ≤ 15 мин;
  security-гейты CI зелёные; time-to-first-value ≤ 30 с; развёртывание контура ≤ 15 мин.
- **Монетизация:** отсутствует — внутренний инструмент. Тарифов, биллинга, платёжных интеграций нет.
- **GTM / SEO / маркетинг:** классического GTM нет; внедрение — прямая демонстрация и обучение.
  Система закрытая, лендинг и SEO не нужны → SPA без SSR. Это следствие цели, а не «пропущенный пункт».
- **Конкуренты и отличие:** Excel + мессенджеры (нет модели статусов, прав и аудита);
  Bitrix24/YouGile/Asana (избыточны, права живут в UI); самописные CRM (нет воспроизводимых миграций,
  декларативных RLS и read-реплики для отчётности).
- **Анти-цели:** не ERP, не сметное и документное ПО, не универсальный трекер, не мессенджер,
  не файлохранилище, не realtime-доска, не BI-платформа, не мультитенантный SaaS, не второй путь записи.

### Трассировка «цель/KPI → что закрывает»

| KPI / цель | Закрывается |
|------------|-------------|
| 1. Доступность 99.9% | мониторинг, алерты, healthcheck'и, staging, runbooks (срезы «эксплуатация», «наблюдаемость») |
| 2. Латентность p95 | индексы `tasks(assignee_id, status)`, TanStack Query, агрегаты на реплике |
| 3. Матрица переходов 100% | `rpc.change_task_status` + триггеры `guard_task_status`/`log_task_status` |
| 4. 0 обходов RLS | RLS на 4 таблицах, колоночные гранты, `security definer` с фиксированным `search_path` |
| 5. Неизменяемая история | append-only таблица, отсутствие грантов на INSERT/UPDATE/DELETE, триггерная запись |
| 6. 0 `service_role` вне seed | разделение ключей, grep-гейт в CI, read-only роль `nova_ro` |
| 7. Лаг репликации p95 ≤ 5 с | публикация/подписка `pgoutput`, `/health/replication`, алерт по лагу |
| 8. RPO/RTO | ежедневные бэкапы + PITR, учения восстановления, runbook |
| 9. Откат релиза ≤ 15 мин | атомарный деплой Vercel, теги Docker-образа, forward-only миграции |
| 10. Security-гейты | CI: `npm audit`, `gitleaks`, CSP-проверка, grep на секреты, ASVS-чеклист |
| 11. Time-to-first-value | экран «Мои задачи» + одна кнопка перехода; отчёт не мешает основному пути |
| 12. Развёртывание ≤ 15 мин | README, `docker compose up`, `supabase db reset`, seed |

## Акторы и цели

| Актор | Цель | Права |
|-------|------|-------|
| Постановщик (`manager`) | видеть статус работ по объектам и принимать результат | читает всё, создаёт/правит объекты и задачи, принимает и возвращает на доработку, архивирует, смотрит отчёты |
| Исполнитель (`executor`) | видеть только свои задачи и двигать их по циклу | читает свои задачи и объекты с ними, меняет статус своих задач, историю своей задачи |
| Администратор (вне UI) | выдавать доступы по регламенту | провижининг в Supabase, журнал операций; прав в приложении не имеет |
| Читатель отчётов (backend) | отдавать агрегаты | только `SELECT` от `nova_ro` на реплике, `API_TOKEN` на входе |

## IN / OUT / LATER

IN SCOPE (полная поставка, каждый пункт — к KPI): вход с MFA и сессией; две роли из БД; объекты
(список, создание, правка, архивирование, карточка); задачи (создание, правка, архивирование,
назначение, карточка); цикл из 5 статусов и 5 переходов с проверкой в БД; неизменяемая история;
экраны входа, объектов, объекта, задачи, «Мои задачи», отчётов, 404; RLS + RPC; seed-данные;
read-only backend и его health-эндпоинты; логическая репликация с контролем лага; безопасность
ASVS L2 (JWT, RBAC, CSRF, заголовки, CSP); эксплуатация (staging, мониторинг, бэкапы, runbooks,
журнал релизов); документация.

OUT OF SCOPE (продуктовые границы §2.2 ТЗ, с причиной): файлы и фотоотчёты, переписка, уведомления,
UI-управление пользователями, мобильное приложение, мультитенантность, универсальный поиск и BI.
LATER отсутствует как категория: исключённое не «отложено», а не входит в продукт.

## Сценарии (P0)

P0 — все 17 сценариев §4 ТЗ: провижининг, вход с MFA, создание объекта, создание задачи, взятие в
работу, отправка на проверку, приёмка, возврат на доработку, повторный старт, изоляция исполнителя,
запрещённый переход, архивирование, «Мои задачи», отчёты, отставание реплики, запрет записи в backend,
инцидент и восстановление. Дополнительно — те же сценарии как негативные кейсы для приёмки.
P1/P2 не выделяются: очередь работ задаётся срезами (`S0…S3` на шаге 09), а не «версиями продукта».

## Доменные сущности

`profiles` (роль, имя), `objects` (объект стройки, архивирование), `tasks` (задача по объекту,
исполнитель, автор, статус), `task_status_history` (append-only журнал переходов). Перечисления
`user_role`, `task_status`. Отчётные вьюхи на реплике: `report_objects`, `report_workload`,
`report_status_ages`. Подробности — шаг 04.

## Интеграции

Supabase Auth (email + пароль + TOTP); Supabase PostgREST/RPC — единственный путь записи;
логическая репликация Supabase → PostgreSQL 16 (`pgoutput`, `nova_pub`/`nova_sub`); Vercel (статика,
заголовки, откат); Docker Compose (реплика + API); Grafana Cloud/Prometheus, Sentry, uptime-монитор;
Cloudflare (TLS, WAF, rate limiting). Платёжных, почтовых, SMS, SSO и внешних продуктовых API нет.

## Неявные требования (гипотезы)

1. Руководитель принимает задачи не только свои — любой `manager` (зафиксировано в ТЗ §13.1 п. 2).
2. Исполнитель видит объект, если у него есть там хотя бы одна неархивированная задача, включая
   принятые (§13.1 п. 6).
3. Комментарий обязателен только для возврата на доработку (§13.1 п. 4).
4. Смена исполнителя возможна только в «Новая» и «На доработке» (§13.1 п. 3).
5. Отчётность — вторичные данные: любой ответ помечен `source: replica` и `lag_seconds`.

## Риски

- Размещение ПДн в ЕС: нужна правовая оценка 152-ФЗ до реальных данных.
- Один регион: 99.9% опирается на SLA Supabase и edge-провайдера; реплика не HA и не failover.
- Токен в `localStorage`: компенсируется строгим CSP и запретом сторонних скриптов.
- Слот репликации удерживает WAL при простое подписчика: нужен алерт по лагу и размеру WAL.
- Провижининг вне UI: ошибка администратора возможна; компенсируется регламентом и журналом.

## Gaps

1. Нет привязки требований ASVS L2 к исполняемым тестам — закрывается шагом 05 и test-plan'ами.
2. Нет DDL и контракта ответов отчётных вьюх — закрывается шагом 04.
3. Не зафиксировано место `spec-state/` и его попадание в репозиторий — шаг 03 (ADR).
4. Нет перечня `INV-###` проекта — шаги 02/05.
5. Нет регламента провижининга как артефакта — шаги 03 (ADR) и 05 (security).
6. Не зафиксированы точные значения retention бэкапов и период учений — шаг 06 (NFR, число + владелец).

Критичных бизнес-вопросов нет: цель, KPI, плательщик, пользователи, границы и стек описаны в ТЗ.
Статус `needs_human` не требуется.

## Дизайн-вход

`present` — `INPUT/design/Design.html`: тёмная тема, токены (`bg-0/1/2`, `panel`, `text`, `cyan`,
`violet`, `magenta`, `lime`, `amber`, `rose`), шрифты Inter и JetBrains Mono, радиусы 10/16/24,
сетка 8 px, стеклянные панели, статусные бейджи, таймлайн истории, карточки объектов, таблица
задач, колонки «Моих задач». В референсе нет: формы входа и MFA, модалок возврата и архивирования,
состояний загрузки/пустоты/ошибки, экрана отчётов, мобильной вёрстки — они проектируются по тем же
токенам и попадают в `docs/design-notes.md`.

## CI/CD (известное из ТЗ)

Задано: три окружения (local/staging/production), джобы `ci`, `backend`, `db-test`, `replication-test`,
`security`, `e2e`; релиз через merge в `main` с подтверждением, forward-only миграции, откат Vercel
и предыдущим Docker-тегом. Требуют решений шага 08: конкретные версии экшенов, раннер, способ
подъёма Supabase в CI, политика кэша, точный состав CSP-проверки.

## Профиль

`web-app` (auth, роли, интерфейс, админка) — основа. Отклонения: `admin-panel` снят (провижининг вне
UI по ТЗ §2.2); добавлен акцент `read-only backend` (Fastify + реплика, отчётность); `caching-redis`
не нужен; `rate-limiting` включён (периметр + API).

## Рекомендуемые модули LIBRARY (черновик, финал — шаг 07)

- `auth-jwt` — **adapt**: Supabase Auth вместо собственных JWT-эндпоинтов; контракт (JWT + роль из БД) сохраняется.
- `crud-table` — **adapt**: списки объектов и задач, состояния загрузки/пустоты/ошибки.
- `logging-pino` — **include**: pino в Fastify.
- `rate-limiting` — **include**: `@fastify/rate-limit` + лимиты Supabase Auth + WAF.
- `admin-panel`, `file-upload`, `websocket-socketio`, `search`, `email-nodemailer`, `payments-stripe` — **skip**: вне продукта (§2.2 ТЗ).
- `caching-redis` — **skip**: кэша нет, TanStack Query и 30-секундный кэш отчётов достаточны.
- Свой модуль `read-replica-reporting` (без LIBRARY-аналога).
