# Применение методологии архитектуры

> Сгенерировано Witness Done v1.31.0. Краткая выжимка `LIBRARY/methodology-architecture/SPEC.md`
> без копирования канона: что из методологии применяется, что нет и почему.

## Применяем (must)

| Принцип | Как применён |
|---------|--------------|
| Один вертикальный срез = один проверяемый результат | D-промпты режутся по срезам S0…S10, у каждого PRE-CHECK |
| Контракты до кода | `specs/data-model.md`, `specs/openapi.yaml`, `specs/domain-rules.md` созданы до D |
| Границы модулей и публичные контракты | `specs/modules.md`; FE-модули не читают чужие таблицы |
| Слои: UI → доступ к данным → домен в БД | UI не содержит бизнес-правил статусов; правила в RPC/триггерах |
| Ошибки как контракт | стабильные коды `P040x`, `E_*`, единый конверт |
| Миграции forward-only | expand/contract, идемпотентность, проверка в CI |
| Наблюдаемость с первого дня | pino + `/metrics` + health-эндпоинты в D каркаса |
| Доказательство вместо «готово» | evidence + `tax_pass`, `progress.d/<Dxx>.md` |

## Применяем с адаптацией (should)

| Принцип | Адаптация |
|---------|-----------|
| Пагинация cursor | keyset `(created_at, id)`, без `COUNT(*)`, `hasMore` = `limit + 1` |
| Repository/Service-слой | на фронтенде — hooks + api-клиент; на backend — модуль `db`, без «сервисного» оверинжиниринга |
| Аудит через отдельный лог | аудит домена — `task_status_history`; технические логи — pino |
| Feature flags | не вводятся: нет поэтапной выкатки, объём поставляется целиком |

## Не применяем (later/none)

| Принцип | Причина |
|---------|---------|
| Микросервисы и API Gateway | один разработчик, 30 RPS, модульный монолит |
| Event sourcing | история статусов уже append-only; полный ES не окупается |
| CQRS с отдельным write-хранилищем | путь записи один (Supabase), отчётный read-контур — реплика |
| Мультитенантные схемы | продукт на одну компанию |
| Distributed tracing (OTel) | отказ зафиксирован в ADR-0006, корреляция по `request_id` |

## Влияние на шаг 09

Каждый D-промпт обязан иметь: ЦЕЛЬ (одна проверяемая фраза), CONSUMES с путями и якорями,
PRODUCES ≤ 6 путей, `SIZE_BUDGET` с `size_ok: yes`, HOW, INVARIANTS (5–12), ACCEPTANCE с `Axx.k`
и ссылкой на test-plan, PRE-CHECK следующего среза.
