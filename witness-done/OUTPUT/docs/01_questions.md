# Вопросы к человеку — шаг 01

> Порядок групп: **Business → Product → Tech → Security → NFR → Ops**. Формулировки совпадают с
> `INPUT/ANSWERS.md`, чтобы можно было отвечать копированием.
> Критичных открытых вопросов нет: бизнес-цель, KPI, плательщик, пользователи, границы и стек
> зафиксированы в `INPUT/TECH_SPEC.md`. Ниже — по каждому вопросу источник ответа и default,
> который применяется, если ответ изменится.

## Business

**Q: Какая главная цель бизнеса на 12–24 мес?**
Зачем: без неё нельзя приоритизировать срезы и KPI.
Ответ: ТЗ §0 — заменить Excel и мессенджеры в оперативном учёте задач по стройобъектам.
Default при отсутствии: не применяется, шаг блокируется (`needs_human`).

**Q: Кто платит и кто пользуется?**
Зачем: определяет интерфейс, роли и приоритет сценариев.
Ответ: ТЗ §0 — платит строительная компания, пользуются руководитель и прорабы/инженеры.
Default: внутренний B2B-инструмент, покупатель = руководитель.

**Q: Какие KPI считают успех?**
Зачем: KPI превращаются в проверяемые NFR и критерии приёмки.
Ответ: ТЗ §0 — 12 измеримых KPI (доступность, латентность, доля отклонённых переходов, обходы RLS,
неизменяемость истории, отсутствие `service_role`, лаг репликации, RPO/RTO, откат, security-гейты,
time-to-first-value, развёртывание).
Default: набор KPI из §0 без изменений.

**Q: Как монетизируем? Что не монетизируем?**
Ответ: ТЗ §0 — монетизации нет, внутренний инструмент.
Default: биллинг, тарифы и платежи не проектируются.

**Q: Как узнают о продукте (GTM)?**
Ответ: ТЗ §0 — прямая демонстрация и обучение; лендинга нет.
Default: SEO, реклама, контент и аналитика трафика не входят в поставку.

**Q: Нужны ли SEO / контент / маркетинг-фичи?**
Ответ: ТЗ §0, §9 — нет, система закрытая, SSR не требуется.
Default: SPA без SSR; появление SEO-требования считается изменением объёма.

**Q: Конкуренты и отличие?**
Ответ: ТЗ §0 — Excel+мессенджеры, Bitrix24/YouGile/Asana, самописные CRM.
Default: отличие формулируется как «права и история в БД, а не в UI».

**Q: Анти-цели?**
Ответ: ТЗ §0 — не ERP/сметное/документное ПО, не универсальный трекер, не мессенджер и не
файлохранилище, не realtime-доска, не BI, не мультитенантный SaaS, не второй путь записи.
Default: перечисленные функции считаются OUT OF SCOPE с причиной.

## Product

**Q: Кто целевой пользователь?**
Ответ: ТЗ §1 — постановщик (`manager`) и исполнители (`executor`).
Default: две роли, третьей не добавляем.

**Q: Основная ценность?**
Ответ: ТЗ §1 — единый статус задачи, видимая загрузка, неизменяемая история.
Default: UI-украшения не приоритетнее прозрачности статуса.

**Q: Нужны ли файлы, переписка, уведомления, управление пользователями из UI?**
Ответ: ТЗ §2.2 — нет, это границы продукта с причиной.
Default: функции не проектируются; их появление — изменение объёма через `sp intake --kind change`.

## Tech

**Q: Backend?**
Ответ: ТЗ §3 — Fastify 4 на Node.js 20 + TypeScript strict, только чтение (отчёты, health, metrics).
Default: write-эндпоинты не создаются ни при каких условиях.

**Q: Frontend и стили?**
Ответ: ТЗ §3 — React 18 + TypeScript 5.5 strict, Vite 5, Tailwind 3.4 + Radix, токены из референса.
Default: тяжёлые UI-киты запрещены.

**Q: Доп. сервисы (кэш, брокер, аналитическая СУБД)?**
Ответ: ТЗ §3 — нет; отчёты читаются с реплики, кэш — TanStack Query и 30 с в процессе API.
Default: новые сервисы не добавляются без NFR-обоснования.

**Q: Инфраструктура?**
Ответ: ТЗ §3, §9c — Supabase Cloud (primary), Vercel (frontend), изолированный контур
backend + PostgreSQL 16 (реплика), Cloudflare на периметре.
Default: без собственного Kubernetes и без мультирегиона.

**Q: БД?**
Ответ: ТЗ §3 — PostgreSQL 15 (Supabase) + PostgreSQL 16 (реплика).
Default: иной СУБД не подставляется.

**Q: Мультитенантность?**
Ответ: ТЗ §2.2 — нет, одна инсталляция на компанию.
Default: схемы `tenant_id` не вводятся.

**Q: Профиль фабрики?**
Ответ: `web-app` + отклонение `read-only backend`, `admin-panel` снят (MANIFEST).

## Security

**Q: Compliance?**
Ответ: ТЗ §7 — ПДн сотрудников, хостинг ЕС; правовая оценка 152-ФЗ до реальных данных.
Default: PCI DSS/GDPR-фичи не проектируются.

**Q: 2FA?**
Ответ: ТЗ §8 — TOTP обязателен для всех учётных записей.
Default: без MFA вход не считается соответствующим требованиям.

**Q: Уровень OWASP?**
Ответ: ТЗ §8.1 — ASVS 4.0.3 Level 2 с зафиксированными отклонениями.
Default: L2, отклонения из таблицы §8.1.

**Q: Отдельный admin-контур?**
Ответ: нет; провижининг через Supabase по регламенту с журналом операций.
Default: UI-админки не появляется.

## NFR

**Q: Нагрузка?**
Ответ: ТЗ §7 — 500 пользователей, 5 000 объектов, 100 000 задач, пик 30 RPS.
Default: расчёт по этим числам; превышение — ревизия архитектуры.

**Q: SLA / доступность?**
Ответ: ТЗ §7 — 99.9% в месяц, RTO ≤ 60 мин, RPO ≤ 5 мин.
Default: 99% не принимается как «достаточно».

**Q: Latency p95?**
Ответ: ТЗ §7 — списки ≤ 400 мс, мутация ≤ 600 мс, вход ≤ 1 000 мс, отчёт ≤ 300 мс, health ≤ 50 мс.
Default: значения из §7 без смягчения.

## Ops

**Q: Хостинг?**
Ответ: ТЗ §3, §9c — Vercel + Supabase Cloud + изолированный контур backend/реплика.
Default: локальный Docker Compose только для разработки и тестов.

**Q: Кто поддерживает и дежурит?**
Ответ: ответственный разработчик; production-релиз с подтверждением через GitHub Environment.
Default: ротация не проектируется, но runbooks обязательны.

**Q: Мониторинг и алертинг?**
Ответ: ТЗ §3, §7 — Prometheus/Grafana Cloud, Sentry, uptime-монитор, алерты по 5xx, p95,
лагу репликации, диску, неуспешным входам.
Default: без наблюдаемости релиз не принимается.
