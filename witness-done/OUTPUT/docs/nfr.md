## 4. Модель нагрузки и объёма (12 месяцев)

Допущения: 500 учётных записей, из них 40 постановщиков и 460 исполнителей; 5 000 объектов;
100 000 задач (20 на объект); в среднем 4 перехода на задачу → 400 000 строк истории; пик 30 RPS
в рабочие часы (09:00–18:00 МСК), средние 5 RPS.

Расчёт — `docs/capacity-notes.md`. Триггеры ревизии: > 30 RPS устойчиво, > 500 000 задач,
размер истории > 2 млн строк, лаг репликации p95 > 5 с при нормальном диске.

## 5. Решения по масштабированию

- **Пагинация:** только keyset по `(created_at, id)`; `limit` ≤ 100. `offset` не используется.
- **Индексы:** под каждый list/filter/sort (`tasks(assignee_id, status) where deleted_at is null`,
  `tasks(object_id)`, `tasks(created_at desc)`, `objects(lower(title))`, `objects(lower(address))`,
  `task_status_history(task_id, created_at desc, id desc)`).
- **Кэш:** 30-секундный LRU в процессе API для отчётов (ключ — отчёт + параметры); TanStack Query
  на клиенте (`staleTime` 30 с, инвалидация по мутациям). Redis не вводится.
- **Пул соединений:** `pg.Pool` с `max = 10`, `idleTimeoutMillis = 10 000`, `connectionTimeoutMillis = 3 000`.
  PgBouncer не нужен: один процесс API, 30 RPS.
- **Партиционирование:** не вводится; триггер — 2 млн строк истории. При достижении —
  партиционирование по месяцу (декларативно) отдельным пакетом изменения.
- **Фоновые задачи:** нет cron внутри приложения; сверка реплики (`check.mjs`) — внешний запуск
  в CI/по расписанию, не в request path.

## 6. Надёжность

- **Идемпотентность:** `archive_*` идемпотентны; `change_task_status` не создаёт дубль истории,
  повторный переход отклоняется `P0422`.
- **Ретраи:** только на чтение (`GET`) с экспоненциальным backoff (200/400/800 мс, максимум 3),
  только на сетевые ошибки и `502/503/504`. Мутации не ретраятся автоматически.
- **Graceful degradation:** при недоступной реплике отчёты отдают `503`, продукт работает;
  при недоступном Supabase UI показывает состояние ошибки с «Повторить» и не теряет формы.
- **Health:** `/health` — процесс жив; `/health/replication` — подписка и лаг; readiness для
  контейнера — оба эндпоинта (replication допускает `lagging` на старте).
- **Миграции:** expand/contract, forward-only, идемпотентны, применяются до кода.

## 7. Наблюдаемость

- Метрики: `http_requests_total{route,status}`, `http_request_duration_seconds{route}`,
  `replica_lag_seconds`, `replica_streaming` (0/1), `db_pool_total/acquired/waiting`,
  `report_cache_hit_total`, `auth_failures_total`.
- Дашборды: продукт (доступность, p95, 5xx), репликация (лаг, слот, WAL), backend (RPS, latency),
  безопасность (неуспешные входы, отказы RLS).
- Алерты: 5xx > 0.5%/5 мин; p95 > 400 мс/5 мин; лаг > 30 с; подписка не `streaming` 5 мин;
  диск > 80%; серия из 10 неуспешных входов; отсутствие данных от uptime-монитора.
- Трассировка: OTel не вводится; корреляция по `request_id` и Sentry trace.
