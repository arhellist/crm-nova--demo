# ADR-0003: Логическая репликация Supabase → PostgreSQL 16 и read-only роль для отчётности

Дата: 2026-11-04

Статус: принят

## Контекст

Отчёты (сводка по объектам, загрузка исполнителей, сроки приёмки) не должны нагружать primary и не
должны иметь возможности менять данные. Нужен второй контур, который: читает те же данные,
отстаёт предсказуемо, восстанавливается из primary и не участвует в авторизации.

## Решение

- **Тип:** логическая репликация PostgreSQL, публикация `nova_pub` (`profiles`, `objects`, `tasks`,
  `task_status_history`) → подписка `nova_sub` на PostgreSQL 16, плагин `pgoutput`,
  `copy_data = true`, `create_slot = true`. `wal_level = logical` уже включён в Supabase.
- **Передаются** `INSERT` и `UPDATE`; `DELETE` в схеме не используется (архивирование — это
  `UPDATE deleted_at`), поэтому `REPLICA IDENTITY` по первичному ключу достаточно.
- **Схема secondary** накатывается теми же миграциями: DDL репликацией не передаётся. Порядок:
  миграции → подписка → сверка счётчиков.
- **Доступ API:** роль `nova_ro` — `LOGIN`, `CONNECT`, `USAGE`, `SELECT` на таблицы и отчётные
  вьюхи, `default_transaction_read_only = on`, DML-грантов нет.
- **Роль подписки:** `replicator` — `LOGIN REPLICATION` + `SELECT` на 4 таблицы; пароль только в
  менеджере секретов, контейнер `api` его не видит.
- **Контроль:** `pg_stat_subscription` (`streaming`), лаг = `pg_current_wal_lsn()` −
  `confirmed_flush_lsn`, `/health/replication` отдаёт `status`, `lag_seconds`, `last_error`;
  `infra/replica/check.mjs` сверяет `count(*)` и `max(updated_at)`; алерт при лаге > 30 с.

## Рассмотренные альтернативы

- **Физическая репликация (streaming)** — бинарная копия кластера, проще по лагу, но нельзя
  фильтровать таблицы, а Supabase-managed среда не даёт нужного доступа к конфигурации WAL.
- **Логический слот с фильтрацией строк** — усложняет initial copy и требует `BYPASSRLS` для роли
  подписки; принято решение публиковать таблицы целиком (4 небольшие таблицы, без `auth.users`).
- **Ночной экспорт (pg_dump)** — отчётность отставала бы на сутки; неприемлемо для приёмки.
- **Отчёты напрямую на primary** — нагрузка на единственный источник правды и лишние права.

## Последствия

Плюсы: primary разгружен, отчёты не могут изменить данные, лаг измерим и виден пользователю.
Минусы: DDL и RLS-политики не реплицируются — обе стороны ведутся миграциями; слот удерживает WAL
при длительном простое подписчика (контролируется алертом и мониторингом размера WAL); реплика не
является резервной копией. Дальше: скрипт `check.mjs` в CI и по расписанию, runbook пересоздания
подписки, отчётные вьюхи в отдельной миграции.

## Глоссарий

| Термин | Пояснение |
|--------|-----------|
| publication / subscription | публикация изменений и подписка на них в PostgreSQL |
| pgoutput | встроенный плагин логического декодирования |
| WAL | журнал предзаписи, из которого читаются изменения |
| REPLICA IDENTITY | правило идентификации строки при репликации |
