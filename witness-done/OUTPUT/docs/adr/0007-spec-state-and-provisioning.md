# ADR-0007: Место `spec-state/` и провижининг пользователей

Дата: 2026-11-04

Статус: принят

## Контекст

Два вопроса остались открытыми на шаге 00. Первый: где живёт каталог эволюции требований
`spec-state/` и как он попадает в репозиторий. Второй: как выдаются учётные записи и роли, если
UI-администрирования в продукте нет, а права менять «по памяти» нельзя.

## Решение

**`spec-state/`.** Живёт в корне проекта рядом с кодом (`<project>/spec-state/`), в том же
репозитории, и коммитится. Причина: baseline описывает действующее поведение продукта и должен
меняться вместе с кодом в одном PR; отдельный репозиторий создал бы дрейф. `OUTPUT/` остаётся внутри
`witness-done/` и описывает проектирование. Структура: `config.yaml`, `baseline/<domain>/spec.md`,
`changes/<id>/`, `archive/<дата>-<id>/`. Наполняется шагом R01 после `SELF_AUDIT: PASS`.

**Провижининг.** Учётные записи создаёт администратор компании в Supabase Auth; роль и имя
записываются в `profiles` (`role`, `full_name`). Порядок: заявка → создание пользователя → выдача
временного пароля по защищённому каналу → обязательное включение MFA при первом входе → запись в
журнал провижининга (`docs/runbooks/provisioning.md`, поля: дата, кто, кому, роль, основание).
Увольнение: блокировка пользователя и отзыв сессий в Supabase, запись в том же журнале. Прямых
грантов на `profiles.role` у приложения нет: изменить роль через API невозможно.

## Рассмотренные альтернативы

- **`spec-state/` внутри `witness-done/`** — смешивает проектирование и действующие требования,
  ломает чистоту канона и обновление фабрики.
- **Отдельный репозиторий спецификаций** — лишний процесс синхронизации при одном разработчике.
- **UI-администрирование пользователей** — расширяет поверхность атаки и требует отдельной
  RBAC-модели администратора; продуктовая граница зафиксирована в ТЗ §2.2.
- **Самостоятельная регистрация** — исключена требованием закрытой системы.

## Последствия

Плюсы: baseline и код меняются вместе; провижининг аудируем; эскалация роли через API невозможна.
Минусы: ошибка администратора возможна — компенсируется регламентом и журналом; процедура ручная.
Дальше: runbook провижининга в `docs/runbooks/`, проверка роли после создания, тест «`PATCH /profiles`
с `role=manager` → 0 строк».

## Глоссарий

| Термин | Пояснение |
|--------|-----------|
| baseline | зафиксированные действующие требования продукта |
| провижининг | создание и настройка учётной записи |
