# ADR-0005: Аутентификация через Supabase Auth, JWT в заголовке, обязательная MFA

Дата: 2026-11-04

Статус: принят

## Контекст

Нужны: закрытая выдача доступов (без самостоятельной регистрации), защита от перебора, второй
фактор и предсказуемое поведение токенов. Требование ТЗ — роль для прав берётся из БД, а не из JWT.
Классический CSRF неприменим, пока нет cookie-аутентификации.

## Решение

- Аутентификация — Supabase Auth (GoTrue): email + пароль, **TOTP MFA обязательна**; открытая
  регистрация (`disable_signup`) и самостоятельный сброс пароля отключены; учётные записи выдаёт
  администратор по регламенту.
- Токен передаётся только в `Authorization: Bearer`; cookie для API не используются, поэтому
  CSRF-модель строится на отказе от cookie, проверке `Origin` и небезопасных методах (ТЗ §8.7).
- Access-токен живёт 1 час, refresh ротируется с детектом повторного использования; inactivity
  timeout 7 дней, time-box 30 дней.
- Прикладная роль читается из `profiles.role`; claim `role` в JWT — это `authenticated` и для
  решений о доступе не используется.
- Токен хранится в `localStorage` (дефолт `supabase-js`); риск XSS компенсируется строгим CSP
  (`script-src 'self'`, без `unsafe-inline`/`unsafe-eval`), отказом от сторонних скриптов и запретом
  `dangerouslySetInnerHTML`.

## Рассмотренные альтернативы

- **Собственный auth-сервис** — полный контроль, но своя криптография, свои лимиты и своя ротация;
  противоречит принципу «не писать криптокод» (ASVS L2, глава V6 delegated).
- **httpOnly-cookie через BFF** — снимает риск XSS-кражи токена, но добавляет полноценную
  CSRF-инфраструктуру (double-submit, `__Host-`, SameSite, проверка токена на каждой мутации).
  Отложено как архитектурная точка расширения, а не «недоделка»: без cookie CSRF-атака невозможна.
- **Роль из claim JWT** — не работает: смена роли не применялась бы до истечения токена.

## Последствия

Плюсы: зрелая реализация, MFA «из коробки», отзыв сессий, минимум собственного кода, честная
CSRF-модель. Минусы: зависимость от Supabase Auth и его лимитов; токен в `localStorage` требует
безупречного CSP; переход на cookie-режим потребует отдельного пакета изменения и чек-листа.
Дальше: guard маршрутов, экран MFA, redact в логах, тесты на `alg:none`, чужой `aud`/`iss`,
истёкший токен и reuse refresh.

## Глоссарий

| Термин | Пояснение |
|--------|-----------|
| GoTrue | сервис аутентификации Supabase |
| TOTP | одноразовый код по времени (второй фактор) |
| aal | уровень гарантии аутентификации |
| reuse detection | обнаружение повторного использования refresh-токена |
