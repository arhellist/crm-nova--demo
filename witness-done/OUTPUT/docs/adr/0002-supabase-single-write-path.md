# ADR-0002: Supabase как единственный путь записи и источник прав

Дата: 2026-11-04

Статус: принят

## Контекст

Требование заказчика: права и переходы должны работать даже при прямом обращении к API в обход
интерфейса. Одновременно нужен собственный backend (отчётность). Если backend тоже умеет писать,
появляются два пути записи и два источника правды: любая проверка «в коде backend» обходится
запросом в Supabase, а RLS-политика перестаёт быть единственной.

## Решение

Единственный путь записи — Supabase: PostgREST для CRUD и `security definer` RPC для смены статуса
и архивирования. Права — RLS на всех таблицах, колоночные гранты, триггеры. Backend не имеет
соединения с primary и не имеет `service_role`. `service_role` используется только локальным
seed-скриптом, ключ берётся из менеджера секретов и не имеет префикса `VITE_`.

## Рассмотренные альтернативы

- **Backend как единая точка записи** — даёт централизованный аудит, но требует собственной
  аутентификации и реализует RBAC в коде, что прямо противоречит требованию.
- **Два пути (Supabase + backend)** — удваивает поверхность атаки, требует синхронизации правил и
  делает невозможным доказательство «обход через API не работает».
- **Только Supabase без backend** — не закрывает требование собственного read-контура и отчётности.

## Последствия

Плюсы: права проверяются в одном месте; обход интерфейса не даёт доступа; компрометация backend
не позволяет изменить данные. Минусы: бизнес-логика живёт в PL/pgSQL, что требует дисциплины
миграций и тестов; сложные отчёты выполняются на реплике, а не в приложении. Дальше: pgTAP-тесты
на каждую политику и переход, grep-гейт на `service_role`.

## Глоссарий

| Термин | Пояснение |
|--------|-----------|
| PostgREST | автоматический REST поверх таблиц PostgreSQL |
| RLS | построчная защита на уровне базы |
| security definer | функция, выполняющаяся с правами владельца |
