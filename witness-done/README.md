# Witness Done (v1.31.0) — полное руководство по фабрике

<div align="center">
  <img src="logo.jpg" alt="Witness Done — фабрика спецификаций для AI-агентов" width="560">
</div>

> **Witness Done** — портативная каноническая фабрика инициализации программных проектов для
> AI-агентов (Cursor IDE, Claude Code, Codex, Gemini, Copilot, Cline, Devin/Windsurf и др.).
> Она превращает техническое задание в
> **исполнимую спецификацию**: набор контрактов, заданий на разработку, критериев приёмки и
> машиночитаемых актов.
>
> Имя — про то, что она продаёт: не «сделано» на словах, а **свидетельство сделанного** (`witness`
> + `done`). Каждая фраза приёмки имеет объявленный тест, каждая галочка — артефакт, который можно
> перепроверить без автора.
>
> Это **единственный документ о проекте**: зачем он существует, как устроен, что делает на каждом
> шаге, чем доказывается готовность и как менять уже работающую систему. Исходные записи канона
> (с примерами из реального прогона) лежат в `aboutDocs/01…04` — они старше этого текста и служат
> первоисточником; актуальная версия правил — здесь и в `catalogs/`.
>
> Версия фабрики — в [`VERSION`](VERSION). Единственная точка входа для агента —
> [`ORCHESTRATOR.md`](ORCHESTRATOR.md). Правила агента в проекте — `AGENTS.md` в корне
> (адаптеры для IDE генерирует `sp rules --sync`). Профили проектов — [`PROFILES.md`](PROFILES.md).
> Вход любого запроса — [`sp.mjs`](SEED/sp-tools/sp.mjs): `status → intake → next`.

**Режимы работы (`MODE`):**

- **`greenfield`** — проектирование новой системы с нуля по ТЗ: `INPUT/TECH_SPEC.md` → волны
  `A → B → C (C1 → C2 → C3) → C4 (10 + 10b)` → `OUTPUT/` → автопереход в `brownfield` через `R01`.
- **`brownfield`** — развитие существующей кодовой базы через живой каталог спецификаций
  `spec-state/`: инициализация `R00 → R01`, затем итерационный цикл `R02 propose → R03 apply →
  R04 verify → R05 archive`.

## 1. Зачем существует Witness Done

### 1.1 Две болезни, которые лечатся архитектурно

Агент пишет код быстро, но забывает середину длинного документа, «додумывает» контракты и
объявляет задачу готовой, когда тесты зелёные, а продукт не работает. Первый релиз обычно
получается; второй — ломает первый, потому что никто не помнит, почему сделано именно так.

| Отказ | Что происходит | Цена |
|---|---|---|
| **Ambiguity** | В ТЗ «сделай личный кабинет», агент сам придумывает 40 решений | Переделки, споры, «а я думал иначе» |
| **Context rot** | На 5-м шаге агент не помнит инварианты с 1-го | Противоречия между модулями |
| **Scope drift** | Каждый промпт тянет новую фичу | Продукт растёт вширь, не вглубь |
| **Fake done** | «Готово», хотя тестов нет | Нельзя отличить работу от отчёта |
| **Lost decisions** | Решение принято в чате и потеряно | Повторные обсуждения, регрессии |
| **Huge prompts** | Один промпт на 3000 строк | Модель теряет середину, качество падает |

Witness Done лечит не «качество текста», а **две конкретные болезни**:

1. **Потеря смысла на дистанции.** Замысел живёт в чате и в голове автора; через месяц его
   восстанавливают заново и обычно хуже.
2. **Приёмка на слово.** «Готово» — это мнение, а не файл, который можно открыть и прочитать.

Ответ фабрики: **артефакты вместо памяти** и **акт приёмки вместо обещания**. Это не «просьба
к модели быть аккуратной», а детерминированный конвейер, где нечем закрыть шаг без файла и нечем
назвать задачу готовой без доказательства.

### 1.2 Три идеи, на которых всё держится

**1. Сначала договориться, потом кодить.**
Фабрика **не пишет код продукта**. Она производит исполнимый контракт: что читать, что сделать,
что нельзя нарушать, чем доказать. Причина не в аккуратности, а в цене ошибки: неверный контракт,
найденный до кода, стоит одного абзаца правки; тот же контракт после кода стоит переписанного
модуля.

**2. Полнота проверяется двумя независимыми способами.**

| Механизм | Вопрос | Где |
|---|---|---|
| Матрица покрытия | каждое требование стало заданием? | `OUTPUT/roadmaps/coverage-matrix.md` |
| Критерии завершения | продукт ведёт себя как продукт? | `OUTPUT/docs/exit-criteria.md` (`E1…En`) |

Одного мало: матрица без критериев даёт полную коробку нерабочих деталей, критерии без матрицы —
работающий продукт без половины обещанного.

**3. Приёмка — это файл, а не мнение.**
`done` ставится только при наличии акта: гейт, уровень, список проверенных утверждений `Axx.*`,
запущенные команды и их коды возврата. Проверку формирует инструмент (`sp-verify`), а не человек в
чате. Поэтому «проверил глазами» не является приёмкой.

### 1.3 Принципы

| Принцип | Что значит по-человечески |
|---|---|
| **Spec-first** | Пока не описано, что и как проверять, код не пишется |
| **Полнота** | Ни одна функция из ТЗ не потерялась: таблица «требование → задача» без пустых клеток |
| **Бизнес-цели первыми** | Сначала «зачем и для кого», потом «какие кнопки» |
| **SIZE_BUDGET** | Слишком большой кусок режется на части, а не «как-нибудь осилим» |
| **Context RAG** | Исполнителю дают только документы, нужные для этой задачи, а не весь проект |
| **VerificationTax** | «Готово» стоит денег: прогнать проверки и оставить след |
| **Decision lock** | Договорённости нельзя менять по ходу; изменение оформляется отдельно |
| **Стек — решение, не default** | Канон не назначает и не запрещает язык: стек выбирает команда, выбор фиксируется ADR, а пустое поле в ТЗ даёт вопрос, а не подстановку |
| **Checkpoint / waves** | Работа идёт порциями с фиксацией состояния, а не одним залпом |
| **Honesty** | Не хватает данных → вопрос человеку, а не догадка |
| **Язык** | Документы и правила — по-русски, чтобы их читал человек, а не только модель |
| **Комментарии** | Подробные, по-русски: через месяц это читает человек |
| **Никаких ярлыков неполноты** | Нельзя «MVP», «PoC», «пока без…» — иначе кусок целевой комплектации тихо выкидывается. Правило и гейт: `catalogs/completeness-policy.md`, `--gate d-prompt-quality` |

Запрет ярлыков неполноты — не косметика. Модель, назвав кусок «MVP», начинает резать целевую
комплектацию и оставляет «потом доделаем». Формулировка «строим сразу полную комплектацию, а
`S0…S8` — порядок поставки, а не поколения продукта» жёстко разделяет **порядок работ** и
**степень готовности**. Это правило канона, а не лозунг: оно записано в
[`catalogs/completeness-policy.md`](catalogs/completeness-policy.md), попадает в конституцию проекта
на шаге 02 и проверяется гейтом `sp-verify --gate d-prompt-quality`.

### 1.4 Что фабрика **не** делает

Это важнее списка возможностей: границы защищают от неправильного применения.

- **Не пишет код продукта.** Ни на одном шаге оркестрации. Код — следующий этап, по готовым заданиям.
- **Не проектирует за бизнес.** Если нет цели и KPI, фабрика останавливается (`needs_human`), а не
  придумывает продукт. «Технически красиво, никому не нужно» — не её результат.
- **Не заменяет архитектора и ревью.** Контракты и инварианты формулирует человек; фабрика их
  фиксирует, проверяет на непротиворечивость и не даёт забыть.
- **Не доказывает семантику тестов.** `sp-verify` проверяет машинно, что у каждой фразы приёмки есть
  тест, который её **объявляет** (`@acceptance Axx.k` или ID в имени), содержит утверждение, не
  пропущен и лежит в `PRODUCES` задания; что фразу не переписали после приёмки видно по
  `binding_hash`. Но что тест проверяет именно `Given/When/Then` по смыслу — по-прежнему
  обязанность автора теста и ревью, а не парсера.
- **Не подменяет staging.** Локальные гейты и smoke-прогоны не равны живому стенду и трафику.
- **Не «дорабатывает» спецификацию сама.** После baseline менять поведение можно только оформленным
  изменением (`R02`→`R05`); правка «по ходу» запрещена.
- **Не гарантирует качество входного ТЗ.** Противоречия в ТЗ она находит и выносит человеку, но не
  решает их за него.
- **Не является заменой CI.** CI — второй прогон тех же проверок; локальная приёмка идёт раньше.

### 1.5 Когда фабрика полезна, а когда нет

| Полезно | Не подходит |
|---|---|
| Продукт с несколькими доменами и живущим поведением | Скрипт на 200 строк, который проще переписать |
| Нужно передать работу другому исполнителю (человеку или ИИ) | Одноразовый прототип, который будет выброшен |
| Требования меняются, и важно помнить «почему так» | Исследование без требований и без приёмки |
| Есть цена ошибки в деньгах, данных или безопасности | Чисто визуальный эксперимент без контрактов |

Аналогия: фабрика — это не автор, а **технадзор и приёмочная комиссия**. Она не рисует дом, но не
даёт сдать его без фундамента и без акта.

## 2. Ключевые понятия

| Термин | Что это по-человечески |
|---|---|
| **`MODE`** | Режим: `greenfield` (с нуля) или `brownfield` (работающая система) |
| **Профиль** | Набор акцентов под тип продукта (`agent-harness`, `web-app`, `data-platform`, `custom`) |
| **`MANIFEST`** | Паспорт прогона: где мы, что готово, что ждёт человека. Единственный источник состояния |
| **`OUTPUT/`** | Что фабрика **спроектировала**: документы, контракты, задания, планы, акты |
| **`spec-state/`** | Что **действует сейчас**: baseline требований + активные и архивные изменения |
| **Baseline** | Снимок действующего поведения: `MUST/SHALL` + сценарии, по которым пишутся тесты |
| **Delta** | Что именно меняется в требованиях: `ADDED` / `MODIFIED` / `REMOVED` |
| **D-промпт** | Задание на поставку куска продукта: контракт, а не описание фичи |
| **Срез (`S0…Sn`)** | Тонкий, но сквозной кусок функциональности, который можно запустить и проверить |
| **Context Pack (`Pxx`)** | Ровно те документы, которые нужны одному заданию, + подтверждение валидности |
| **`ACCEPTANCE` / `Axx.k`** | Фраза-утверждение внутри задания, которая становится тестом |
| **Акт (evidence)** | Файл с результатом: что гоняли, с каким кодом, какие утверждения закрыты |
| **Гейт** | Конкретный вызов `sp-verify` (`pre_ci`, `change`, `self-audit`, …) |
| **Уровень `L0…L3`** | Строгость **задания**: сколько и каких проверок оно требует |
| **Scope `unit/module/app/eco`** | Четыре разных вопроса приёмки, а не «где запускали» |
| **Контур 1/2/3** | Точка приёмки: после задания → после группы → перед релизом |
| **VerificationTax** | Обязательная доля доказательств, без которой работа не выполнена |
| **Decision lock** | Зафиксированные контракты меняются только через оформленную процедуру |
| **SIZE_BUDGET** | Предел объёма задания; превышен — режем, а не «дотерпим» |
| **Матрица покрытия** | Таблица «требование → метрика → задание», 0 пропусков |
| **Критерии завершения** | `E1…En`: наблюдаемое поведение продукта с доказательством на каждый |
| **ADR** | Запись о принятом архитектурном решении: контекст, решение, последствия, отвергнутые варианты |
| **NFR** | Требования «как хорошо»: число + способ проверки + владелец |

Три слова, которые путают чаще всего:

- **`L0…L3`** — насколько строгий чек-лист у задания;
- **контур 1/2/3** — в какой момент проверяем;
- **гейт** — какой именно командой `sp-verify` проверяем.

Один и тот же уровень может проходить разные контуры разными гейтами.

### 2.1 Расшифровка: ADR и NFR

Два слова, которые встречаются в шагах и без расшифровки звучат как пароль.

**ADR — запись об архитектурном решении.** Короткая записка «почему сделали именно так», которую
можно открыть через год. Внутри: контекст; решение; последствия; **отклонённые альтернативы**;
статус. Появляется на шаге 03, по одной записи на каждое решение, которое дорого менять.

Зачем: чтобы «почему» не жило в голове автора. Через полгода новый участник видит не только «сделано
так», но и какие варианты отвергли — и не переделывает спор заново.

**NFR — требования «как хорошо», а не «что делает».** Функциональное требование говорит, **что**
система делает («сохраняет событие»); NFR говорит, **насколько хорошо** («падение процесса не теряет
запись», «p95 < 10 мс», «не дороже 10 $ на разговор»). Появляется на шаге 06.

Зачем отдельный шаг: без числа требование превращается в прилагательное («быстро», «экономно»,
«надёжно»), а прилагательное нельзя проверить и нельзя провалить. Поэтому каждое NFR имеет **число**,
**способ проверки** и **владельца** и превращается в рабочую задачу; иначе оно остаётся декларацией.

Разница в одну строку: ADR отвечает «почему мы так решили», NFR — «каким числом убедимся, что решили
хорошо».

### 2.2 Почему это «фабрика», а не «набор промптов»

1. **Порядок обязателен и обоснован.** План модулей — до нарезки работ, иначе куски начнут дублировать
   друг друга и спорить о границах. Реестры типов — до тел заданий, иначе каждый придумает свой формат
   события.
2. **Проверки, а не советы.** Программа приёмки возвращает результат и файл, а не «выглядит хорошо».
   Статус «готово» технически невозможен без пройденной проверки.
3. **Воспроизводимость.** Любой прогон оставляет состояние, артефакты и акты. Через месяц видно не
   только «что», но и «почему».

## 3. Структура фабрики

```
witness-done/
├── VERSION                     # версия фабрики (одна на всё)
├── ORCHESTRATOR.md             # точка входа для агента: режимы, волны, правила, resume
├── AGENTS.md                   # правила агента: источник истины, здесь же протокол входа
├── README.md                   # этот документ
├── logo.jpg                    # обложка этого README
├── PROFILES.md                 # профили проектов и отклонения от них
├── validate.sh                 # проверка целостности фабрики (без ИИ)
├── run.sh                      # короткая памятка запуска + validate
├── .cursorrules                # адаптеры правил в поставке: Cursor, Claude,
├── CLAUDE.md                   # Gemini, Copilot, Cline, Devin и команды /sp
├── .cursor/rules/ …            # генерируются из AGENTS.md командой sp rules --sync
│
├── catalogs/                   # «законы»: политики и каноны качества
│   ├── business-goals.md       # приоритет бизнес-целей, KPI, GTM
│   ├── completeness-policy.md  # полнота скоупа и SIZE_BUDGET
│   ├── stack-policy.md         # стек-агностичность: решение команды + ADR
│   ├── language-policy.md      # язык документов и кода
│   ├── typing-and-tests.md     # типы на границах и обязательные автотесты
│   ├── code-comments.md        # обязательные подробные комментарии
│   ├── verification-tax.md     # уровни, контуры, гейты, акты
│   ├── invariants.md           # глобальные INV-### проекта и селектор
│   ├── contour-smoke.md        # регламент смоук-тестирования
│   ├── agent-harness.md        # цикл работы агента-разработчика
│   ├── context-rag.md          # context packs и ограничения чтения
│   ├── design-input.md         # опциональный HTML-дизайн
│   ├── nfr-checklist.md        # чек-лист нефункциональных требований
│   ├── cicd-environments.md    # окружения и порядок деплоя
│   ├── intake-and-decisions.md # вход в проект и журнал решений
│   ├── agent-rules.md          # один источник правил → адаптеры IDE
│   └── antipatterns.md         # известные антипаттерны
│
├── PIPELINE/                   # пошаговые сценарии
│   ├── 00_bootstrap.md … 10_assembly.md   # greenfield
│   ├── 10b_self_audit.md                  # самопроверка продукта (волна C4)
│   └── R00_reverse_engineer.md … R05_archive_change.md  # brownfield
│
├── SEED/                       # базовые шаблоны, переносимые в проект
│   ├── cursorrules.template.md # шаблон правил агента
```

`spec-state/` — «что действует сейчас». Смешивать их — источник дрейфа: через месяц невозможно
сказать, какое из двух описаний правильное.

### 3.2 Какие файлы являются доказательствами

| Файл | Что доказывает | Когда появляется |
|---|---|---|
| `OUTPUT/evidence/Dxx.json` | приёмка **одного задания**: `acceptance_ids`, команды, коды возврата, `tax_pass` | после `sp-verify --d Dxx --gate pre_ci` |
| `OUTPUT/evidence/CHANGE-<id>.json` | приёмка **изменения**: дельта корректна, задачи закрыты, тесты прошли | после `sp-verify --change <id> --gate change` |
| `OUTPUT/evidence/RELEASE.json` | приёмка **релиза**: расширенный набор проверок | перед выпуском |
| `OUTPUT/evidence/BASELINE.json` | приёмка **базовой линии** R01 | после `--gate baseline` |
| `OUTPUT/evidence/SELF_AUDIT.json` | аудит продукта на шаге 10b | после `--gate self-audit` |
| `OUTPUT/evidence/prompt-quality-batch-N.json` | качество пачки заданий | после `--gate d-prompt-quality --batch N` |
| `OUTPUT/roadmaps/progress.md` | **производный статус**: `done` невозможен без ссылки на акт | после каждой приёмки |
| `OUTPUT/MANIFEST.md` | **состояние прогона** | после каждого шага |
| `OUTPUT/docs/exit-criteria.md` | критерии `E1…En` с доказательством на каждый | шаги 10 / 10b |
| `spec-state/archive/<дата>-<id>/` | что менялось и когда | после R05 |

Отдельно — **не доказательства, но измерения**: отчёты стенда и дымовых прогонов. Они говорят
«поведение такое», но не «задание принято».

**Почему тест-файл сам по себе — не доказательство.** Он отвечает только на «есть код проверки». Он
не отвечает: какую фразу он проверяет, запускали ли его, на каком наборе и с каким результатом.
`pytest -q` в терминале — тоже не доказательство: зелёный вывод не привязан к фразам и исчезает при
закрытии окна.

Цепочка, в которой каждое звено выводится из предыдущего:

```
фраза в задании (A03.2)
   → тест с этим номером в имени
      → строка в акте: A03.2 в acceptance_ids + команда exit 0
         → строка в progress.md: done + evidence_ref
            → MANIFEST: last_completed_step
```

Разрыв любого звена делает статус недоказуемым.

## 4. Быстрый старт

### 4.1 Установка и размещение

**Этот репозиторий и есть папка `witness-done`.** При установке она кладётся в проект под этим именем:

```bash
# SSH — если ключ добавлен в GitHub. <project>/witness-done — куда кладём фабрику.
git clone git@github.com:arhellist/WitnessDone.git <project>/witness-done
# HTTPS — публичный репозиторий, авторизация не нужна.
git clone https://github.com/arhellist/WitnessDone.git <project>/witness-done
# Уже скачан: -r копирует каталог рекурсивно, второй путь — приёмник.
cp -r WitnessDone <project>/witness-done
```

Имя `witness-done` фиксировано не из вкуса:

- на нём разрешаются ссылки `@witness-done/...` во всех шагах `PIPELINE/`;
- он первый кандидат при поиске `OUTPUT/`; если папки с таким именем нет, CLI берёт каталог,
  где лежит сам `sp.mjs`, — поэтому переименование папки не ломает запуск;
- в `MANIFEST` поле `FACTORY_PATH: witness-done/` — часть паспорта прогона.

Проверка после установки:

```bash
# run.sh — сам находит свой корень (проверяет VERSION/ORCHESTRATOR.md рядом с собой),
#           печатает ROOT, проект и OUTPUT/, затем маршрут первого шага. Аргументов нет.
bash witness-done/run.sh
```

Скрипт сам находит свой корень и печатает раскладку: `ROOT` (фабрика) и проект, в котором она стоит.

Нестандартный путь (папка называется иначе):

```bash
# status --factory <путь> — явно указать, где лежит канон. Обычно не нужно: CLI сам берёт
#                           каталог, в котором лежит sp.mjs. --root <путь> — где проект.
node <путь>/SEED/sp-tools/sp.mjs status --factory <путь>
```

Все подкоманды `sp` принимают `--factory` и `--root`. Внутри `PIPELINE/` путь `@witness-done/`
при этом придётся заменить на фактический — канон рассчитан на имя `witness-done`.

| Где вы находитесь | Как проверять | Как звучит `PROJECT_ROOT` |
|---|---|---|
| В репозитории фабрики (этот репозиторий) | `./validate.sh`, `./run.sh` | каталог, в который установлена папка `witness-done` |
| В проекте с установленной фабрикой | `bash witness-done/validate.sh` | корень проекта |

Пути внутри скриптов самолокализующиеся: `cd witness-done && ./validate.sh` **не нужно** — вы уже в ней.

### 4.2 Шаг 1. Подготовка ТЗ (`INPUT/TECH_SPEC.md`)

1. Скопируйте шаблон в рабочий файл:
   ```bash
   # cp <шаблон> <приёмник>: создаёт INPUT/TECH_SPEC.md из бланка.
   # Существующий файл будет перезаписан — сначала проверь, что он не заполнен.
   ```

   Образец заполненного ТЗ — `witness-done/TEMPLATES/examples/TECH_SPEC.demo.md` (пример, не вход проекта).
2. Заполните разделы:
   - **§0 Бизнес-цели и KPI (обязательно):** какую ценность несёт продукт, целевые метрики
     (LTV, CAC, Retention, RPS), стратегия GTM. Без этого шаг 01 остановится на `needs_human`.
   - **§2 Границы:** `IN SCOPE` (будет покрыт заданиями на 100%) и `OUT OF SCOPE` (явно исключено;
     уезжает в бэклог, а не выбрасывается).
   - **§3 Стек:** любой — язык, фреймворк и БД выбирает команда. Если не указан, фабрика спросит,
     а не подставит вариант по умолчанию; выбор фиксируется ADR на шаге 03.
   - Профиль продукта — по [`PROFILES.md`](PROFILES.md) (`agent-harness` / `web-app` /
     `data-platform` / `custom`) и отклонения от него, если профиль не подходит целиком.
3. *(Опционально)* дизайн: `INPUT/DESIGN.html` или `INPUT/design/*.html` — правила в
   `catalogs/design-input.md`, образец формы в `TEMPLATES/examples/DESIGN.example.html`.

### 4.3 Шаг 2. Проверка фабрики перед запуском

Из корня фабрики:

```bash
# validate.sh — проверка канона. Аргументов нет, ничего не меняет.
# --skip не предусмотрен: единственный переключатель — переменная SP_SKIP_SELFTEST=1.
./validate.sh
```

В конце должно быть `RESULT: PASS`. Валидатор не запускает ИИ: он проверяет структуру, каталоги,
шаблоны, обязательные поля и согласованность имён. Заодно он убеждается, что в `OUTPUT/` нет
остатков прошлого прогона, а `ORCHESTRATOR.md` существует ровно один.

### 4.4 Шаг 3. Запуск оркестратора

1. Откройте AI-ассистент (Cursor / Claude Code / Codex / Gemini).
2. Загрузите **`witness-done/ORCHESTRATOR.md`** и отправьте:
   ```text
   Запусти выполнение фабрики по ORCHESTRATOR.md. Начни с волны A.
   ```
3. Оркестратор пойдёт по шагам:
   - **00** — паспорт прогона `OUTPUT/MANIFEST.md` (`MODE`, профиль, `PROJECT_ROOT`, `FACTORY_PATH`),
     корневой `AGENTS.md` с протоколом входа, адаптеры IDE, `decisions.md`, pre-commit;
   - **01** — анализ ТЗ, бизнес-цели, границы, черновые срезы;
   - **02** — полная конституция в `AGENTS.md` + повторная генерация адаптеров;
   - **03–04** — архитектура, ADR, схема данных, OpenAPI;
   - далее волны B и C по таблице из §5.

Состояние фиксируется в `MANIFEST` после каждого шага, поэтому прогон можно продолжить в новой
сессии — через `sp next`, а не по памяти.

### 4.5 Шаг 4. Обработка вопросов (`NEEDS_HUMAN` и `ANSWERS.md`)

Если в ТЗ есть неоднозначности, оркестратор остановится со статусом `NEEDS_HUMAN` и запишет вопросы
в **`witness-done/INPUT/ANSWERS.md`**.

1. Ответьте на вопросы в файле.
2. Вернитесь в чат:
   ```text
   ANSWERS готовы — продолжай фабрику
   ```
3. Оркестратор продолжит с места остановки.

Правило трёх попыток: если ответа нет трижды, применяются разумные значения по умолчанию, и это
**честно** пишется в `MANIFEST` (`defaults_applied: true`) — допущение видно, а не замазано.
Канон не задаёт ни одного «своего» значения для стека: если стек не назван, вариантом по умолчанию
становится тот, что записан в ADR как допущение (высокий риск), а не скрытая настройка фабрики.

### 4.6 Вход в проект: `/sp`, intake и журнал решений

Вход один для всех режимов: **сначала запись, потом маршрут, потом код**. Команда `/sp` (Cursor,
Claude Code, Gemini CLI) делает это явно; в остальных инструментах те же команды вызываются руками.

```bash
# статус: где стоит проект. Аргументов нет.
node witness-done/SEED/sp-tools/sp.mjs status

# запись входа: "…" — запрос дословно (обязателен).
#   --kind <kind>   — new | question | change | task | bugfix, если классификация неоднозначна
#   --source <…>    — chat | issue | doc, откуда пришёл запрос
node witness-done/SEED/sp-tools/sp.mjs intake "Добавь экспорт отчёта в CSV"

# маршрут: next: из последней открытой записи. Аргументов нет.
node witness-done/SEED/sp-tools/sp.mjs next
```

Что происходит:

1. `status` читает `OUTPUT/MANIFEST.md`, активные `spec-state/changes/*`, `done` без актов и
   открытые записи входа.
2. `intake` создаёт `journal/intake/<YYYYMMDD-HHMM>-<slug>.md`: запрос **цитатой**, снимок состояния,
   `kind`, обоснование классификации и поле `next:`.
3. `next` печатает маршрут из последней открытой записи, иначе — resume из `MANIFEST`.

Классификация детерминированная (не «модель решила»):

| Условие | `kind` | Маршрут |
|---|---|---|
| прогон не начат | `new` | `PIPELINE/00_bootstrap.md` |
| `D\d\d` + greenfield | `task` | `OUTPUT/prompts/Dxx_*.md` |
| вопрос без глагола изменения | `question` | ответ + `sp decide` |
| вопрос **и** глагол изменения | `exit 3` | человек выбирает `--kind` |
| признак дефекта + принятое поведение есть | `bugfix` | `R02` с причиной в `proposal.md` §1 |
| есть незакрытый change | `change` | `R02 → R05` |

«Принятое поведение» — baseline (brownfield) или хотя бы одно `done` в `progress.md`; до первого
принятого задания дефект — это просто не написанная работа. Заказ новой работы дефектом не
считается: «добавь обработку ошибок 500» — `change`/`task`, «исправь ошибку» и «кнопка не
работает» — `bugfix`. Сомнительный случай называется явно: `--kind bugfix`.

Выбор, догадка, компромисс, конфликт контрактов — в журнал **до** кода:

```bash
# decide: решение в журнал. "…" — что решили и почему (обязателен),
#         --intake <ID> — к какой записи входа привязать, --adr — если решение архитектурное.
node witness-done/SEED/sp-tools/sp.mjs decide "Экспорт только CSV: XLSX не просили" --intake <ID>
# → journal/decisions/DEC-001-<slug>.md + индекс journal/decisions.md
```

Завершение — только ссылкой на артефакт, а не словом «готово»:

```bash
# close: закрыть запись входа.
#   <ID>        — имя файла в journal/intake/ без .md (обязателен)
#   --ref <…>   — id change-пакета, Dxx (проверит evidence) или DEC-### (проверит журнал)
node witness-done/SEED/sp-tools/sp.mjs close <ID> --ref DEC-001
```

### Куда попадает журнал

| Где работаем | Журнал | В git |
|---|---|---|
| Проект (`<project>/witness-done/`) | `<project>/journal/{intake,decisions}` + индекс `decisions.md` | **коммитится**: решения — часть проекта, а не заметки на ноутбуке |
| Корень канона (этот репозиторий) | `.witness-done-work/{intake,decisions}` | **никогда**: канон поставляется копией, чужие записи в нём недопустимы |

`journal/` создаётся из пустой заготовки `SEED/journal/` (`sp journal --init`, это же делает шаг 00).
В поставке он пуст: заполненный пример означал бы, что в новый проект приехали чужие решения.
Одна запись — один файл, поэтому ветки с разными решениями не конфликтуют; оглавление
`decisions.md` — производный вид и пересобирается `sp journal --index`. Проверка перед сдачей:
`sp journal --check --strict` (дубли `DEC-###`, битые ссылки, дрейф индекса, незакоммиченный журнал).

Коды: `0` — ok, `1` — ошибка вызова (пустой запрос, неизвестный `kind`/`--ref`), `2` — провал
проверки, `3` — нужен человек. Без `MANIFEST` `intake` не начинает прогон: он пишет маршрут
установки (в корне канона — режим §4.7). Полный цикл:

```text
intake → next → (вопрос? decide) → код по D / change-пакету → evidence → close → doctor --strict
```

CLI недоступен — порядок тот же руками по `catalogs/intake-and-decisions.md`. Журнал остаётся
обычным Markdown, а `sp doctor` проверяет файлы, а не историю вызовов.

| `.junie/guidelines.md`, `.kiro/steering/witness-done.md` | Junie, Kiro | копия / обёртка |
| `.aider.conf.yml` | Aider | `read: [AGENTS.md]` |

Копия, а не указатель, потому что Zed читает только первый найденный файл списка, а Claude Code
молча игнорирует `AGENTS.md` при существующем `CLAUDE.md`. `.rules` для Zed **не создаётся** — он
затенил бы `AGENTS.md`.

```bash
# rules --list — показать 13 целей адаптеров и состояние каждой: ok | missing | drift.
node witness-done/SEED/sp-tools/sp.mjs rules --list

# rules --sync — пересобрать адаптеры из AGENTS.md. Единственный режим, который пишет файлы.
#                --targets id,id — ограничить набор целей, например claude,cursorrules.
node witness-done/SEED/sp-tools/sp.mjs rules --sync

# rules --check — сверить без записи; exit 2 при рассинхроне (гейт для CI и pre-commit).
node witness-done/SEED/sp-tools/sp.mjs rules --check
```

Правка правил: только `AGENTS.md` → `sp rules --sync`. Канон и добавление новой цели —
`catalogs/agent-rules.md`.

**В самом репозитории фабрики правила уже в поставке.** `AGENTS.md` и все обязательные адаптеры
(`.cursorrules`, `.cursor/rules/witness-done.mdc`, `CLAUDE.md`, `GEMINI.md`, Copilot, Cline, Devin,
команды `/sp`) лежат в корне и закоммичены — агент видит конституцию канона сразу после `git clone`,
без установки. Правка канона изнутри репозитория идёт тем же входом:

```bash
# status — корень канона: MANIFEST нет, это норма.
node SEED/sp-tools/sp.mjs status
# intake — "…" запрос дословно; журнал уйдёт в .witness-done-work/, не в OUTPUT/.
node SEED/sp-tools/sp.mjs intake "…"
# decide — "…" формулировка решения; журнал локальный: .witness-done-work/decisions/
node SEED/sp-tools/sp.mjs decide "…"
# validate.sh — гейт канона; rules --check — адаптеры не разошлись с AGENTS.md.
./validate.sh && node SEED/sp-tools/sp.mjs rules --check
```

`sp doctor` в этом режиме проверяет не прогон, а канон (`doctor: ok — корень канона`).

### 4.8 Гейт: pre-commit и CI

| Где | Что проверяет |
|-----|---------------|
| pre-commit (`SEED/git-hooks/pre-commit`) | `sp doctor --staged`: правка вне `PRODUCES`, `done` без акта, рассинхрон правил |
| CI (`SEED/ci.yml.example`) | job `entry-and-rules` (`sp rules --check`, `sp doctor --strict`) + `evidence-gate` |
| шаг 10b | `sp doctor --strict` в чек-лист и в ось «трассируемость» |

Установка хука:

```bash
# cp <хук> .git/hooks/pre-commit — установить хук: git запускает файл с таким именем
#                                  перед каждым коммитом.
# chmod +x — сделать его исполняемым, иначе git его проигнорирует.
cp witness-done/SEED/git-hooks/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

`doctor` видит только файлы: он не знает, что происходило в чате. Дисциплину держит правило,
подкреплённое гейтом; `doctor` ловит последствия — изменённый файл без записи входа и без D.

### 4.9 Обновление фабрики

Фабрика лежит папкой `witness-done/` внутри проекта, и в этой папке соседствуют **две разные вещи**:

```text
witness-done/
├── VERSION README.md ORCHESTRATOR.md AGENTS.md catalogs/ PIPELINE/ SEED/ TEMPLATES/ LIBRARY/
│                                    ← КАНОН: обновляется
├── INPUT/                           ← вход проекта: не трогать
└── OUTPUT/                          ← артефакты прогона: не трогать
```

Отсюда единственное правило обновления: **заменить канон, сохранить прогон**. Распаковать архив
поверх нельзя — сотрётся `INPUT/TECH_SPEC.md`, `ANSWERS.md` и весь `OUTPUT/`.

Версия — одна строка в `VERSION` (сейчас `1.31.0`). Проверка обновления не скачивает фабрику, она
сравнивает эту строку с версией в репозитории из `SEED/update.json`:

```bash
# update — сверить VERSION с репозиторием. Обновление НЕ применяет, только печатает шаги.
#   --offline      — только кэш .sp-cache/update.json, без сети
#   --no-cache     — игнорировать кэш (он живёт 24 ч)
#   --timeout <мс> — таймаут HTTPS-запроса, по умолчанию 8000
#   --json         — машинный вывод
node witness-done/SEED/sp-tools/sp.mjs update                      # проверить (кэш 24 ч)
node witness-done/SEED/sp-tools/sp.mjs update --offline            # только кэш, без сети
node witness-done/SEED/sp-tools/sp.mjs update --no-cache --timeout 3000  # принудительно, таймаут 3 с

# status — строка «Версия фабрики» из кэша; в сеть не ходит никогда.
node witness-done/SEED/sp-tools/sp.mjs status
```

Два источника, по порядку:

| # | Источник | Когда работает |
|---|----------|----------------|
| 1 | `git ls-remote --tags origin` | фабрика установлена клоном: берётся максимальный тег `vX.Y.Z`, файлы не скачиваются |
| 2 | HTTPS `raw.githubusercontent.com/<repo>/<branch>/VERSION` | установка копированием или тегов нет: один запрос, таймаут по умолчанию 8 с |

Коды: `0` — актуально, `2` — есть обновление, `3` — проверить не удалось (нет сети, репозиторий
пуст, нет `SEED/update.json`). Третий код существует специально: «неизвестно» не должно выглядеть
как «всё хорошо».

**Что проверяется у `origin`.** Если URL похож на GitHub (`github.com:owner/repo`), `owner/repo`
сверяется с `SEED/update.json`: чужой remote — ошибка, а не «обновлений нет». Если URL не GitHub
(локальный зеркало-клон, `file://`), сравнить не с чем — проверка пропускается, а источник в выводе
помечается `git-теги (mirror)`. Это осознанный компромисс: без него работа через зеркало ломается,
но и гарантии «версия именно из канона» в этом режиме нет — поэтому `status` и вывод `update`
показывают источник явно, а не выдают зеркало за оригинал.

Вывод при доступном обновлении:

```text
Witness Done update
локально:  1.16.2   (/app/witness-done)
удалённо:  1.17.0   (arhellist/WitnessDone@main, git-теги)
установка: git clone
статус:    доступно обновление
обновиться:
  git -C "/app/witness-done" pull --ff-only
  node SEED/sp-tools/sp.mjs rules --sync
  node SEED/sp-tools/sp.mjs doctor --strict
```

Кэш — `witness-done/.sp-cache/update.json` (в `.gitignore`), TTL 24 ч; `--no-cache` проверяет
принудительно, `--offline` читает только кэш. `sp status` печатает
`Версия фабрики: <VERSION> (обновление: …)` и **никогда** не ходит в сеть.

**Чего команда не делает.** Она не применяет обновление сама. Канон — это шаблоны, по которым уже
созданы артефакты прогона: подмена на середине меняет правила под готовыми документами. Поэтому
`sp update` печатает шаги, а решение остаётся за человеком. В pre-commit проверка не входит: сеть
в хуке означает падение коммита без интернета.

Для установки копированием обновление — замена каталогов канона с сохранением `INPUT/` и `OUTPUT/`;
готовые команды печатает сама `sp update`. После любого обновления:

```bash
# После обновления канона: пересобрать адаптеры и проверить вход.
node witness-done/SEED/sp-tools/sp.mjs rules --sync     # адаптеры IDE под новую конституцию
node witness-done/SEED/sp-tools/sp.mjs doctor --strict  # гейт входа; предупреждения = провал
```

**Переход с версий до 1.29.** Бренд сменился, поэтому папка установки теперь называется
`witness-done/`. Если в проекте фабрика лежит под прежним именем — переименуйте каталог и
пересоберите адаптеры:

```bash
# <project> — корень проекта; <прежняя-папка> — каталог, куда фабрика была установлена раньше.
mv <project>/<прежняя-папка> <project>/witness-done
node witness-done/SEED/sp-tools/sp.mjs rules --sync    # адаптеры получат новые имена файлов
node witness-done/SEED/sp-tools/sp.mjs doctor --strict
```

Резолвер CLI от имени папки не зависит (он берёт каталог, где лежит `sp.mjs`), но ссылки
`@witness-done/...` в шагах `PIPELINE/` и поле `FACTORY_PATH` в `MANIFEST` рассчитаны на новое имя.
Старые файлы правил IDE (`*.mdc`, `*.md` в каталогах адаптеров) после `rules --sync` остаются
лежать рядом — их нужно удалить руками, иначе в проекте окажутся два набора правил.

## 5. Greenfield: что происходит на каждом шаге

### 5.0 Зачем вообще делить работу на шаги

Если дать ИИ задачу целиком — «сделай мне платформу» — получится правдоподобный черновик. Причины
механические: у модели нет памяти между сессиями; большой объём «размывается» (из 60 требований
выполняются 30, и неизвестно какие); ошибка обнаруживается в конце; нет общего языка (в одном месте
поле `input`, в другом `tool_input`); нечем доказать «готово».

Шаг **уменьшает неопределённость** и оставляет артефакт, на который можно ссылаться. К началу
программирования на руках: описание продукта, правила, архитектура, контракты, план работ и
критерии приёмки. Догадываться не нужно — нужно выполнить.

### 5.1 Что должно быть на входе

| Вход | Обязателен | Что с ним делают |
|---|---|---|
| `TECH_SPEC.md` | да | цели, пользователи, сценарии, ограничения, IN/OUT OF SCOPE |
| бизнес-контекст | да | зачем продукт: цель, метрики, как продаётся |
| дизайн (`*.html`) | нет | превращается в `design-notes.md`; UI-задания обязаны им следовать |
| `ANSWERS.md` | при возобновлении | ответы человека на вопросы фабрики |

Перед стартом: создаётся `MANIFEST`, выбирается профиль, фиксируются язык и стек. «Поменять стек по
привычке» запрещено — иначе к десятому шагу половина решений противоречит другой половине.

**Типичная ошибка:** начинать с архитектуры. Архитектура без разбора «для кого и зачем» описывает
воображаемый продукт. Порядок шагов это блокирует: архитектура идёт третьей.

### Волна A — понять, что строим (00–04)

Смысл: **зафиксировать смысл**. После волны любой участник отвечает: что за продукт, для кого, по
каким правилам, из каких узлов состоит, какие у него словари.

#### Шаг 00 — каркас и состояние

- структура `OUTPUT/`: `docs`, `specs`, `security`, `roadmaps`, `prompts`, `context/packs`, `tests`,
  `tooling`, `evidence`, `rules`;
- поля `MANIFEST`: режим, версия, дата, `PROJECT_ROOT`, `FACTORY_PATH`, профиль и отклонения,
  покрытие, волна, статусы шагов 00–10b **и** R00–R05;
- запрет `OUTPUT/library/`: библиотека живёт только в глобальной `LIBRARY/`.

**Проверка:** файл существует, поля заполнены, все шаги перечислены со статусами.
**Почему не формальность:** это единственная точка, из которой отвечается «где мы и что дальше».

#### Шаг 01 — анализ: кто, зачем, где границы

Четыре вопроса: кто участники (пользуется, админ, платит, атакует); какие метрики улучшаем; что
входит и что не входит; где в ТЗ дыры и противоречия. Плюс **черновые вертикальные срезы** —
кандидаты на тонкие сквозные куски.

**Выход:** `docs/01_analysis.md`, `docs/01_questions.md`, обновлённый `MANIFEST`.
**Почему нельзя додумать:** додуманное требование всплывёт через месяц в виде переделки.

#### Шаг 02 — правила проекта (исполняемая память)

Создаются `AGENTS.md` и `.cursorrules`: роль агента; **приоритет источников истины** (спеки →
правила → архитектура → код → чат); выбранный стек и кодовые запреты (языковых запретов в каноне
нет); правила типов; правила комментариев; обязательность тестов; формат отчёта в конце задачи.

Особые запреты, которые выглядят мелкими, но спасают проект:

- никаких ярлыков неполноты (`MVP`, «пока без…», `v1` как статус) — канон:
  `catalogs/completeness-policy.md`;
- никакой пересборки и перезапуска без разрешения;
- не изобретать архитектуру молча: «останавливаюсь, не хватает X» + один предложенный вариант.

**Выход:** `AGENTS.md` в корне + адаптеры IDE (`sp rules --sync`), `OUTPUT/rules/definition-of-done.md`,
`OUTPUT/rules/INSTALL.md`. Копий правил в `OUTPUT/rules/` нет: их роль забрали корневые файлы.

#### Шаг 03 — архитектура и «почему так»

1. Уровни описания: система и внешние участники → крупные блоки → модули → критичные узлы.
2. **ADR** на каждое необратимое «почему»: контекст, решение, последствия, отвергнутые
   альтернативы, статус.
3. Границы модулей: кто кому что может, кто владеет какими данными.
4. Числовые требования к качеству (не «быстро», а «столько-то»).
5. Базовая безопасность: что считается недоверенным входом.
6. Если есть дизайн — заметки по экранам, состояниям, тону.

**Проверка:** у каждого модуля есть ответственность и владелец данных; у каждого «почему» есть
запись; нет модулей «на всякий случай».
**Типичная ошибка:** архитектура «на вырост» — очередь и микросервисы для трёх пользователей.

#### Шаг 04 — данные, интерфейсы и словари

Создаются **реестры** — именно их отсутствие превращает задания в лоскутное одеяло:

| Реестр | Что в нём | Почему критично |
|---|---|---|
| **Типы событий** | имя, обязательные поля, когда возникает, поведение при воспроизведении + общий конверт | без него каждый кусок придумает свой формат |
| **Контракты инструментов** | повторяемость, воспроизводимость, человек, таймаут, вычищение, лимиты, режимы отказа | иначе один вернёт текст, другой объект, третий ошибку как успех |
| **Транспорт** | CLI, HTTP, поток событий, коды выхода, форматы | иначе «наружу» получится три разных продукта |

Плюс модель данных, внешний API, бизнес-правила, политики (пути, секреты, redaction,
параллельность).

**Проверка:** каждый тип события из сценариев есть в реестре; каждый инструмент есть в контрактах;
у контракта заполнены все поля.
**Почему раньше заданий:** задание не имеет права «придумать поле». Если реестра нет, два задания
назовут одно и то же по-разному, и расследование инцидента упрётся в нечитаемую историю.

**Итог волны A:** в `MANIFEST` волна закрыта, последний шаг — 04. Идти дальше нельзя, пока реестры
не полны: волна B начнёт на них ссылаться.

### Волна B — зафиксировать ограничения (05–08)

Смысл: **добавить реальность**. Продукт понятен; теперь — чего он не должен делать, сколько
выдерживает, из каких модулей состоит и как проверяется.

#### Шаг 05 — безопасность: модель угроз

- угрозы по категориям для каждого блока: подмена, незаметное изменение, отказ, раскрытие данных,
  перегрузка, повышение прав;
- субъекты и разрешения: роли, области действия;
- секреты и настройки: хранение, подстановка, что попадает в логи/события/запрос к модели;
- защита данных: персональные данные, redaction, сроки хранения, шифрование, бэкапы;
- чек-лист «да/нет с доказательством», а не «желательно».

**Проверка:** у каждой угрозы есть контроль и место реализации; нет угроз без решения и без явного
«принимаем риск».

#### Шаг 06 — числовые требования и ёмкость

Задержка ответа и время до первого токена, доступность; сколько групп/клиентов/браузеров держит
узел; сколько живут события, артефакты, логи; обязательные метрики и трассировки; поведение при
переполнении бюджета, таймауте, падении провайдера; **превращение требований в задачи**.

**Проверка:** у каждого NFR есть **число**, **способ проверки** и **владелец**. NFR без числа — это
прилагательное («быстро», «экономно»), которое нельзя проверить и нельзя провалить.

#### Шаг 07 — план модулей и конфликты

- перечень модулей: ответственность, зависимости, публичные интерфейсы;
- где модули пересекаются, кто владеет функциональностью, как решили;
- правила переиспользования: не дублировать утилиты, не делать «свой велосипед» в каждом задании;
- библиотеку **описываем**, а не копируем в `OUTPUT/`.

**Почему до заданий:** без горизонтального плана два задания создадут «свой retry» и «свою очередь»,
и потом их придётся сливать.

#### Шаг 08 — линтеры, сборка, окружения, CLI

- реальные конфиги линтера, строгие типы, `no any`;
- конвейер: зависимости → линт → типы → тесты → дымовой прогон;
- окружения: что где запускается, переменные, порты, порядок деплоя;
- CLI уже стоит в `witness-done/SEED/sp-tools/`; копировать в `scripts/sp-tools/` не нужно (DEC-034),
  путь фиксируется в `OUTPUT/tooling/`;
- `OUTPUT/tooling/verify-commands.md` — команды lint/typecheck/test, wave smoke vs product-smoke;
- `OUTPUT/tooling/harness.md` — цикл работы агента, resume-фразы, запрет `done` без акта;
- смок-шаблоны из `SEED/smoke/` материализуются в `scripts/smoke/` и `OUTPUT/docs/runbooks/`.

**Проверка:** конвейер запускается, дымовые команды воспроизводимы, секретов в репозитории нет.

**Итог волны B:** в `MANIFEST` волна закрыта. Дальше — самая дорогая часть.

### Волна C — разложить работу и написать задания (09, 10, 10b)

#### C1 — карта работ (ещё без тел заданий)

Семь артефактов: обзор плана; граф зависимостей (**циклы запрещены**); вертикальные срезы
`S0…Sn` и чем проверяются; нарезка `d-cut-list`; матрица покрытия; прогресс; индекс контекста.

**Главная идея — вертикальный срез.** Срез не «слой» (все события в одном, весь интерфейс в
другом), а тонкая, но сквозная функциональность, запускаемая и проверяемая в тот же день. Пример:
первый срез = «каркас + команда `version` + заглушка обработки сбоев», проверка — `version`
возвращает 0. Выглядит скромно — и поэтому работает: первый кусок честно проверяется в первый день.

Границу среза выбирают по четырём вопросам:

| Вопрос | Хороший ответ | Плохой ответ |
|---|---|---|
| Что появится такого, что можно запустить? | «команда отвечает и возвращает 0» | «появится модуль событий» |
| Чем проверить одной командой или заготовкой? | конкретный сценарий | «проверим, когда будет всё остальное» |
| От чего зависит и всё ли уже принято? | только от закрытых кусков | «зависит от шести других» |
| Сколько затрагивает? | одна сущность, ограниченное число файлов | «заодно тронем журнал, интерфейс и шлюз» |

Порядок: строки объёма из ТЗ → группировка по **способности** → проверка на каждую группу → нарезка
заданий **по владельцу данных** → проверка объёма. Итог — в `roadmaps/d-cut-list.md`: что вошло и что
сознательно вынесено.

**Главный признак неправильной нарезки:** кусок нельзя проверить, не закончив следующий.

**Проверка C1:** матрица покрытия без дыр; граф без циклов; у каждого среза есть способ проверки; у
каждого задания есть срез и группа.

#### C2 — тексты заданий (пачками не больше пяти)

Для каждого задания: набор контекста с подтверждением валидности; тело задания (роль, срез, что
читать, что потребляет, что производит, как делать, что нельзя нарушать, как проверить, бюджет);
самопроверка на двусмысленность; формальная проверка пачки.

Правила:

- пачка ≤5 — иначе качество падает;
- context pack без `validation_ok` → остановка: читать нечего;
- задание **не переписывает** реестры; не хватает контракта — правится шаг 04;
- после пачки — `sp-verify --gate d-prompt-quality --batch N` и обновление `MANIFEST`.

#### C3 — планы проверок и бэклог

- план проверок на каждое задание: какие тесты, какие данные, какие `Axx` закрывают, что считается
  нестабильным и как лечится;
- карта «задание → план проверок → тесты → доказательство»;
- бэклог улучшений (всё, что вне объёма, с приоритетом «потом»);
- полная комплектация: что должно быть в продакшене независимо от порядка поставки.

**Проверка C3:** у каждого утверждения есть план проверки; нет утверждения без теста.

#### Шаг 10 — сборка и связность

1. Отчёт о связности: ссылки ведут на существующие типы и контракты; нет висячих идентификаторов и
   дублей.
2. Индексы: с чего читать, карта артефактов.
3. Обратная связь `feedback.md`: что сработало, что было непонятно, что пришлось переделывать.
4. Критерии завершения `exit-criteria.md`: каждое условие наблюдаемо и имеет доказательство.
5. Финальная проверка полноты: покрытие без пропусков, у заданий есть материалы и планы проверок.

#### Шаг 10b — аудит собственного продукта

Аудит **по артефактам**, без «мнений модели»:

| Проверка | Что смотрит | Если провал |
|---|---|---|
| Доказательства | акт по каждому заданию: гейт, налог, утверждения | задание нельзя считать готовым |
| Базовая линия | покрывает ли описание действующего поведения все домены | следующий этап начнётся с дыры |
| Качество заданий | `HOW` / `INVARIANTS` / `ACCEPTANCE`, объём | задание непригодно к исполнению |
| Планы проверок | у каждого утверждения есть тест | приёмка — фикция |
| Критерии завершения | покрытие, ссылки, доказательства | продукт не соответствует ТЗ |
| Риски | у каждого риска есть владелец | риск без владельца — это сюрприз |

Инструментально: `--gate d-prompt-quality` (все пачки), `--gate self-audit`, `--gate product-smoke`.
Провал → исправления → повторный 10b. `SELF_AUDIT: PASS` — обязательное условие перехода в `R01`.

#### Финиш: описание действующего поведения (R01)

После аудита автоматически создаётся **базовая линия** — описание того, как система работает
**сейчас**, по доменам. Режим переключается на `brownfield`.

**Зачем:** артефакты первого этапа описывают **замысел**, baseline описывает **действительность**.
С этого момента менять систему можно только оформленным изменением — иначе через полгода никто не
скажет, что соответствует реальности, а что осталось от планов.

### 5.2 Волны и checkpoint

| Волна | Шаги | Результат | Resume |
|---|---|---|---|
| **A** | 00 → 04 | анализ, правила, архитектура, данные и контракты | `продолжай волну B` |
| **B** | 05 → 08 | безопасность, NFR, план модулей, CI/CD и линтеры | `продолжай волну C` |

После каждой волны: обновить `MANIFEST` (`last_completed_step`, `wave`, `c_subwave`, `c2_batch`),

### 5.3 Сводная схема

```
ТЗ + бизнес-контекст
  → 00 каркас / MANIFEST
    → 01 анализ (кто, зачем, границы, срезы)
      → 02 правила (AGENTS.md + .cursorrules)
        → 03 архитектура + ADR
          → 04 данные, API, реестры

                        → C3 тест-планы + бэклог
                          → 10 сборка (связность, exit-criteria)
                            → 10b аудит (доказательства, качество)
                              → R01 baseline → brownfield
```

## 6. Задание на разработку (D-промпт)

### 6.1 Проблема, которую решает задание

Дать агенту «сделай EventLog» — значит получить разное понимание объёма, пропущенные требования,
недоказуемость, расползание и невоспроизводимость. Задание отвечает на шесть вопросов:

1. **Что читать** (и что не читать).
2. **Что произвести** — конкретный список файлов, событий, контрактов, тестов.
3. **Как делать** — порядок действий, а не пожелание.
4. **Что нельзя нарушать** — свойства, которые важнее удобства.
5. **Как доказать** — наблюдаемые утверждения, каждое из которых становится тестом.
6. **Сколько это по объёму** — иначе задание расползётся.

### 6.2 Анатомия

| Секция | Отвечает на вопрос | Требование |
|---|---|---|
| Шапка | в какой срез входит, с кем в группе, от чего зависит | без среза и группы задание не начинается |
| **РОЛЬ** | кто исполняет и на каком уровне | «senior-инженер такого-то стека», а не «универсальный помощник» |
| **ЗАВИСИТ ОТ** | что должно быть принято раньше | `Dxx`, все `done` в `progress.md` |
| **SIZE_BUDGET** | сколько это по объёму | `surfaces` ≤2, `produces_count` ≤6, `entity`, `delivery_slice`, `split_group`, `split_from`, `size_ok` |
| **ЦЕЛЬ** | какой вертикальный результат | одна фраза, без «и» между независимыми deliverable |
| **CONSUMES** | что уже существует и используется | ссылки на реестры и якоря, а не «примерно так же» |
| **CONTEXT_PACK** | что прочитать | `pack_id`, `pack_path`, `retrieve_query`, `max_chunks` ≤12, `validation_ok: yes` |
| **HOW** | в каком порядке делать | шаги-действия; для `L0` — явное `N/A — причина` |
| **INVARIANTS** | что нельзя нарушить | 5–12 проверяемых буллетов |
| **ACCEPTANCE** | как доказать | таблица `Axx.k` Given/When/Then; `L1` ≥3, `L2/L3` 6–12 |
| **FIT_CHECKS** | за что задание может зацепить соседей | `module`, `conflicts_ref`, `conflicts_applied`, `app_contracts`, `depends_done`, `eco_invariants` |
| **VERIFICATION_TAX** | насколько строгая приёмка | `level`, `verify_cmd`, `evidence`, `done_forbidden_unless` |
| **PRODUCES** | что появится | проверяемый список; код/конфиг ≤6 (тесты отдельно) |
| **НЕ ТРОГАТЬ** | защита от расползания | «не agent loop, не реестр инструментов, не интерфейс» |
| **PRE-CHECK** | что проверить до кода | существование входов, отсутствие BLOCKER, `size_ok`, pack валиден |
| **ОГРАНИЧЕНИЯ / ФОРМАТ ВЫВОДА / ЧЕКЛИСТ / STOP** | границы и правила остановки | один D — один заход, затем `pre_ci` |

### 6.3 Почему каждая секция именно такая

**CONTEXT_PACK — не «прочитай репозиторий».** Полный набор артефактов — десятки тысяч строк. Если
задание читает всё: контекст переполняется и модель теряет **середину**; растут стоимость и задержка;
появляется «случайная связанность» — задание правит чужое, потому что «увидело». На каждое задание
собирается минимально достаточный набор + `Pxx.validation.json`. **Правило жёсткое:** pack без
отметки «валиден» → остановка.

**HOW — не «требования».** «События должны надёжно сохраняться» можно выполнить десятью способами и
нельзя проверить. «Проверь схему → вычисти секреты → запиши во временный файл → сбрось на диск →
переименуй → сбрось каталог → только теперь уведоми подписчиков» — это алгоритм, и свойство «сначала
запись, потом уведомление» становится проверяемым.

**INVARIANTS — не «постарайся».** Инвариант — свойство, которое нельзя нарушить даже ради удобства:
ни один подписчик не получает событие до записи на диск; цепочка отпечатков не рвётся; сырой пароль
не попадает ни в журнал, ни в запрос к модели; путь не выходит за рабочую папку. **Инвариант без
механизма проверки — лозунг:** каждый привязан к тесту или к проверке в коде.

**ACCEPTANCE — не «готово».** Вместо «работает корректно» пишутся конкретные фразы. Проверка фразы:
*можно ли это проверить, не спрашивая автора, что он имел в виду?* Если нет — переписывается.

| Бесполезно | Рабочая версия |
|---|---|
| «события сохраняются надёжно» | «если убить процесс после записи, но до уведомления, после перезапуска событие читается» |
| «инструменты работают корректно» | «чтение пути вне рабочей папки возвращает ошибку политики и не читает файл» |
| «UI удобный» | «при нажатии «Отклонить» запрос исчезает из списка, агент получает отказ» |
| «обрабатываются ошибки» | «при таймауте сети инструмент делает один повтор, затем возвращает `network_timeout`» |

**SIZE_BUDGET — не «как-нибудь осилим».** Задание на 400 строк исполняется хуже трёх по 120: теряется
середина, растёт число внутренних противоречий, инвариант из начала перестаёт влиять на конец. Не
влезает — режем **внутри способности** (взять меньше сценария), а не «отрезаем слой».

`split_from` — не украшение: он показывает историю решения («выделено из D12»), и через месяц видно,
что это не новая функция, а продолжение старой.

**Почему задания готовятся пачками ≤5.** Причины инженерные, а не эстетические: пять заданий с
наборами контекста — это уже десятки тысяч токенов, дальше модель начинает «экономить» и сокращать;
шестое задание обычно копирует структуру первого и теряет свои инварианты; пачка проходит гейт
целиком, и если одно задание плохое — дешевле переписать пачку, чем искать дефект в двадцати.

### 6.4 Антипаттерны заданий

| Антипаттерн | Как выглядит | Лечение |
|---|---|---|
| Абстракция вместо действия | «обеспечить надёжность» | порядок шагов в `HOW` |
| Непроверяемая приёмка | «работает корректно» | утверждение с наблюдаемым результатом |
| Скрытая зависимость | использует поле, которого нет в реестре | правка шага 04 до написания заданий |
| Дублирование | свой retry в каждом задании | общий модуль в плане модулей |
| Раздувание | пять модулей в одном задании | резать по вертикали |
| Двусмысленность | «при необходимости» | убрать или задать числовое условие |
| Подмена проверки | «проверено вручную» | доказательство только из формального прогона |
| Ярлык неполноты | «MVP», «пока без авторизации» | полная комплектация; `S0…Sn` — порядок поставки |

### 6.5 Почему задание нельзя «поправить по ходу»

После написания заданий **словари блокируются**: типы событий, контракты инструментов, транспорт.
Причины: задания опираются на одни и те же типы; журнал только дополняется; без блокировки «мелкое
улучшение» превращается в дрейф. Легальный путь — **оформленное изменение** (см. §8), даже если
проект создан только что. Именно поэтому фабрика сама переводит проект в brownfield на финише.

### 6.6 Как задание исполняется (Harness Loop)

```
прочитать CONTEXT_PACK
  → прочитать HOW / INVARIANTS / ACCEPTANCE
    → реализовать по шагам, не расширяя объём
      → написать тесты, привязанные к Axx
        → sp-verify --d Dxx --gate pre_ci  (линтер → типы → тесты)
          → прочитать акт глазами
            → progress.md: done только при tax_pass + всех Axx
```

1. **Взять задачу:** следующий по порядку `OUTPUT/prompts/Dxx_….md`.
2. **Код + тесты:** строго по стеку (`catalogs/stack-policy.md`), подробные комментарии на русском
   (`catalogs/code-comments.md`), тест на каждую фразу.
3. **Верификация:** `node witness-done/SEED/sp-tools/sp-verify.mjs --d Dxx --gate pre_ci`.
4. **Статус:** `done` только при коде возврата 0, `tax_pass: true` и непустом `acceptance_ids`
   (для `L1+`), иначе `needs_rework`.
5. **Стоп:** следующий D не начинается. «Доделаю потом» превращается в каскад из трёх задач на
   непроверенном фундаменте.

## 7. Как доказывается готовность (VerificationTax)

### 7.1 «Готово» — это не ощущение

| Возможное содержание слова «готово» | Как проверить |
|---|---|
| «компилируется» | это только синтаксис |
| «я проверил вручную один раз» | не воспроизводится, не видно, что именно проверяли |
| «тесты зелёные» | какие тесты? покрывают ли они требование? |
| «работает у меня» | а в контуре? а на клиенте? |
| «почти, осталось мелочи» | самая дорогая категория |

Идея: сделать «готово» **платным**. Чтобы назвать шаг готовым, надо заплатить налог — прогнать
проверки и оставить машиночитаемый акт. Нет акта — нет статуса.

Три слова, которые надо различать:

| Слово | Что значит |
|---|---|
| **Утверждение** (`A03.2`) | фраза «если сделать так, то должно наблюдаться вот это» |
| **Проверка / тест** | код, который делает «так» и смотрит, наблюдается ли «это» |
| **Акт (evidence)** | файл с результатом: что гоняли, с каким кодом, какие утверждения закрыты |

Утверждение без теста — пожелание. Тест без утверждения — код, который что-то проверяет, но
неизвестно что. Акт без утверждений — красивая бумага.

### 7.2 Четыре вопроса (`scope`) и четыре уровня (`level`)

| `scope` | Вопрос по-человечески | Аналогия с ремонтом |
|---|---|---|
| **unit** | «Эта деталь вообще работает сама по себе?» | проверили розетку тестером |
| **module** | «Не залезла на территорию соседа и не сломала его?» | электрик не перерезал чужую проводку |
| **app** | «Стыкуется с остальными частями?» | вилка подходит к розетке, автомат не выбивает |
| **eco** | «Не нарушает правил дома?» | пожарная безопасность, не затопил соседей |

Конкретно: `unit` — линт, типы, тесты задания; `module` — нет «второго владельца» функциональности,
границы модулей не нарушены; `app` — внешние контракты существуют и не изменены молча, зависимости
приняты; `eco` — логирование, rate-limit, отсутствие секретов, заметки по дизайну, антипаттерны.

Уровень — свойство задачи, а не самооценка «мне кажется, это важно»:

| Уровень | Когда | Что требуется |
|---|---|---|
| **L0** | только документация | файлы появились; приёмка может быть `N/A` с причиной |
| **L1** | обычный код | четыре scope + **≥3** `Axx` → `pre_ci` |
| **L2** | API / UI / домен | `L1` + ≥1 `METHOD /path` в `app_contracts` + **6–12** `Axx` + eco baseline |
| **L3** | деньги, квоты, бухгалтерия | `L2` + eco full + **обязательное подтверждение человеком** + участие в `pre_release` |

### 7.3 Контуры и гейты

| Контур | Когда | Что |
|---|---|---|
| **1. D** | после каждого runtime-задания | `HOW` + `INVARIANTS` + `ACCEPTANCE` + тесты `Axx.*` + `--gate pre_ci` |
| **2. Wave** | после `split_group` | API-smoke **затронутого** контура, не весь продукт |
| **3. Release** | перед staging/prod | `--gate pre_release` + полный product-smoke на staging |

CI — **второй** прогон unit-контура на чистой машине, не первая приёмка и не замена wave/release.

| Гейт | Что проверяет | Когда |
|---|---|---|
| **`pre_ci`** | реализацию задания: `Axx` и их связь с тестами (`@acceptance`, утверждение, не skip, файл в `PRODUCES`), module/app/eco, наличие `PRODUCES`, линт/типы/тесты → `evidence/Dxx.json` | после каждого задания, **до** push |
| **`acceptance`** (`--d Dxx` \| все) | связь фраз и тестов в строгом виде: текст фразы `Given/When/Then`, согласие `tests/test-plan-Dxx.md` с исходниками, нет висячих ссылок → `ACCEPTANCE.json` | после шага 09, в 10b и перед релизом |
| **`d-prompt-quality`** (`--batch N`) | само задание: `HOW`, `INVARIANTS` 5–12, `ACCEPTANCE` по уровню, `SIZE_BUDGET` (`size_ok`, `produces_count` ≤6, `surfaces` ≤2, `delivery_slice`), `PRODUCES` ≤6, валидность `CONTEXT_PACK`, отсутствие ярлыков неполноты (`MVP`, `PoC`, «пока без…», `v1` как статус) → `prompt-quality-batch-N.json` | при написании заданий, на каждую пачку ≤5 |
| **`baseline`** | R01: у каждого требования `MUST/SHALL` и ≥2 сценария (happy + negative/boundary) → `BASELINE.json` | после `R00`, перед `R02` |
| **`change`** | оформленное изменение: дельта `ADDED/MODIFIED/REMOVED`, ссылки на baseline, ≥2 сценария, обратная совместимость в `proposal.md`, 100% `tasks.md`, линт/тесты → `CHANGE-<id>.json` (`schema_version: 1`) | при изменении работающей системы |
| **`self-audit`** | шаг 10b: покрытие без строк без задания, `exit-criteria.md` с доказательствами, акты у `done` → `SELF_AUDIT.json` | перед переходом в brownfield |
| **`product-smoke`** | продукт как продукт: runbook + smoke-скрипт существуют и зелёные → `RELEASE-product-smoke.json` | релиз и демо |
| **`pre_release`** | агрегат: P0 `done` + `acceptance_ids`, coverage без `missing`, ноль CONFLICTS-blocker, ops у `L2/L3` → `RELEASE.json` | перед релизом |
| **`evidence-sync`** | сверка `progress.md` `done` ↔ наличие актов | аудит и CI-джоб |

**Почему гейтов несколько:** ошибка должна ловиться там, где возникла. Плохое задание дешевле
переписать до реализации, чем после.

```json
  "fit": {
    "acceptance_ids": ["A03.1", "A03.2", "A03.3", "A03.4", "A03.5", "A03.6"],
    "acceptance_source": "prompt",
    "depends_done": ["D01", "D02"],
    "conflicts_applied": [],
    "out_of_produces": [],
    "produces": ["src/events/log.py", "tests/events/test_log.py"]
  },
  "commands": [
    {"cmd": "npm run lint", "exit": 0},
    {"cmd": "npm run typecheck", "exit": 0},
    {"cmd": "npm test", "exit": 0}
  ],

  "tax_pass": true,
  "producer": "dev@example.com",
  "code_hash": {"git_head": "fed002a…", "git_dirty": false, "produces_digest": "sha256…"},

```

| Поле | Что означает по-человечески |
|---|---|
| `d` / `level` / `gate` | какое задание, насколько строго и на каком рубеже принимали |
| `scopes` | на какие четыре вопроса ответили «да» |
| `fit.acceptance_ids` | **вот эти конкретные утверждения** проверены; если список пуст или короче задания — работа не принята |
| `acceptance_source` | откуда взялись утверждения: из задания (`prompt`) или из изменения; на `pre_release` и `self-audit` список **сверяется с промптом** — акт от другой редакции задания не проходит |
| `depends_done` | зависимости действительно закрыты |
| `produces` / `out_of_produces` | что появилось и что появилось сверх обещанного (список считается `pre_ci` из `git status`; `tax_pass` от него не зависит — жёсткий гейт делает `sp doctor`) |
| `conflicts_applied` | какие заранее известные конфликты модулей применены |
| `commands` + `exit` | что реально запускали и с каким кодом |
| `commands_skipped` | `true` — акт снят структурно (`--skip-commands`, `--quick` или `L0`): линт, типы и тесты не гонялись. Такой акт виден в `pre_release`, и релиз его не принимает |
| `review` | акт кто-то прочитал: `verdict`, `reviewer`, чем кончилось. Для `L2+` без `supports` акта нет |
| `producer` / `code_hash` | кто создал акт и **какой именно код** он подтверждает (`produces_digest`) |
| `evidence_hash` | печать самого акта: тихая правка байтов ломает сверку |
| `tax_pass` | итог: налог уплачен |

Акт по изменению проще, потому что вопросы другие: `change_id`, `delta_valid`, `tasks_completed`,
`commands`, `issues`, `tax_pass`, `schema_version`.

`issues: []` означает «проблем не найдено», а не «мы не смотрели».

### 7.4.1 Сквозной пример: «событие не должно теряться»

Требование: «Агент делает шаги. Каждый шаг — запись в журнал. Журнал должен переживать падение
процесса. Событие сначала должно оказаться на диске, и только потом о нём узнают подписчики».

Из такого требования нельзя напрямую написать тест — слишком крупно. Его разбивают на фразы:

| ID | Фраза из задания | Что это значит по-человечески |
|---|---|---|
| `A03.1` | пустая папка разговора → сохранение события → файл существует, поля соответствуют справочнику | запись появляется и выглядит как договорились |
| `A03.2` | процесс убит после записи на диск, но до уведомления → после перезапуска событие читается с диска | если процесс умрёт в неудобный момент, событие не исчезнет |
| `A03.3` | в данных строка, похожая на токен → на диске `<secret_hidden>`, а не исходное значение | секрет не попадёт в журнал, даже если модель его туда положила |
| `A03.4` | записано 26 событий → читаем диапазон → не больше двух обращений к файлам | чтение истории не деградирует с ростом журнала |
| `A03.5` | два одновременных сохранения → два файла, разные идентификаторы, оба читаются | одновременная запись ничего не съедает |
| `A03.6` | сохранение без версии схемы → отказ до создания файла | битое событие не попадёт на диск |

Обратите внимание: каждая фраза — **сценарий**, а не свойство. Есть условие («что дано»), действие
(«что делаем») и наблюдаемый результат («что должно быть»). Именно поэтому фразу можно механически
превратить в тест.

**Как фраза становится тестом.** Самая неочевидная — `A03.2`. В тесте есть крючок: сразу после записи
на диск вызывается функция, которую тест подменяет на «падение». Дальше проверяется, что подписчик
**ничего не получил** (уведомление действительно после записи), и что «перезапущенный» журнал читает
событие с диска. Тест проверяет ровно ту фразу, которая написана в задании, — не «сохранение
работает», а «порядок действий правильный и потеря невозможна».

**Что делает приёмщик** на этом примере: открывает задание и выписывает все `A03.1…A03.6`; проверяет,
что каждая фраза объявлена тестом (`@acceptance A03.k` или ID в имени), что тест не пустой и не
пропущен и что файл теста заявлен в `PRODUCES`; сверяет `tests/test-plan-D03.md` с исходниками;
запускает линтер, типы и тесты; пишет акт с отпечатком связи (`binding_hash`). Никакого «понимания
кода» здесь нет — и это честно написано.

**Что читает человек в акте** (пять конкретных вещей):

1. список фраз совпадает с заданием — не «6 из 6 по количеству», а именно те фразы;
2. `out_of_produces` пуст — не появилось файлов «заодно»;
3. `depends_done` — правда, а не «я знаю, что там всё работает»;
4. `commands` — те команды: линтер, типы и тесты реально были в списке;
5. для `L2/L3` — `ops_checked` не пуст, внешний контракт действительно трогали.

И главный вопрос, который не формализуется: **тест правда проверяет эту фразу?** Акт доказывает, что
у фразы есть исполняемое утверждение в заявленном файле, что ссылка не висит в пустоте и что фразу
не переписали после приёмки. Совпадение смысла теста и фразы знает только человек, прочитав тест.

| Без механики | С механикой |
|---|---|
| тест «сохранение не падает» — зелёный | тест «падение после записи не теряет событие» — зелёный |
| через месяц никто не помнит, проверялась ли устойчивость | в акте написано, что проверялась и каким тестом |
| потеря события обнаруживается в проде | обнаруживается на приёмке |
| «готово» — это мнение | «готово» — файл с шестью фразами и тремя командами |

#### Fail-closed: «не понял» не значит «пропустил»

Правило действует с v1.24 и относится ко всем гейтам сразу. Раньше проверка, которая не смогла
разобрать вход, молча возвращала «ок»: строка `done ✅` выпадала из `progress.md`, и `pre_release`
проходил при нуле выполненных заданий; glob `src/**/*.ts` не совпадал с `src/index.ts`; пустое поле
`conflicts_ref` считалось ошибкой, а `D01-D02` в `depends_done` — словом «нет». Теперь наоборот:

- гейт, который не разобрал строку, статус, пару `METHOD /path`, glob или акт, **падает**, а не
  возвращает «ок»;
- один разбор на всю фабрику: `progress.md` читает `progress-lib.mjs`, glob и служебные префиксы —
  `evidence-lib.mjs`, поэтому `sp doctor`, `sp`, `sp-verify` и `pre_release` не расходятся;
- «быстрый» прогон `--skip-commands` законен, но оставляет след `commands_skipped: true`, и релиз
  такой акт не принимает;
- релизные акты (`product-smoke`, `runtime`) проверяются теми же правилами, что и акты заданий:
  печать, `code_hash`, привязка к скрипту и плану. Файл из 18 байт `{"tax_pass": true}` актом не является.

Цена правила — ложные провалы на нестандартной разметке. Это осознанный выбор: ложный провал виден
и исправляется, ложный пропуск выглядит как зелёный релиз.

Честные пределы: программа **не читает смысл фразы** и потому **не доказывает совпадение смысла
теста и фразы**. Связь с v1.27 проверяется машинно, но по форме: фраза объявлена тестом
(`@acceptance Axx.k` или ID в имени), тест содержит утверждение, не пропущен, лежит в `PRODUCES`,
а отпечаток фразы (`binding_hash`) не даёт переписать формулировку после приёмки. «Тест-пустышка»
(`expect(true).toBe(true)`) по-прежнему формально проходит: машинно отличить проверку результата
от проверки константы нельзя.

Отсюда обязательный шаг «прочитать акт и тест глазами». Автоматика без человека даёт «формально
зелёное», человек без автоматики — «доверься мне». Машина проверяет, что проверки **были**; человек —
что они **осмысленные**.

**Предел хешей.** `evidence_hash` ловит тихую случайную правку, но не того, кто пересчитает хеш.
Настоящий якорь — git: `produces_digest` считается по **раскрытым** файлам `PRODUCES` (glob
превращается в конкретные пути), а `--verify-evidence` дополнительно требует, чтобы закоммиченный
акт не был изменён в рабочем дереве. `git_head` — только факт «на каком коммите писался акт» и не
сравнивается с текущим `HEAD`: коммит самого акта сдвигает `HEAD`, и равенство обнуляло бы печать.
Незакоммиченный акт — законный черновик, но не якорь: поле `committed` в выводе проверки говорит,
подтверждён ли он историей. Review доказывает, что акт прочитали и подтвердили именно этот код, а не
компетентность ревьюера: независимость проверяется по `reviewer ≠ producer`, а имя ревьюера —
самодекларируемая строка, не подпись.

**Предел инвариантов.** Селектор детерминированный (`module` + уровень), не «умный»: ложное
применение правила хуже пропуска. Применение видно в акте (`fit.invariants`), пропуск разбирает человек.

**Runtime: план, а не надежда.** Фабрика не угадывает чужой стек — она выводит окружение из своих
же входов прогона. На шаге 08 `architecture`, `04_data_and_api`, `nfr`, `env-vars` и `01_contract.md`
переписываются в **`OUTPUT/runtime/runtime-plan.json`**: `stack`, `up[]` с условием готовности
(`ready` — http или cmd, не `sleep`), `seed[]` (идемпотентный), `down[]` и `verify[]` — по записи
на каждую фразу `Axx.k`. Плейсхолдеры `{{...}}` и `TODO` запрещены: план — исполняемый контракт.

`sp-verify --gate runtime-plan` проверяет план статически: нет заглушек, teardown есть, метки не
фантомные (сверка с `01_contract.md`), и **каждая принятая фраза** либо проверяется `cmd`, либо
снята через `na` с причиной. Непокрытая принятая фраза — провал: значит рантайм не подтверждает
то, что фабрика уже приняла.

`sp-verify --gate runtime` **исполняет** план: поднимает `up[]`, ждёт `ready` поллингом, гоняет
`seed[]`, выполняет `verify[]` по фразам, пишет логи в `OUTPUT/evidence/trace/`, **всегда** снимает
`down[]` и пишет `OUTPUT/evidence/RELEASE-runtime-verify.json` с результатом по каждой фразе.
Если внешнего трейса нет, фабрика **порождает** `Dxx.trace.json` с `commit`, `code_hash`,
`captured_at` и `produced_by.plan_hash`. `pre_release` требует исполненный акт, если план существует.

**Что это меняет и чего не меняет.** Раньше трейс был только внешним артефактом, который можно
подделать формой; теперь прогон, который фабрика делает сама, привязан к коммиту, к хешу `PRODUCES`
и к номеру фразы. Предел остался один и он не про инфраструктуру, а про оракул: `verify[]` —
это команды проекта, и фабрика доказывает «команда прогнана на этом коде и вернула этот код выхода»,
а не «поведение правильно». Оракул задаёт контракт и тесты, удостоверение честности — CI заказчика.
`coverage_confidence` по-прежнему **оценка покрытия доказательствами**, а не доказательство
корректности, и не отменяет ни одного гейта.

**Lite-режим** (`Режим прогона: lite` в `MANIFEST.md` или `SP_LITE=1`) не отменяет акт: он снимает
требование `coverage-matrix.md` и `exit-criteria.md` у `self-audit`/`pre_release` и разрешает
`spec-packet` вместо полного промпта. `tax_pass` остаётся обязательным.

### 7.6 Признаки фиктивной проверки

| Признак | Что на самом деле произошло |
|---|---|
| Список фраз пустой | тесты писались «как получилось», акт ничего не доказывает |
| Фразы размытые («работает корректно») | проверить нельзя, значит и не проверяли |
| У тестов нет номеров фраз | связь «требование → проверка» потеряна: `pre_ci` теперь падает на «фраза без теста» |
| Тест объявил фразу, но ничего не утверждает | пустая связь: `pre_ci` падает на «утверждения в нём нет» |
| Фразу переписали под уже написанный тест | `binding_hash` в акте не сходится, `pre_release` требует новый `pre_ci` |
| Для `L2/L3` `ops_checked` пуст | внешний контракт не трогали, задание про API не проверено |
| В акте «проверено вручную» | ручная проверка не воспроизводится |
| Все тесты зелёные с первого раза после крупного рефакторинга | подозрительно: скорее всего, ничего не проверяют |
| Задача закрыта, а файлов из `PRODUCES` нет | «сделано» на словах |
| `tax_pass: true` при `acceptance_ids` короче задания | акт формально зелёный — читать глазами |

### 7.6.1 Ошибка → правило

Повторяющиеся ошибки не лечатся напоминанием в чате. Они превращаются в правило:

1. пункт в `.cursorrules`, чтобы ошибка не повторялась автоматически;
2. ужесточение чек-листа конкретного модуля (добавили фразу, которую раньше не проверяли);
3. регрессионный тест на конкретный случай.

Примеры: «агент для проверки сам пересобирал образы и ронял стенд» → жёсткий запрет на сборку без
явной команды; «редактирование email ломало сценарии с почтой» → отдельный флаг + тест на сценарий;
«ввод в браузере залипал после редиректа на недоверенный домен» → автоснятие блокировки при возврате
на доверенный + тест. Смысл: процесс учится, а не «мы постараемся быть внимательнее».

### 7.7 Двумерная полнота

| Механизм | Вопрос | Требование |
|---|---|---|
| **Матрица покрытия** | каждое требование превратилось в задание? | 0 пропусков: требование → метрика → задание |
| **Критерии завершения** (`E1…En`) | продукт ведёт себя как продукт? | каждое условие проверяемо и имеет доказательство |

Матрица — «все позиции в накладной есть в коробках», критерии — «каждая вещь работает после
сборки». Первое без второго даёт полную коробку нерабочих деталей.

### 7.8 Дымовые прогоны

| Уровень | Что проверяет | Чем |
|---|---|---|
| wave | затронутый контур после группы заданий | `scripts/smoke/wave-api-smoke.sh` |
| product | продукт целиком по сценариям пользователя | `scripts/smoke/product-smoke.sh` + `OUTPUT/docs/runbooks/product-smoke.md` |
| release | всё вместе на staging | тот же runbook на стенде + `--gate pre_release` |

Смысл: проверяется не «функция», а **контур** — связка «команда → событие → разрешение → ответ».

### 7.9 Порядок проверки по шагам

| Шаг | Что делается | Зачем именно так |
|---|---|---|
| **0. До кода — выписать фразы и проверить вход** | `Axx`, зависимости приняты, `PRODUCES` осмысленный, контракты существуют | фразы, написанные после кода, всегда описывают то, что получилось |
| **1. Код и по тесту на каждую фразу** | не «тесты в целом», а один тест — одна фраза | единственная связь между требованием и машинной проверкой |
| **2. Дешёвые проверки первыми** | линтер → типы → тесты | каждый следующий шаг дороже; тот же порядок в CI, чтобы результаты не расходились |
| **3. Программа приёмки** | выписывает фразы, проверяет связи, гоняет команды, пишет акт | решение «достаточно ли сделано» перестаёт быть вкусовым |
| **4. Чтение акта глазами** | сверка списка фраз, `out_of_produces`, `depends_done`, `commands`, `ops_checked` | программа видит форму, а не смысл |
| **5. Статус и стоп** | `done` или `needs_rework`, следующий D не начинается | следующая задача опирается на контракты этой |
| **6. Срез закрыт — проверка среза** | короткий сценарий по узлу: «записать, прочитать, воспроизвести» | по отдельности модули работают, вместе — нет; но полный e2e после каждой задачи слишком дорог и его перестанут запускать |
| **7. Деньги, квоты, бухгалтерия — человек** | 5–10 осознанных кликов или скриптовый API-smoke только затронутых операций | ошибку в списании нельзя ловить «в проде» |
| **8. Перед релизом — всё вместе на стенде** | `pre_release` + полный product-smoke | локальные проверки не воспроизводят сеть, браузер, кластер |
| **9. Изменение поведения — отдельная приёмка** | `change`-гейт: дельта, задачи, тесты, совместимость | изменение — обещание; расхождение кода и описания делает архив лживым |
| **10. Аудит всей системы доказательств** | `self-audit`: акты, покрытие, критерии, риски | можно аккуратно закрыть каждую задачу и получить продукт с дырой в покрытии |

### 7.10 CLI `sp-tools`

Из корня проекта CLI всегда доступен по `witness-done/SEED/sp-tools/` (копия в `scripts/sp-tools/`
не нужна — DEC-034). Что делает каждая команда и что значит каждый аргумент:

```bash
# --- вход и маршрут ---------------------------------------------------------
# status: где стоит проект. Без аргументов.
node witness-done/SEED/sp-tools/sp.mjs status                    # где стоит проект

# intake: запись входа. "…" — запрос дословно (обязателен).
node witness-done/SEED/sp-tools/sp.mjs intake "Добавь экспорт отчёта в CSV"

node witness-done/SEED/sp-tools/sp.mjs next                      # маршрут из последней записи

# decide: решение в журнал. "…" — формулировка (обязателен),
#         --intake <ID> — к какой записи привязать.
node witness-done/SEED/sp-tools/sp.mjs decide "Экспорт только CSV" --intake <ID>

# close: закрыть запись входа. <ID> — имя файла intake без .md,
#        --ref <…> — DEC-001 | D01 | <change-id>.
node witness-done/SEED/sp-tools/sp.mjs close <ID> --ref DEC-001

node witness-done/SEED/sp-tools/sp.mjs rules --sync              # адаптеры IDE из AGENTS.md
node witness-done/SEED/sp-tools/sp.mjs doctor --strict           # гейт входа; предупреждения = провал

# --- приёмка ----------------------------------------------------------------
# --d D01          — задание из OUTPUT/prompts/ (для pre_ci обязателен)
# --gate <имя>     — какой гейт запускать (обязателен)
# --skip-commands  — без линта/тестов, только структура
# --batch <n>      — номер пачки заданий (≤5 за раз)
# --change <id>    — пакет изменения spec-state/changes/<id>/
# --budget-min <n> — бюджет прогона плана рантайма, минуты (по умолчанию 30)
node witness-done/SEED/sp-tools/sp-verify.mjs --d D01 --gate pre_ci          # принять задание D01
node witness-done/SEED/sp-tools/sp-verify.mjs --gate acceptance [--d D01]     # связь «фраза ↔ тест» + test-plan
node witness-done/SEED/sp-tools/sp-verify.mjs --gate d-prompt-quality --batch 1  # качество пачки №1
node witness-done/SEED/sp-tools/sp-verify.mjs --gate self-audit               # самопроверка 10b
node witness-done/SEED/sp-tools/sp-verify.mjs --gate baseline                 # базовый набор R01
node witness-done/SEED/sp-tools/sp-verify.mjs --gate product-smoke            # смоук продукта
node witness-done/SEED/sp-tools/sp-verify.mjs --gate runtime-plan             # план подъёма/проверки: статика
node witness-done/SEED/sp-tools/sp-verify.mjs --gate runtime                  # подъём → проверки → teardown
node witness-done/SEED/sp-tools/sp-verify.mjs --gate pre_release              # готовность к релизу
node witness-done/SEED/sp-tools/sp-verify.mjs --gate evidence-sync            # сверка progress ↔ evidence
node witness-done/SEED/sp-tools/sp-verify.mjs --change <id> --gate change     # принять изменение

# --- контекст ---------------------------------------------------------------
# --reindex                 — перестроить индекс OUTPUT/ и spec-state/
# --d D03 --validate        — проверить существующий pack (не создаёт его)
# --query "…" --out <path>  — собрать pack по запросу в файл
node witness-done/SEED/sp-tools/sp-retrieve.mjs --reindex                     # перестроить индекс
node witness-done/SEED/sp-tools/sp-retrieve.mjs --d D03 --validate            # проверить pack для D03
node witness-done/SEED/sp-tools/sp-retrieve.mjs --query "JWT auth middleware" --out OUTPUT/context/packs/P-draft.md  # собрать pack
```

- `sp` — вход и маршрут: `status`/`intake`/`next`/`decide`/`close`, генерация и проверка адаптеров
  правил (`rules`), гейт входа (`doctor`). `sp verify …` и `sp retrieve …` делегируют в соседние CLI,
  чтобы не появился третий интерфейс.
- `sp-verify` — приёмщик: парсит задание, выписывает фразы, проверяет связи, гоняет линт/типы/тесты,
  пишет акт. `--skip-commands` оставляет только структурные проверки.
- `sp-retrieve` — сборка и валидация context packs. `--validate` **не создаёт** pack: отсутствующий
  pack — это явная ошибка (exit 2), иначе проверка доказывала бы сама себя.
- Чистый Node ≥18, без npm-пакетов. Коды `sp`: `0` ok, `2` провал, `3` нужен человек.
  Подробности — `SEED/sp-tools/USAGE.md`.

## 8. Brownfield: эволюция спецификаций

### 8.1 Зачем второе описание

После первого этапа есть артефакты «как задумывали». Продукт живёт дальше, и появляется второй
вопрос — «как работает сейчас». Если хранить только замысел: новый участник видит расхождение кода и
описания и «чинит» код, ломая историческое поведение; через полгода непонятно, какое описание верное;
решение «почему так» потеряно и принимается заново — обычно хуже.

```
spec-state/
  baseline/<домен>/spec.md      ← что действует сейчас
  changes/<id>/
    proposal.md                 ← какая проблема и что предлагаем
    design.md                   ← как именно меняем
    tasks.md                    ← задачи + чем докажем
    specs/<домен>.md            ← что именно меняется в требованиях
  archive/YYYY-MM-DD-<id>/      ← применённые изменения
```

Baseline — не «краткое описание», а набор проверяемых требований, по которым можно писать тесты.

### 8.2 R00 — описать существующее «как есть»

Цель — снять снимок, а не улучшить. Правила:

- факт берётся из кода, конфигурации или теста; неоднозначное помечается «нужен человек», а не
  «наверное, имелось в виду»;
- фиксируются **наблюдаемые** вещи: имена событий, поля, коды выхода, пути, схемы;
- расхождения «код против исходной спецификации» выписываются отдельно — это риски и долги;
- запрещено «причёсывать»: снимок должен быть правдой, даже если правда некрасивая.

**Проверка:** каждый домен имеет модуль-владельца; неясности перечислены; выдуманных требований нет.

### 8.3 R01 — записать требования

```markdown
### Requirement: EventLog append-only persist-before-dispatch
Система MUST сохранять событие до уведомления подписчиков.
Компонент SHALL соответствовать OUTPUT/specs и TECH_SPEC §… .

#### Scenario: happy path
- GIVEN валидный GroupContext и зависимости домена
- WHEN выполняется основной сценарий домена `events`
- THEN add_event writes file before notify

#### Scenario: negative / boundary
- GIVEN нарушены предусловия контракта
- WHEN операция вызывается
- THEN система MUST отклонить действие без нарушения SoT / без утечки секретов
```

Правила:

- **MUST/SHALL** — обязательное, **SHOULD** — желательное; формулировки проверяемые;
- у каждого требования минимум **два** сценария: обычный и плохой/граница. Требование без плохого
  сценария почти всегда означает, что про отказ не подумали;
- исторические особенности фиксируются **явно** (пример: «для бота `main` использовать
  `conversation_id = ui-main`») — это контракт совместимости, и без записи его «починят»;
- baseline — исполнимые требования, а не пересказ: по ним пишутся тесты.

Инструмент: `sp-verify --gate baseline` → `evidence/BASELINE.json`.

### 8.4 R02 — предложить изменение

**Главное правило:** изменение начинается с **проблемы**, а не с решения. «Давайте добавим
планировщик» — это решение в поисках проблемы.

Что обязано быть в `proposal.md`:

| Пункт | Зачем |
|---|---|
| Проблема с наблюдаемым симптомом | иначе непонятно, что улучшаем |
| Механика решения (а не лозунг) | «сделаем лучше» нельзя проверить |
| Обоснование против альтернатив | показывает, что думали, а не угадали |
| **Обратная совместимость** (Backwards Compatibility) | что будет со старыми данными, событиями, клиентами |
| **Трассировка** на baseline/задания | видно, какие требования и как меняются |
| **Что не делаем (Non-goals)** | защита от расползания |
| Риски и способы их поймать | риск без владельца — это сюрприз |

Изменения требований пишутся тремя операциями:

- **ADDED** — новый блок требования целиком;
- **MODIFIED** — блок **заменяется целиком**, а не патчится в три слова;
- **REMOVED** — с причиной.

**Почему полная замена, а не дифф:** при мелких правках через два изменения никто не соберёт итоговый
текст. Полная замена позволяет собирать действующее описание **механически**.

`design.md` отвечает «как именно»: новые поля событий, совместимость со старыми данными, порядок
миграции, влияние на воспроизведение (старые события должны читаться!), влияние на кэш модели,
влияние на интерфейс.

`tasks.md` — задачи по волнам, **каждая привязана к утверждению**:

```markdown
## S1 — ядро
- [x] 1.1 Учёт занятости ресурсов — R1
- [x] 1.2 Убрать очередь при свободных ресурсах — R2
- **A1.1** R1: текстовая задача проходит рядом с браузерной
- **A1.2** R2: второй браузер ждёт освобождения
- **A1.3** R3: освобождение → ожидающая допускается
```

Привязка `Axx.k` / `Rxx` проверяется гейтом `change`: задача без утверждения — это «сделали и
надеемся».

### 8.5 R03 — применить

- код и тесты строго по дизайну и дельте; **никаких** «заодно улучшил»;
- каждое изменение поведения сопровождается событием или тестом; новое событие сначала в реестр, потом
  в код;
- старые данные должны читаться: воспроизведение старых разговоров не падает;
- если выяснилось, что дизайн неверен — **остановка**, правка `proposal.md`/`design.md`. Не «тихая»
  реализация «как получилось».

### 8.6 R04 — проверить

```bash
# sp-verify --change <id> --gate change — принять пакет изменения.
#   --change <id> — каталог spec-state/changes/<id>/ (обязателен для гейта change)
#   --gate change — гейт R04; его имя фиксировано, других значений для пакета нет
node witness-done/SEED/sp-tools/sp-verify.mjs --change <id> --gate change
```

| Что проверяется | Смысл |
|---|---|
| `delta_valid` | изменения требований корректны и применимы |
| ≥2 сценария на требование | про отказ подумали |
| ссылки на baseline | изменяемое требование существует |
| обратная совместимость в `proposal.md` | старые данные и клиенты не забыты |
| чеклист `tasks.md` 100% | «почти готово» не существует |
| линт / типы / тесты | зелёные |
| `schema_version: 1` | акт читается машиной |

**Выход:** `OUTPUT/evidence/CHANGE-<id>.json` с итогом «налог уплачен». Без акта изменение не
архивируется.

### 8.7 R05 — влить в действующее описание

1. Перенести дельту в baseline: ADDED — добавить, MODIFIED — заменить блок, REMOVED — убрать.
2. Переместить пакет в `spec-state/archive/YYYY-MM-DD-<id>/`.
3. Переиндексировать поиск: `sp-retrieve --reindex` — чтобы следующие изменения видели актуальное
   описание.
4. Обновить `MANIFEST` и `OUTPUT/roadmaps/progress.md`.
5. Записать уроки: что оказалось сложнее, что учесть в следующий раз.

**Проверка:** описание собирается без противоречий, поиск находит новые требования, архив полный
(предложение + дизайн + задачи + дельта).

### 8.8 Как отвечать на «зачем так сложно»

> «Сложность здесь дешевле, чем её отсутствие. Без описания действующего поведения каждый новый
> исполнитель переоткрывает поведение по коду и ломает исторические контракты, потому что они нигде
> не записаны. Без описания изменения решение живёт в голове автора и умирает вместе с его памятью.
> Без формальной проверки "готово" — вопрос веры.
>
> Мой процесс стоит один документ с проблемой и один прогон тестов на изменение. Цена ошибки без него
> — регрессия в проде и потерянная причина решения».

## 9. Профили проектов

Профиль — **набор акцентов под тип продукта**, а не «все модули сразу». Выбирается на шаге 00 и
записывается в `OUTPUT/MANIFEST.md` (поля `Профиль` и `Отклонения от профиля`). Можно сузить скоуп,
нельзя молча расширять `OUT OF SCOPE`.

| Профиль | Акцент | Что обязательно поднимается |
|---|---|---|
| `agent-harness` | агенты, инструменты, оркестрация | журнал событий append-only / persist-before-dispatch; контракты инструментов; подтверждения человеком (`L3`); воспроизводимость; изоляция прав и лимитов |
| `web-app` | API, роли, интерфейс, админка | auth, RBAC, валидация на границах, UI-задания по `design-notes.md` |
| `data-platform` | пайплайны, хранилище, аналитика | идемпотентность, расписания, качество данных, отчёты |
| `custom` | ни один не подходит | акценты перечисляются в ТЗ; отклонения обязательны |

Профиль наследует верификацию полностью: `pre_ci`, wave-smoke, `pre_release` + product-smoke.
Подробный выбор модулей — [`PROFILES.md`](PROFILES.md).

## 10. Все команды управления

Полный список того, чем вообще управляется Witness Done. Ниже — все точки входа: скрипты,
подкоманды `sp`, приёмщики, гейты автоматики и слэш-команды. Сокращённый вариант для работы —
§11 «Полный перечень команд».

Общие правила для всех команд:

- Запуск — из корня проекта (где лежит `witness-done/`) или из корня фабрики.
- `--root <путь>` — где проект, `--factory <путь>` — где канон. По умолчанию `root` = текущий
  каталог, `factory` = `<root>/witness-done`, а если его нет — каталог самого скрипта.
- `--help` у любого CLI печатает справку и выходит с кодом `0`.
- Пути к CLI записываются как `<FACTORY_PATH>/SEED/sp-tools/…`. В обычном проекте это
  `witness-done/SEED/sp-tools/…`, в самом репозитории фабрики — `SEED/sp-tools/…`.

### 10.1 Скрипты в корне фабрики

| Команда | Аргументы | Что делает | Код |
|---------|-----------|-----------|-----|
| `./run.sh` | нет | Находит свой корень, печатает раскладку (`ROOT`, проект, `OUTPUT/`) и маршрут первого шага. Ничего не меняет и ничего не пишет | `0` |
| `./validate.sh` | нет; переменная `SP_SKIP_SELFTEST=1` отключает внутренний selftest | Проверка целостности **канона**: структура, шаблоны, CLI, единственность `ORCHESTRATOR.md`, чистота поставки, наличие протокола входа, синхронность адаптеров. Запускает `selftest.sh` | `0` / `1` |
| `bash SEED/sp-tools/selftest.sh` | нет | Самопроверка `sp` на одноразовых фикстурах во `/tmp`: классификация входа, код `3`, правила и адаптеры, `doctor`, `update`, режим канона, полный цикл. Репозиторий не трогает | `0` / `1` |
| `SP_SKIP_SELFTEST=1 ./validate.sh` | переменная окружения, не флаг | То же, но без прогона selftest (быстрая проверка при правке документации) | `0` / `1` |

`validate.sh` проверяет канон, а `sp doctor` — прогон в проекте. `doctor` сам различает контекст:
если `--root` совпадает с фабрикой и прогон не начат (`MANIFEST` нет), он проверяет **канон**
(адаптеры, пустой `OUTPUT/`, `VERSION`, `SEED/update.json`, единственность `ORCHESTRATOR.md`)
и печатает `doctor: ok — корень канона`.

### 10.2 `sp` — единая точка входа

```bash

```

Обзор. Разбор каждой подкоманды — ниже, в 10.2.1–10.2.13.

| Подкоманда | Что делает | Код |
|-----------|-----------|-----|
| `status` | Где стоит проект: `MODE`, шаг, прогресс `D`, журнал, открытые записи входа, активные changes, `done` без акта, версия фабрики | `0` |
| `intake` | Создать запись входа `journal/intake/<ID>.md` с классификацией и маршрутом `next:` | `0` / `1` / `3` |
| `next` | Показать маршрут из последней открытой записи входа | `0` |
| `decide` | Добавить `DEC-###` файлом в `journal/decisions/` и пересобрать индекс | `0` / `1` / `2` |
| `close` | Закрыть запись входа ссылкой на артефакт | `0` / `1` / `2` |
| `journal` | Журнал проекта: init, index, check, list, migrate | `0` / `2` |
| `review` | Review-артефакт акта: `evidence/Dxx.review.json` | `0` / `1` / `2` |
| `progress` | Сборка `progress.md` из фрагментов `progress.d/` | `0` / `2` |
| `feedback` | `feedback.md` / `feedback-lite.md` + `coverage_confidence` | `0` / `2` |
| `rules` | Показать / пересобрать / сверить адаптеры IDE из `AGENTS.md` | `0` / `2` |
| `doctor` | Гейт входа: правила, записи, акты, изменённые файлы, границы | `0` / `2` |
| `update` | Сверить `VERSION` с версией в репозитории | `0` / `2` / `3` |
| `verify …` | Делегирование в `sp-verify.mjs` | как у приёмщика |
| `retrieve …` | Делегирование в `sp-retrieve.mjs` | как у retrieve |

Общие флаги (работают с любой подкомандой):

| Флаг | Значение | По умолчанию |
|------|----------|--------------|
| `--root <путь>` | Корень проекта: откуда читаются `INPUT/`, `spec-state/` и код; `OUTPUT/` ищется в `FACTORY_PATH` (не в `--root`) | текущий каталог |
| `--factory <путь>` | Корень канона: откуда берутся `SEED/`, `TEMPLATES/`, `catalogs/` | `<root>/witness-done`, иначе каталог скрипта |
| `--json` | Машинный вывод вместо человекочитаемого | выкл. |
| `--help`, `-h` | Справка и выход с кодом `0` | — |

#### 10.2.1 `status` — где стоит проект

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs status [--json]
```

**Что делает.** Только читает файлы, ничего не пишет и в сеть не ходит. Собирает: `PROJECT_ROOT`,
`FACTORY`, `MODE` (greenfield / brownfield / «прогон не начат»), профиль, `last_completed_step`,
прогресс `D`, открытые записи входа (`ID` и `kind`), активные `spec-state/changes/*`, задачи `done`
без акта в `evidence/`, `VERSION` фабрики и статус обновления **из кэша**.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--json` | нет | Вернуть тот же набор полей объектом JSON — для скриптов и CI |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs status
# PROJECT_ROOT: /app
# FACTORY: /app/witness-done
# MODE: greenfield
# last_completed_step: 04
# Следующий шаг: PIPELINE/05_security.md
```

**Когда использовать.** Первым делом в любой сессии и перед `intake`: не заведена ли уже запись
по тому же запросу. Код `0` всегда, даже если прогон не начат — это справка, а не проверка.

#### 10.2.2 `intake` — запись входа

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs intake "<запрос дословно>" [--kind …] [--source …]
```

**Что делает.** Создаёт файл `journal/intake/<YYYYMMDD-HHMM>-<slug>.md`: запрос цитатой, снимок
состояния (`MANIFEST`, шаг, открытые changes), `kind` с обоснованием, поле `next:` с маршрутом.
Классификация детерминированная — не «модель решила», поэтому повтор на том же состоянии даёт тот
же ответ. `kind` не меняет ни один файл продукта: это запись, а не действие.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `"<запрос дословно>"` | да | Текст запроса как его сформулировал человек. Не пересказ и не «причёсанная» версия: по нему восстанавливается намерение |
| `--kind <new\|question\|change\|task\|bugfix>` | нет | Задать классификацию вручную. Нужен, когда CLI вернул `3` (неоднозначно) или когда контекст знает человек, а не эвристика |
| `--source <chat\|issue\|doc>` | нет | Откуда пришёл запрос. `chat` — по умолчанию (разговор), `issue` — задача из трекера, `doc` — из документа. Попадает в запись для трассировки |

`kind` — что означает каждое значение:

| `kind` | Когда ставится | Куда ведёт `next:` |
|--------|----------------|--------------------|
| `new` | прогон не начат (`MANIFEST` нет) | `PIPELINE/00_bootstrap.md` |
| `question` | вопрос без глагола изменения | ответ по артефактам + `sp decide` |
| `change` | есть открытый change или режим brownfield | `R02_propose_change.md` |
| `bugfix` | дефект в уже принятом поведении | `R02` с причиной в `proposal.md` §1 |
| `task` | в тексте `Dxx` и режим greenfield | `OUTPUT/prompts/Dxx_*.md` |

В корне канона (`--root` = фабрика, `MANIFEST` нет) прогона не существует, поэтому любой запрос
получает `change` с маршрутом «правка канона → `./validate.sh`», а не `new` → `PIPELINE/00`.

**Пример.**

```bash
# обычный вызов: классификация автоматическая
node witness-done/SEED/sp-tools/sp.mjs intake "Добавь экспорт отчёта в CSV"
# Wrote journal/intake/20261028-1200-dobav-eksport-otcheta-v-csv.md
# kind: change (есть незакрытое изменение: add-report-export)
# next: PIPELINE/R02_propose_change.md (id изменения: dobav-eksport-otcheta-v-csv)

# --kind question — вопрос; --source issue — пришёл из трекера
node witness-done/SEED/sp-tools/sp.mjs intake "Можно ли X?" --kind question --source issue
```

**Коды.** `0` — запись создана; `3` — форма вопроса и глагол изменения одновременно: CLI печатает
два варианта и требует `--kind`, чтобы человек выбрал, а не угадывал агент; `1` — пустой текст
запроса или неизвестное значение `kind`.

#### 10.2.3 `next` — маршрут

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs next
```

**Что делает.** Печатает `next:` из последней открытой записи входа. Если открытых записей нет —
берёт точку возобновления из `OUTPUT/MANIFEST.md` (`last_completed_step`, `wave`, `c_subwave`).
Аргументов нет: маршрут — это факт из файлов, а не параметр.

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs next
# next: PIPELINE/R02_propose_change.md (id изменения: add-report-export)
```

**Зачем отдельно от `intake`.** Между «записал» и «начал работать» агент обязан показать маршрут
человеку. `next` можно вызвать повторно в любой момент — он ничего не меняет.

#### 10.2.4 `decide` — журнал решений

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs decide "<решение>" [--intake <ID>] [--adr ADR-000N]
```

**Что делает.** Создаёт файл `journal/decisions/DEC-###-<slug>.md` (одна запись — один файл) и
пересобирает индекс `journal/decisions.md`. Номер берётся как max+1 по локальным файлам **и** по
`origin/main`, поэтому две ветки не получат один `DEC-###`. С `--intake` проставляет `DEC-###`
в поле «связано» этой записи входа. Решение фиксируется **до**
кода: потом поздно объяснять, почему выбрали так.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `"<решение>"` | да | Формулировка выбора в утвердительной форме: что решили и почему. Не «может быть, CSV», а «экспорт только CSV: XLSX не просили» |
| `--intake <ID>` | нет | ID записи входа (`20261028-1200-…`), к которой привязать решение. Проверяется, что запись существует |
| `--adr ADR-000N` | нет | Связать решение с архитектурной записью из `OUTPUT/docs/adr/`, если решение архитектурное |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs decide "Экспорт только CSV: XLSX не просили" --intake 20261028-1200-dobav-eksport
# Wrote journal/decisions/DEC-001-<slug>.md → DEC-001
```

**Коды.** `0` — записано; `1` — не передан текст решения; `2` — указанный `--intake` не найден.

#### 10.2.5 `close` — закрыть запись входа

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs close <ID> --ref <change-id|Dxx|DEC-###>
```

**Что делает.** Ставит в записи входа `статус: closed` и ссылку на артефакт. Перед этим проверяет,
что артефакт существует: для `Dxx` — `OUTPUT/evidence/Dxx.json`, для `DEC-###` — файл в `journal/decisions/`,
для `<change-id>` — каталог `spec-state/changes/<id>/`. Закрыть «просто так» не получится: ссылка —
это и есть доказательство.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `<ID>` | да | ID записи входа — имя файла в `journal/intake/` без `.md`. Достаточно уникального префикса (например `20261028-1200`) |
| `--ref <…>` | да | На что ссылается запись: `DEC-001` (решение в журнале), `D01` (акт приёмки задания), `add-user-avatar` (пакет изменения) |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs close 20261028-1200-dobav-eksport --ref add-report-export
# closed 20261028-1200-dobav-eksport → add-report-export
```

**Коды.** `0` — закрыто; `1` — не передан `<ID>`; `2` — нет `--ref`, записи или артефакта.
Слово «готово» без закрытой записи и акта в каноне не существует.

#### 10.2.6 `journal` — журнал проекта

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs journal [--init] [--index] [--check [--strict]] [--list] [--limit N] [--migrate]
```

**Что делает.** Управляет коммитируемым журналом `<project>/journal`: `intake/`, `decisions/`,
`decisions.md`. Без флагов печатает сводку: сколько решений, какие записи входа открыты.
В корне канона журналом считается `.witness-done-work/` — тот же CLI, но вне git.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--init` | один из режимов | Создать `journal/` из заготовки `SEED/journal/`. Идемпотентно: существующее не трогает |
| `--index` | один из режимов | Пересобрать `journal/decisions.md` из `decisions/*.md`. Единственный способ править оглавление |
| `--check` | один из режимов | Дубли `DEC-###`, заголовок ≠ имени файла, ссылки на несуществующие записи, открытый intake без `next:`, дрейф индекса, незакоммиченный журнал |
| `--strict` | нет, с `--check` | Предупреждения считать провалом (режим CI) |
| `--list` | нет | Список: последние решения и открытые записи входа |
| `--limit <n>` | нет | Сколько последних решений показать, по умолчанию `10` |
| `--migrate` | один из режимов | Перенести старый журнал из `OUTPUT/intake/` и `OUTPUT/docs/decisions.md` в `journal/` |

**Пример.**

```bash
# создать журнал в проекте (делает и шаг 00)
node witness-done/SEED/sp-tools/sp.mjs journal --init
# journal: /app/journal

# после мержа: пересобрать оглавление
node witness-done/SEED/sp-tools/sp.mjs journal --index

# гейт: дубли и битые ссылки — провал
node witness-done/SEED/sp-tools/sp.mjs journal --check --strict
```

**Коды.** `0` — ok / записано; `2` — проблемы журнала (в `--strict` — включая предупреждения).

#### 10.2.7 `review` — акт кто-то прочитал

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs review <Dxx> --verdict supports|does_not_support|unclear [--notes "…"] [--reviewer "…"]
```

**Что делает.** Создаёт `OUTPUT/evidence/<Dxx>.review.json` — артефакт, доказывающий, что акт не
только посчитан, но и прочитан человеком или другим агентом. Без него для `L2+` гейт `pre_ci`
возвращает `tax_pass: false`.

Перед записью команда проверяет: акт существует, опечатан (`evidence_hash` сходится), `reviewer`
не совпадает с `producer` акта. Review привязывается к `code_hash.produces_digest` и набору
`acceptance_ids`, а не к байтам акта: повторный `pre_ci` обновляет `timestamp` и не обесценивает review.
Дайджест считается по раскрытым файлам `PRODUCES`, поэтому правка любого файла под glob-шаблоном
(`src/events/**`) обесценивает review так же, как правка точного пути.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `<Dxx>` | да | Задание, чей акт читали |
| `--verdict <v>` | да | `supports` — подтверждаю; `does_not_support` — нет; `unclear` — сомневаюсь |
| `--notes "…"` | нет | Что именно проверили. Пустое поле допустимо, но бесполезно при разборе |
| `--reviewer "…"` | нет | Кто смотрел. По умолчанию `SP_AGENT`, иначе `git user.email` |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs review D03 --verdict supports \
  --reviewer anna@example.com --notes "A03.2: процесс убит после записи, событие читается"
# Wrote OUTPUT/evidence/D03.review.json

node witness-done/SEED/sp-tools/sp-verify.mjs --d D03 --gate pre_ci
```

**Коды.** `0` — review записан; `1` — нет `<Dxx>`, нет `--verdict`, неизвестный verdict, не известен
ревьюер; `2` — нет акта, акт изменён после приёмки, `reviewer` совпал с `producer`.

#### 10.2.8 `progress` — сборка прогресса из фрагментов

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs progress [--merge] [--check]
```

**Что делает.** Держит `OUTPUT/roadmaps/progress.md` производным от `OUTPUT/roadmaps/progress.d/<Dxx>.md`:
разные агенты меняют разные файлы, конфликт в мерже исчезает. Без флагов печатает список фрагментов.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--merge` | один из режимов | Собрать строки фрагментов в `progress.md` (сортировка по `D`). Конфликт одного `D` в двух фрагментах решается более новым `updated_at`; при равенстве — отказ со списком |
| `--check` | один из режимов | Сверить `progress.md` с фрагментами: `exit 2`, если строки расходятся или есть дубли. Строка `done`, для которой нет фрагмента (удалённый фрагмент, правка руками), — тоже расхождение |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs progress --merge
node witness-done/SEED/sp-tools/sp.mjs progress --check
```

**Коды.** `0` — собрано/согласовано; `2` — расхождение, дубль `D`, нет `progress.md` или таблицы `| D |`.

#### 10.2.9 `feedback` — короткая обратная связь

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs feedback [--lite]
```

**Что делает.** Пишет `OUTPUT/docs/feedback.md` из `TEMPLATES/feedback.md`; с `--lite` —
`OUTPUT/docs/feedback-lite.md` из `TEMPLATES/feedback-lite.md` (три вопроса вместо шести секций).
Режим по умолчанию берётся из `MANIFEST.md` (`Режим прогона`) и `SP_LITE=1`.
В файл добавляется `coverage_confidence` — статистическая оценка, а не замена `tax_pass`.
Компонент с нулевым знаменателем (например, `L3`-задач нет) не считается нулём: он исключается,
а веса `0.5 / 0.3 / 0.2` перераспределяются между оставшимися. Полностью подтверждённый проект
без `L3` даёт `1.0`, а не `0.8`.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--lite` | нет | Три вопроса: можно начинать, что критично, что отложено |

**Коды.** `0` — записано; `2` — нет шаблона.

#### 10.2.10 `rules` — адаптеры правил IDE

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs rules --list | --sync [--targets id,id] | --check
```

**Что делает.** Читает `SEED/agent-config/manifest.json` и `AGENTS.md`, затем показывает (`--list`),
пересобирает (`--sync`) или сверяет (`--check`) 13 файлов правил для IDE. Источник один —
`AGENTS.md`; сгенерированные файлы помечены и правятся только через источник.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--list` | один из трёх | Вывести цели и их состояние: `ok`, `missing`, `drift` |
| `--sync` | один из трёх | Записать адаптеры из `AGENTS.md`. Единственный режим, который меняет файлы |
| `--check` | один из трёх | Сверить без записи; `exit 2`, если обязательная цель отсутствует, разошлась или есть запрещённый файл |
| `--targets id,id` | нет, только с `--sync` | Ограничить набор целей: `claude,cursorrules` — обновить только их |

**Пример.**

```bash
# --targets cursorrules,claude — пересобрать только две цели, остальные не трогать
node witness-done/SEED/sp-tools/sp.mjs rules --sync --targets cursorrules,claude

# --check — сверка без записи; при рассинхроне exit 2
node witness-done/SEED/sp-tools/sp.mjs rules --check   # Правила синхронны (13 целей).
```

**Коды.** `0` — синхронно / записано; `2` — рассинхрон (гейт для CI и pre-commit).

#### 10.2.11 `doctor` — гейт входа

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs doctor [--strict] [--staged] [--team] [--json]
```

**Что делает.** Семь проверок входа, каждая — по файлам, а не по истории чата:

1. правила и адаптеры: `AGENTS.md` есть, оба маркера протокола на месте, обязательные адаптеры
   синхронны, запрещённых файлов (`.rules`) нет;
2. у каждой открытой записи входа заполнено `next:`;
3. нет `done` без акта в `OUTPUT/evidence/`;
4. изменённые файлы не выходят за `PRODUCES` шага (кроме `intake/` и `evidence/`);
5. `DEC-###`, упомянутые в записях и proposal, существуют в журнале;
6. чистота входа: нет ответов и артефактов от чужого прогона;
7. `ORCHESTRATOR.md` ровно один и в корне фабрики.

В корне канона (`--root` = фабрика, `MANIFEST` нет) проверяет канон, а не прогон — см. §4.7.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--strict` | нет | Предупреждения считать провалом. Режим CI: «почти хорошо» не проходит |
| `--staged` | нет | Проверять только файлы в индексе git (`git diff --cached`). Режим pre-commit |
| `--json` | нет | Вернуть `{ok, strict, problems, warnings, notes}` для машинной обработки |

**Пример.**

```bash
node witness-done/SEED/sp-tools/sp.mjs doctor --strict
# FAIL адаптер claude (CLAUDE.md): missing — выполнить sp rules --sync
# doctor: 1 проблем(а/ы) в strict-режиме        → exit 2
```

**Коды.** `0` — чисто; `2` — есть провалы (в `--strict` — включая предупреждения).

#### 10.2.12 `update` — версия фабрики

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp.mjs update [--json] [--offline] [--no-cache] [--timeout <мс>]
```

**Что делает.** Сравнивает `VERSION` фабрики с версией в репозитории из `SEED/update.json`
(сейчас `arhellist/WitnessDone@main`) по semver. Источники: `git ls-remote --tags origin` для клона,

Обновление **не применяет** — печатает готовые шаги. Подробно — §4.9.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--offline` | нет | Не ходить в сеть: только кэш. Нет кэша — `exit 3` |
| `--no-cache` | нет | Игнорировать кэш и проверить заново (кэш живёт 24 ч) |
| `--timeout <мс>` | нет | Таймаут HTTPS-запроса, по умолчанию `8000` |
| `--json` | нет | `{status, local, remote, source, repo, install, commands}` |

**Пример.**

```bash

# локально:  1.16.2
# удалённо:  1.17.0   (arhellist/WitnessDone@main, git-теги)
# статус:    доступно обновление      → exit 2
```

**Коды.** `0` — актуально; `2` — есть новая версия; `3` — проверить не удалось (нет сети, пустой
репозиторий, нет `SEED/update.json`). `3` не означает «всё хорошо».

#### 10.2.13 `verify …` и `retrieve …` — делегирование

|----------|--------------------|

### 10.5 `sp-verify` — приёмка

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp-verify.mjs --d D01 --gate pre_ci
```

**Что делает.** Парсит D-промпт или пакет изменения, выписывает фразы и идентификаторы, сверяет
связи со спецификацией, запускает линт/типы/тесты (если не `--skip-commands`) и пишет акт
в `OUTPUT/evidence/`. Акт — единственное основание считать задачу выполненной.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--gate <имя>` | нет, по умолчанию `pre_ci` | Какой гейт запускать (таблица ниже). Неизвестное имя — `exit 1` |
| `--d <Dxx>` | для `pre_ci` | Задание, которое принимается: `D01`, `D12` — имя файла в `OUTPUT/prompts/` без расширения |
| `--change <id>` | для `change` | ID пакета изменения: каталог `spec-state/changes/<id>/` |
| `--batch <n>` | нет, только `d-prompt-quality` | Номер пачки заданий. Канон запрещает проверять больше 5 за раз, поэтому `1`, `2`, `3`… |
| `--skip-commands` | нет | Только структурные проверки, без запуска линта и тестов. Акт помечается `commands_skipped: true`: для быстрой итерации годится, релиз такой акт не принимает |
| `--quick` | нет | Алиас `--skip-commands`: документированный режим быстрой итерации |
| `--budget-min <n>` | нет, `runtime` | Бюджет исполнения плана в минутах (по умолчанию 30) — на **весь** прогон, а не на команду. Остаток передаётся в таймаут каждой команды; тест за бюджетом не исполняется и попадает в `issues` |
| `--verify-evidence <путь>` | нет | Не гейт, а проверка одного акта: `evidence_hash`, `produces_digest` (glob раскрыт в файлы) и чистота акта в git. `git_head` печатается как факт и не сравнивается с `HEAD`; `committed: false` значит «черновик, историей не подтверждён» |
| `--root`, `--factory` | нет | Как у `sp`: где проект и где канон |

| Гейт | Что проверяет | Нужны аргументы |
|------|---------------|-----------------|
| `pre_ci` | задание `Dxx`: структура, `ACCEPTANCE`, связи со спецификацией; линт/типы/тесты | `--d Dxx` |
| `d-prompt-quality` | качество пачки заданий: `CONTEXT_PACK`, `HOW`, `INVARIANTS`, `ACCEPTANCE`, `SIZE_BUDGET`, ярлыки неполноты | `--batch N` |
| `self-audit` | самопроверка продукта 10b: покрытие, критерии выхода, качество заданий, акты | — |
| `baseline` | базовый набор спецификаций brownfield (R01): `MUST`/`SHALL` и ≥2 сценария на требование | — |
| `product-smoke` | смоук-прогон продукта по runbook; скрипт обязан метить проверки номерами `Axx.k`; акт опечатан (`evidence_hash`), пишет `code_hash`, `runtime.labels`, `uncovered_acceptance` и `script_sha256` | — |
| `runtime-plan` | `OUTPUT/runtime/runtime-plan.json`: нет заглушек, `down[]` есть, метки не фантомные, каждая принятая `Axx` покрыта `cmd` или `na` с причиной. Ничего не исполняет | — |
| `runtime` | исполняет план: `up` → `ready` → `seed` → `verify` → `down`; акт `RELEASE-runtime-verify.json` по каждой фразе, привязан к `plan_hash`, автотрейс обновляется после смены кода | `--budget-min N` |
| `change` | пакет изменения: delta-формат, связи с baseline, чек-лист задач, совместимость | `--change <id>` |
| `pre_release` | готовность к релизу: каждый `done` с опечатанным актом (`evidence_hash` + `produces_digest` + `commands_skipped: false`, для `L0` структурный акт законен), review у `L2/L3`, покрытие; `progress.md` разобран без остатка; при наличии runtime-кода — опечатанный акт `product-smoke`, при плане — исполненный акт `runtime` | — |
| `evidence-sync` | узкая сверка `progress.md` ↔ `evidence/*.json`: `done` без акта, акт без строки, акт при статусе не `done`. Пишет свой акт `EVIDENCE_SYNC.json`, а не `RELEASE.json` | — |

**Примеры.**

```bash
node witness-done/SEED/sp-tools/sp-verify.mjs --d D01 --gate pre_ci               # задание D01
node witness-done/SEED/sp-tools/sp-verify.mjs --gate d-prompt-quality --batch 2  # пачка №2
node witness-done/SEED/sp-tools/sp-verify.mjs --change add-user-avatar --gate change  # изменение
```

**Коды.** `0` — акт записан и `tax_pass: true`; `2` — провал проверки (акт с `tax_pass: false`
или без него); `1` — неизвестное имя гейта или неверные аргументы. `sp-verify` не доказывает, что тесты соответствуют `Given/When/Then` — он только
перечисляет `Axx` и запускает раннер; это ограничение записано в §7.5.

### 10.6 `sp-retrieve` — контекст

```bash
node <FACTORY_PATH>/SEED/sp-tools/sp-retrieve.mjs --reindex
```

**Что делает.** Три независимых режима: перестроить индекс, проверить готовый context pack,
собрать pack по запросу. Pack ограничивает, что агент читает при работе над заданием.

| Аргумент | Обязателен | Что значит |
|----------|-----------|------------|
| `--reindex` | один из режимов | Перестроить индекс `OUTPUT/` и `spec-state/`. Запускать после крупных правок артефактов |
| `--validate` | один из режимов | Проверить **существующий** pack. Сам pack не создаёт: отсутствующий — это `exit 2` |
| `--d <Dxx>` | для `--validate` | К какому заданию относится pack: `D03` → `OUTPUT/context/packs/P03.md` |
| `--pack <path>` | нет | Взять конкретный файл pack вместо вычисленного по `--d` |
| `--query "<текст>"` | для сборки | Текст запроса, по которому собирается pack: «JWT auth middleware» |
| `--out <path>` | для сборки | Куда записать pack. Без него — в stdout |
| `--max-chunks <n>` | нет | Ограничить число фрагментов в pack; `n > 12` — отказ вызова (`exit 1`), лимит канона не поднимается |
| `--root`, `--factory` | нет | Как у `sp` |

**Примеры.**

```bash
node witness-done/SEED/sp-tools/sp-retrieve.mjs --reindex            # перестроить индекс
node witness-done/SEED/sp-tools/sp-retrieve.mjs --d D03 --validate   # проверить pack для D03
# --query — что искать; --out — куда записать собранный pack
node witness-done/SEED/sp-tools/sp-retrieve.mjs --query "JWT auth middleware" \
  --out OUTPUT/context/packs/P-draft.md
```

**Коды.** `0` — индекс построен / pack валиден / pack собран; `2` — pack отсутствует или не
проходит `required_sections`; `3` — нечего индексировать.

| Команда | Где доступна | Что делает |
|---------|--------------|-----------|

### 10.9 Коды возврата

| Код | Значение |
|-----|----------|
| `0` | Успех / актуально |
| `1` | Ошибка вызова: неизвестная подкоманда, плохие аргументы |
| `2` | Провал проверки; для `update` — доступна новая версия |
| `3` | Нужен человек или проверить не удалось (неоднозначный intake, нет сети, нет `MANIFEST`) |

Код `3` — это не «ок». Скрипты и агенты обязаны различать «проверено и хорошо» и «не проверено»:
именно на этом различии держится запрет объявлять работу готовой без акта.

## 11. Полный перечень команд

§11 отвечает на вопрос «что набрать», §10 — «что при этом происходит внутри». Покрытие у них
одинаковое: **каждая подкоманда и каждый флаг** трёх CLI есть в обеих частях. Расхождение ловит
`validate.sh`: он вытаскивает флаги из исходников `sp.mjs`/`sp-verify.mjs`/`sp-retrieve.mjs` и
требует, чтобы каждый встречался в этом разделе. Поэтому «полный перечень — в §10» здесь больше
не пишется: этот раздел и есть полный перечень.

Практическое следствие: **новый флаг CLI обязан появиться в §11 в том же коммите**, иначе
`validate.sh` падает. Это не бюрократия — шпаргалка, отставшая от кода, врёт молча; падение
валидатора превращает молчание в отказ.

Обозначения: `<…>` — обязательный аргумент, `[…]` — необязательный, `|` — «или».

В блоках ниже комментарий относится ко всей группе строк под ним: первая строка — основной вызов,
следующие — варианты с теми же флагами (`--json`, `--offline`, `--staged`, другой `--ref` и т. п.).
Ни одна команда не осталась без разбора: либо строка подписана сама, либо подписана её группа,
либо её флаги разобраны в таблицах 11.2–11.4.

### 11.1 Откуда вызывать

| Где | Как выглядит команда |
|-----|----------------------|
| Проект с фабрикой в `witness-done/` | `node witness-done/SEED/sp-tools/sp.mjs …` |
| Проект со старой копией CLI в `scripts/sp-tools/` | `node witness-done/SEED/sp-tools/sp.mjs …` (копия допустима, но не нужна — DEC-034) |
| Корень канона (этот репозиторий) | `node SEED/sp-tools/sp.mjs …` |
| Папка фабрики называется иначе | `node <путь>/SEED/sp-tools/sp.mjs … --factory <путь>` |

Дальше в разделе пишется короткая форма `sp …`, `sp-verify …`, `sp-retrieve …`; подставляй тот
префикс, который соответствует твоему случаю. Без аргументов `sp` печатает справку и выходит
с кодом `1`; `sp --help` печатает её же и выходит с `0`.

### 11.2 Все флаги `sp`

| Флаг | С какой подкомандой | Что значит |
|------|--------------------|------------|
| `--help`, `-h` | любая | Справка и выход с кодом `0` |

### 11.5 Вход в проект

```bash
# status — «где я»: MODE, последний шаг, профиль, открытые записи входа, активные changes,
#          done без акта, версия фабрики. Аргументов нет; --json — машинный вывод.
sp status
sp status --json

# intake — создать запись входа journal/intake/<ID>.md.
#   "…"                — запрос дословно, как сказал человек (обязателен)
#   --kind <kind>      — new | question | change | task | bugfix (при exit 3 или явном решении)
#   --source <источник> — chat (по умолчанию) | issue | doc
sp intake "Добавь экспорт отчёта в CSV"
sp intake "Можно ли X?" --kind question --source issue

# next — показать маршрут из последней открытой записи входа (иначе resume из MANIFEST).
#        Аргументов нет, ничего не меняет.
sp next

# decide — дописать решение DEC-### в journal/decisions/ ДО кода.
#   "…"            — что решили и почему, утвердительно (обязателен)
#   --intake <ID>  — к какой записи входа привязать решение
#   --adr <ADR-id> — если решение архитектурное
sp decide "Экспорт только CSV: XLSX не просили" --intake <ID>
sp decide "JWT в httpOnly-cookie, не localStorage" --intake <ID> --adr ADR-003

# close — закрыть запись входа ссылкой на артефакт.
#   <ID>        — имя файла в journal/intake/ без .md (достаточно уникального префикса)
#   --ref <…>   — DEC-001 (решение) | D01 (акт приёмки) | <change-id> (пакет изменения)
sp close <ID> --ref DEC-001
sp close <ID> --ref D01
sp close <ID> --ref add-report-export

# journal — журнал проекта в journal/ (коммитится вместе с кодом).
#   --init    — создать из заготовки SEED/journal/
#   --index   — пересобрать оглавление decisions.md
#   --check   — дубли DEC, битые ссылки, дрейф индекса (exit 2)
#   --migrate — перенести старый журнал из OUTPUT/
#   --list    — показать записи; --limit N — сколько последних
sp journal
sp journal --init
sp journal --index
sp journal --check --strict

# review — «акт прочитан» как артефакт, а не как обещание.
#   --verdict supports|does_not_support|unclear — обязателен, только supports пропускает
#   --reviewer "…" — кто смотрел (по умолчанию SP_AGENT или git user.email)
#   --notes "…"    — что именно проверили
sp review D03 --verdict supports --reviewer anna@example.com
sp review D03 --verdict unclear --notes "A03.2 не проверял"

# независимая проверка акта: только файл и дерево, без транскрипта создателя
node witness-done/SEED/sp-tools/sp-verify.mjs --verify-evidence OUTPUT/evidence/D03.json

# командный прогресс: каждый агент пишет свой фрагмент, progress.md собирается
sp progress --merge
sp progress --check

# короткая обратная связь с оценкой уверенности
sp feedback --lite
```

**Командный режим.** `sp doctor --team` дополнительно требует: у каждого `done` есть `evidence_ref`,
`review` непустой и не устарел, один `D` не объявлен дважды в разных фрагментах `progress.d/`.
`progress.md` помечен `merge=union` в `.gitattributes` — строки не теряются при мерже.

`<ID>` — реальный идентификатор вида `20261028-1200-dobav-eksport-otcheta-v-csv`; его печатает
`intake`, и он же лежит в имени файла записи. `DEC-001` — номер из журнала решений.

## 12. Версии и обозначения

**Одна версия фабрики — в `VERSION`.** В каталогах и шаблонах встречается пометка «правило действует
с vX»: это **версия, в которой правило появилось**, а не текущая версия фабрики. Так видно, что
нового, и не нужно угадывать, «устарел ли» каталог.

**История версий не ведётся и нигде не хранится** — ни в README, ни отдельным файлом. README
описывает текущее состояние, а не прошлое; что и зачем менялось, видно из сообщений коммитов и
тегов `vX.Y.Z`. Копия списка изменений внутри репозитория всегда врёт: её забывают обновлять,
и она начинает конкурировать с git как источник истины.

| Обозначение | Где | Если потерять |
|---|---|---|
| `MODE` | `OUTPUT/MANIFEST.md` | шаги greenfield и R00–R05 смешаны — непонятно, что запускать |
| Профиль + отклонения | `OUTPUT/MANIFEST.md` | акценты продукта потеряны, шаг 01 «додумывает» |
| `wave` / `c_subwave` / `c2_batch` | `OUTPUT/MANIFEST.md` | resume невозможен без перечитывания всего OUTPUT |
| `last_completed_step` | `OUTPUT/MANIFEST.md` | непонятно, с какого шага продолжать |
| `FACTORY_PATH` | `OUTPUT/MANIFEST.md` | артефакты ссылаются на «где-то там» |

Термины, которые легко перепутать:

- **`L0…L3`** — строгость задания: `L0` — документы, `L1` — модуль, `L2` — приложение/API/UI,
  `L3` — деньги/квоты/реестр с обязательным подтверждением человеком.
- **контур 1/2/3** — точка приёмки: `pre_ci` → wave smoke → `pre_release` + product-smoke.
- **гейт** — конкретный вызов `sp-verify` (`pre_ci`, `change`, `d-prompt-quality`, `self-audit`,
  `baseline`, `product-smoke`, `pre_release`, `evidence-sync`).

- [ ] `proposal.md` содержит `Intake: <ID>`, и запись входа существует.
- [ ] Дельта: `ADDED`/`MODIFIED`/`REMOVED`, блоки заменяются целиком.
- [ ] Требования: `MUST/SHALL` + ≥2 сценария (happy + negative/boundary).
- [ ] `tasks.md` 100% и каждая задача привязана к `Axx.k` / `Rxx`.
- [ ] `sp-verify --change <id> --gate change` → `tax_pass: true`, `evidence/CHANGE-<id>.json`.
- [ ] Дельта влита в baseline, пакет в `spec-state/archive/YYYY-MM-DD-<id>/`.
- [ ] `sp-retrieve --reindex`, `progress.md` и `MANIFEST` отражают реальность.
- [ ] `sp close <ID> --ref <change-id>` выполнен; `sp doctor --strict` → exit 0.

### 13.3 Как рассказать проект за минуту

> «У меня был выбор: писать проект в Cursor по кускам и надеяться, что не разъедется, — или сначала
> построить процесс, который делает разъезд невозможным. Я выбрал второе и оформил это как
> переносимый канон. Фабрика проходит волнами A→B→C→C4, на каждом шаге фиксирует состояние в
> MANIFEST, на выходе даёт задания на разработку с контрактами, списками проверяемых фраз и пакетами
> документов. Дальше код пишется по ним, а каждая фича закрывается прогоном приёмки и актом. В итоге
> у меня не "проект, который я помню", а проект, который можно восстановить и проверить по артефактам».

### 13.4 Как ответить «покажите пример контроля качества»

> «Возьмём задание про запись события. У него шесть проверяемых утверждений: сохранность на диске,
> монотонность номеров, целостность цепочки, одновременная запись, проверка схемы, отсутствие дублей.
> Каждое — тест. Формальный прогон запускает их и пишет файл доказательств с результатом аудита и
> списком закрытых утверждений. Таблица прогресса не даст поставить "готово", если файла нет. Поэтому
> "сделано" — это не моя оценка, а файл, который можно открыть».
