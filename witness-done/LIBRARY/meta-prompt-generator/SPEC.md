# LIBRARY MODULE: meta-prompt-generator

## Назначение

Мета-промпт: генерировать новые компонентные ТЗ в формате LIBRARY (`SPEC.md`) под React/Node/PostgreSQL (или стек из constitution).

## Когда использовать

- В ТЗ появилась фича, которой нет в LIBRARY.
- Шаг 09: `gaps.md` → сгенерировать черновик модуля.
- Расширение фабрики между проектами.

## Когда не использовать

- Модуль уже есть — адаптировать через `ADAPTATION.md`, не плодить дубликаты.
- Просьба «сразу код» без ТЗ — сначала SPEC.

---

## Промпт (вставлять в Cursor)

```markdown
Ты — senior full-stack архитектор. Напиши техническое задание (LIBRARY SPEC)
для реализации: **[НАЗВАНИЕ ФУНКЦИОНАЛА]**.

Стек проекта (из constitution / ТЗ): […]
Связанные модули LIBRARY (не дублировать, а CONSUMES): […]
Ограничения OUT OF SCOPE: […]

Опирайся на канон: @witness-done/LIBRARY/methodology-architecture/SPEC.md
Формат секций — как в @witness-done/TEMPLATES/library-module.md и существующих SPEC
(например @witness-done/LIBRARY/auth-jwt/SPEC.md).

Обязательно включи:
1. Назначение
2. Когда использовать / когда НЕ использовать
3. Зависимости (другие LIBRARY id)
4. Env
5. Модели данных
6. API / события (метод, path, auth, ошибки)
7. Структура кода (папки)
8. Frontend (компоненты/хуки)
9. Security invariants (**критичное — явно**)
10. NFR / perf заметки
11. Тест-сценарии
12. Антипаттерны
13. Критерии готовности

Правила стиля:
- Без воды; нумерованные секции
- Код — только короткие фрагменты контрактов, не полная реализация
- Junior должен понять порядок работ
- Пометь GATE-решения (то, что человеку подтвердить)
- Явно напиши, что модуль подключать только если приемлемо к текущему приложению

Выход: один файл `LIBRARY/<id>/SPEC.md` (без README в папке модуля).
Укажи допустимые runtime (Node/Go/Java) и что в примерах кода — иллюстрация, не единственный стек.
```

## Выход фабрики

Сохранять только в глобальную `LIBRARY/<id>/SPEC.md` фабрики.  
**Не** писать модули в `OUTPUT/library/` проекта.

## CONFLICTS with other modules

| С другим модулем | Проблема | Решение |
|------------------|----------|---------|
| Существующий SPEC | Дубликат модуля | Сначала adapt существующий; новый id только при новом домене |
| `methodology-architecture` | Расхождение стиля | Новые SPEC обязаны ссылаться на канон, stack-policy и иметь CONFLICTS |
