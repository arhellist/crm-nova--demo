# Runbook инцидента NOVA CRM

> Исполнитель: дежурный инженер, не автор последнего изменения. Шаги идут по порядку,
> у каждого есть команда и ожидаемый результат. Если ожидание не совпало — переходите
> к следующему шагу и фиксируйте отклонение в журнале инцидента.
>
> Алерты ссылаются на разделы этого файла: `docs/runbooks/incident.md#1-подтверждение-алерта`.

## 0. Что считается инцидентом

- Сработал алерт из `observability/prometheus/rules.yml`.
- Или пользователь сообщает об отказе входа, задач, отчётов.
- Или `/health` отвечает не 200 дольше минуты.

Алерт — не инцидент. Инцидент начинается, когда подтверждено влияние на пользователей
или на данные. Одиночный всплеск 5xx без влияния закрывается записью в журнале наблюдений.

## 1. Подтверждение алерта

1. Откройте панель «Доступность отчётного API» дашборда `nova-product`.
2. Проверьте живосость процесса:

   ```sh
   curl -sS -o /dev/null -w '%{http_code}\n' "$REPORT_API_URL/health"
   ```

   Ожидается `200`. `503` от `/health` не бывает: этот маршрут не зависит от реплики.
3. Проверьте состояние подписки:

   ```sh
   curl -sS -H "Authorization: Bearer $API_TOKEN" "$REPORT_API_URL/health/replication"
   ```

   Ожидается `status: streaming`. `lagging` или `broken` — инцидент контура чтения.
4. Зафиксируйте время первого алерта (UTC) в журнале инцидента.

## 2. Определить контур

| Признак | Контур | Что это значит |
|---------|--------|----------------|
| Вход и задачи работают, `/api/reports/*` отвечают 503 | чтение | реплика отстала или подписка упала |
| Вход или задачи не работают | запись/аутентификация | primary/Supabase Auth, отчёты не виноваты |
| `/health` не 200, `/replication` не отвечает | процесс | контейнер отчётного API или сеть |
| 5xx только на `/api/reports/*` | чтение | запросы к реплике или кэш |
| 5xx на всех маршрутах | процесс | общий сбой отчётного API |

Команды различения:

```sh
# Отчёты: деградация контура чтения, запись не затронута.
curl -sS -o /dev/null -w 'reports=%{http_code}\n' \
  -H "Authorization: Bearer $API_TOKEN" "$REPORT_API_URL/api/reports/objects"

# Метрики: лаг и очередь пула.
curl -sS -H "Authorization: Bearer $API_TOKEN" "$REPORT_API_URL/metrics" \
  | grep -E '^(replica_|db_pool_)'
```

Ожидание: при живом primary и упавшей подписке отчёты дают `503`, а вход и задачи — нет.
Если недоступен вход, эскалируйте в контур Supabase, не перезапускайте отчётный API.

## 3. Временные меры

### 3.1. Реплика отстала (`NovaReplicaLagHigh`, `NovaReplicaNotStreaming`)

1. Проверьте `replica_streaming` и `replica_lag_seconds` в `/metrics`.
2. Если `replica_streaming = 0` дольше 5 минут:

   ```sh
   docker compose -f infra/replica/docker-compose.yml ps
   docker compose -f infra/replica/docker-compose.yml logs --tail=200 replica
   ```

   Ожидается `healthy` и повторяющиеся сообщения `logical replication apply worker`.
3. Перезапустите только подписчик:

   ```sh
   docker compose -f infra/replica/docker-compose.yml restart replica
   ```

   Ожидание: через 1–2 минуты `replica_streaming = 1`, лаг падает ниже 30 секунд.
4. Если подписка не восстанавливается, объявите деградацию отчётов: пользователи видят
   панель «Отчёты временно недоступны», запись продолжает работать. Не пересоздавайте слот
   без второго инженера: это потеря истории и рост WAL на primary.

### 3.2. Отчёты отвечают 5xx дольше 5 минут (`NovaReport5xx`)

1. Проверьте `/health/replication`: если `broken`, действуйте по 3.1.
2. Если подписка `streaming`, но отчёты падают, найдите `request_id` в логах отчётного API:

   ```sh
   docker compose -f infra/replica/docker-compose.yml logs --tail=500 api \
     | grep -E '"status":5|E_REPLICA|E_INTERNAL'
   ```

   Ожидание: `E_REPLICA_DOWN`/`E_REPLICA_LAG` при проблеме реплики, `E_INTERNAL` — дефект.
3. Очистите кэш перезапуском отчётного API только при зависшем кэше:

   ```sh
   docker compose -f infra/replica/docker-compose.yml restart api
   ```

   Ожидание: `/health` = 200, `/api/reports/objects` = 200 или 503 с `retry-after`.
4. При дефекте кода откатите релиз по `docs/runbooks/release.md`, не правьте данные вручную.

### 3.3. Очередь пула (`NovaReportPoolSaturation`)

1. Снимите `/metrics`, сравните `db_pool_waiting`, `db_pool_acquired`, `db_pool_total`.
2. Если `db_pool_waiting > 5` и растёт, ограничьте период отчёта в UI (кнопка «Повторить»
   не должна вызываться в цикле) и проверьте медленные запросы на реплике:

   ```sh
   psql "$DATABASE_URL_REPLICA" -c "select pid, state, wait_event_type, now()-query_start as age, left(query,120) from pg_stat_activity where state <> 'idle' order by age desc limit 10;"
   ```

   Ожидание: нет запросов старше 3 секунд (statement_timeout). Если есть — эскалируйте
   владельцу отчётов; увеличивать пул вслепую запрещено.

## 4. Коммуникация

1. Первое сообщение — в течение 15 минут после подтверждения: что не работает, кого касается,
   что уже сделано, когда следующее обновление.
2. Обновление каждые 30 минут до восстановления.
3. Шаблон: «Отчёты недоступны с HH:MM UTC. Вход и задачи работают. Причина: лаг репликации.
   Восстановление: перезапуск подписчика, ETA HH:MM. Следующее обновление HH:MM.»
4. Не публикуйте внутренние адреса, SQL и имена таблиц.

## 5. Закрытие инцидента

1. Убедитесь, что алерт погас, а `/health/replication` = `streaming` не меньше 10 минут.
2. Выполните smoke отчётов: три вкладки, `source: replica`, лаг меньше 30 секунд.
3. Запишите в журнал: время начала и конца (UTC), контур, причину, действия, влияние.
4. Обновите этот runbook, если шаг не сработал или его не хватило.
5. Создайте задачу на устранение причины, если она не разовая.

## Ограничения наблюдаемости

- Размер WAL primary и p95 длительности переходов не собираются: backend читает только
  реплику (INV-001), отдельного экспортёра primary нет (DEC-028). Не ищите эти панели
  в дашборде — их отсутствие не является инцидентом.
- Метрики отчётного API живут в процессе; при падении контейнера они исчезают вместе с ним,
  поэтому `NovaApiDown` и `NovaMetricsMissing` смотрят на `up`, а не на счётчики.

## 6. Учения: остановка реплики (`@acceptance A13.4`)

Протокол, ожидания и фактический прогон с таймстампами — `docs/runbooks/incident.drill.md`.
Кратко: reporting-сервис с недоступной репликой обязан отдавать `/health` = 200,
`/health/replication` = 503 `broken`, отчёты — 503 `E_REPLICA_DOWN`, а запись задач через
Supabase остаётся рабочей (reporting не имеет прав записи, INV-001). Инцидент закрывается
по §5 с временем начала и конца в UTC.
