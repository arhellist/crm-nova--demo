# Backup и восстановление NOVA CRM

> Цели NFR8: **RPO ≤ 5 минут** (логическая репликация + PITR primary), **RTO ≤ 60 минут**.
> Бэкап без проверенного восстановления не считается бэкапом: каждое учение заполняет акт
> в конце этого файла.
>
> Владелец процедуры — platform. Учение проводит инженер, не автор последнего изменения схемы.

## 1. Что и как часто

| Контур | Механизм | Частота | Хранение |
|--------|----------|---------|----------|
| Supabase primary | автоматический бэкап Supabase + PITR (WAL) | ежедневно, PITR непрерывен | 7 дней (PITR), 30 дней (бэкапы) |
| Вторичная БД | логическая репликация `nova_sub` | непрерывно | не является бэкапом |
| Конфигурация | git (миграции, compose, runbooks) | на каждый merge | бессрочно |

Вторичная реплика **не заменяет** бэкап: ошибка на primary реплицируется в неё за секунды.

## 2. Ежедневная проверка

```sh
BACKUP_DIR=/var/backups/nova \
WAL_ARCHIVE_DIR=/var/backups/nova/wal \
sh scripts/ops/backup-check.sh
echo $?
```

Ожидается:

```text
backup: последняя точка 2026-11-04T02:00:00Z, возраст 3600 с (порог 86400 с)
wal: последняя точка 2026-11-04T03:00:00Z, возраст 120 с (порог 3600 с)
```

`0` — точки свежие; `1` — бэкапа за 24 часа или WAL за час нет. Код `1` — повод открыть
инцидент, а не «подождать до завтра». Планировщик вызывает тот же скрипт и отправляет
результат в мониторинг.

## 3. Восстановление на staging (PITR)

Предусловия: staging-проект Supabase, доступ к PITR в панели, `psql` и `supabase` CLI,
никто не пишет в staging во время учения.

1. Зафиксируйте целевую точку (UTC) до начала: время последней ожидаемой записи.

   ```sh
   date -u +%Y-%m-%dT%H:%M:%SZ
   ```

2. В панели Supabase: **Database → Backups → Point in time** → выберите точку из шага 1 →
   **Restore**. Ожидание: статус `Restoring`, затем `Healthy`; RTO отсчитывается от нажатия.
3. Дождитесь применения миграций и подписки:

   ```sh
   npx supabase status -o json
   psql "$DATABASE_URL_REPLICA" -c "select status, lag_seconds from (select 'streaming' as status, 0 as lag_seconds) s;"
   ```

   Ожидание: `API URL` доступен, подписка `streaming`, лаг меньше 30 секунд.
4. Проверьте целостность по счётчикам четырёх таблиц (эталон — снимок до учения):

   ```sh
   psql "$DATABASE_URL_REPLICA" -At -c "
     select 'profiles='||count(*) from public.profiles union all
     select 'objects='||count(*) from public.objects union all
     select 'tasks='||count(*) from public.tasks union all
     select 'history='||count(*) from public.task_status_history;"
   ```

   Ожидание: числа совпадают с эталоном до последней мутации. Расхождение — остановить
   учение, зафиксировать точку и передать владельцу данных.
5. Проверьте один сквозной сценарий: вход менеджера, список задач, отчёт с `source: replica`.
6. Заполните акт ниже и сохраните его в журнале релиза.

## 4. Откат при неудачном восстановлении

- Не удаляйте исходный проект: PITR-точка остаётся доступной.
- Верните staging на предыдущую точку тем же способом; RTO считается по последней попытке.
- Если восстановление не удаётся за 60 минут, эскалируйте в Supabase Support и объявите
  инцидент по `docs/runbooks/incident.md`.
