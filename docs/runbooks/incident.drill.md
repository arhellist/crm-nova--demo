# Учения: остановка реплики (`@acceptance A13.4`)

Протокол проверяет, что `docs/runbooks/incident.md` выполняется дежурным инженером без автора
изменений и что деградация контура чтения не затрагивает запись. Учения имитируют остановку
реплики: reporting-сервис запускается с `DATABASE_URL_REPLICA` на закрытый порт, primary и
`nova_ro` не трогаются.

## 1. Шаги и ожидания

| № | Действие | Ожидание |
|---|----------|----------|
| 1 | `curl -sS -o /dev/null -w '%{http_code}' "$REPORT_API_URL/health"` | `200`: процесс жив, health не зависит от реплики |
| 2 | `curl -sS "$REPORT_API_URL/health/replication"` | `503`, `status: broken` |
| 3 | `GET /api/reports/objects` с `Authorization: Bearer $API_TOKEN` | `503`, `code: E_REPLICA_DOWN`, без SQL и имён таблиц (INV-007) |
| 4 | `GET /metrics \| grep -E '^(replica_\|http_requests_)'` | `replica_streaming 0`, растёт `http_requests_total{status="503"}` |
| 5 | UI `#/reports` | бейдж свежести показывает деградацию, навигация и задачи работают (A11.6) |
| 6 | Создать задачу и сменить статус через Supabase | запись проходит: reporting не пишет и не читает primary (INV-001) |
| 7 | Восстановить реплику, повторить 1–4 | `/health/replication` → `200`, отчёты → `200`, лаг ниже 30 с |
| 8 | Зафиксировать таймстампы и закрыть инцидент по §5 | инцидент закрыт с временем начала и конца |

## 3. Критерии успеха

- Отчёты деградируют предсказуемо (`503 E_REPLICA_DOWN`), приложение остаётся рабочим.
- Запись задач и смена статусов не зависят от состояния реплики.
- Каждый шаг имеет таймстамп UTC; инцидент закрыт с временем обнаружения и закрытия.
- Секреты (токен, строка подключения) не попадают в вывод команд и журнал учений.

## 4. Повторяемость

Учения повторяются перед релизом и после изменения схемы репликации; результат оформляется
таблицей §2. Действия при инциденте — `incident.md`, восстановление из бэкапа —
`backup-restore.md`.
