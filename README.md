# NOVA CRM — объекты и задачи строительной компании

Небольшая закрытая веб-CRM: руководитель (постановщик) ведёт объекты (стройки) и задачи,
исполнители выполняют их и отдают на проверку. Права и переходы статусов проверяет
**база данных** (RLS и RPC), а не только интерфейс.

| | |
|---|---|
| **Демо** | https://arhellist.ru/crm-nova/ |
| **Репозиторий** | этот проект (миграции в `supabase/migrations/`) |
| **Стек** | React 18 + TypeScript, Vite, Supabase (Auth + Postgres + PostgREST), Fastify BFF |
| **Решения** | [`docs/decisions.md`](docs/decisions.md) · ADR в `witness-done/OUTPUT/docs/adr/` |

## 1. Доступ к демо (тестовые учётные записи)

Открытая регистрация **отключена**. Seed даёт три учётки; постановщик может создать
ещё менеджера в UI «Команда» (одноразовый пароль, DEC-060).

| Роль | Email | Пароль | Что проверить |
|------|-------|--------|----------------|
| Постановщик | `manager@nova.local` | `nova-local-password` | объекты, задачи, приёмка, отчёты, **Команда** |
| Исполнитель 1 | `executor1@nova.local` | `nova-local-password` | только свои задачи, «В работу» / «На проверку» |
| Исполнитель 2 | `executor2@nova.local` | `nova-local-password` | изоляция от задач первого исполнителя |

- Вход **только email + пароль**.
- В базе после seed: **3 объекта**, **≥8 задач** во всех пяти статусах.
- Имена в UI: Ирина Волкова (manager), Пётр Смирнов / Анна Ковалёва (executors).

> Демо-пароли из `supabase/seed.sql`. `service_role` / secret key — только на BFF для
> `POST /api/auth/managers`, не в клиенте и не в git (DEC-060).

## 2. Что умеет система (коротко)

1. **Роли:** постановщик (`manager`) и исполнитель (`executor`); роль берётся из
   `profiles.role`, не из JWT. Постановщик может добавить менеджера в разделе «Команда».
2. **Объекты:** название, адрес; создание / правка / **архивирование** (вместо hard-delete);

   карточка со списком задач.
3. **Задачи:** название, описание, объект, исполнитель, статус, автор, дата создания.
4. **Статусы и переходы** (другие запрещены в БД):
   | Из | В | Кто |
    |----|---|-----|
    | — | Новая | постановщик (при создании) |
    | Новая | В работе | назначенный исполнитель |
    | В работе | На проверке | назначенный исполнитель |
    | На проверке | Принята | постановщик |
    | На проверке | На доработке | постановщик (+ обязательный комментарий) |
    | На доработке | В работе | назначенный исполнитель |
5. **История:** кто, когда, из какого статуса в какой, комментарий; append-only

   (клиент не может INSERT/UPDATE/DELETE историю).
6. **Экраны:** вход, объекты, карточка объекта, карточка задачи, «Мои задачи», отчёты

   (только постановщик), **Команда** (только постановщик), 404. Кнопки показывают только
   доступные действия.
7. **Команда** — см. §2.1 ниже.

### 2.1. Команда (только постановщик)

Раздел в навигации **«Команда»** (`/team`). Исполнителю пункт не показывается.

**Карточки менеджеров.** В UI заказчика «менеджеры» — это люди, которым назначают задачи
(в схеме БД роль `executor`: в демо **Анна Ковалёва** и **Пётр Смирнов**). На каждой
карточке:

- ФИО;
- всего активных задач (на неархивных объектах);
- разбивка по статусам: Новая / В работе / На проверке / На доработке / Принята;
- KPI — доля принятых среди этих задач.

Данные — агрегаты с read-only API (`GET /api/reports/workload`), без email и описаний
(INV-011). Карточка **текущего постановщика** (в демо Ирина Волкова) в сетке **не
показывается** — экран про команду, не про себя (DEC-068).

**Добавить менеджера.** Форма создаёт учётку с ролью `manager` (ещё один постановщик):
ФИО + email → одноразовый пароль показывается **один раз** и в API повторно не
отдаётся. Нужны права `service_role` только на BFF (`POST /api/auth/managers`); в
браузер и git ключ не попадает (DEC-060, INV-006). Прочее администрирование
пользователей (блокировка, смена роли, сброс пароля) — вне объёма.

|---------------|--------|-------------|

| Исполнитель: в работу / на проверку | Да | матрица переходов в БД |
| Объект: название, адрес; список задач в карточке | Да | |
| Задача: поля из ТЗ + история | Да | |
| Матрица из 5 разрешённых переходов; остальное запрещено | Да | триггер + RPC, коды `P0403` / `P0422` |
| Комментарий обязателен при возврате на доработку | Да | и в UI, и в БД |
| История смен статуса видна обеим ролям | Да | `task_status_history` |
| Экраны: вход, объекты, карточки, «Мои задачи» | Да | React Router |
| UI показывает только доступные действия | Да | роль + статус |
| Команда: KPI по исполнителям + создание менеджера | Да* | *сверх hh; §2.1, DEC-060/068 |

### 3.2. Безопасность (§3)

| Требование ТЗ | Статус | Как сделано |
|---------------|--------|-------------|
| Права на уровне БД (RLS), не только скрытие в UI | Да | политики на всех таблицах |
| Исполнитель не читает/не меняет чужие задачи | Да | RLS + тесты pgTAP |
| Запрещённый переход статуса не проходит даже вручную | Да | RPC + триггер |
| Историю нельзя подделать/изменить/удалить через API | Да | append-only, нет прав у клиента |
| Открытая регистрация отключена | Да | `disable_signup` / нет UI signup |
| `service_role` не во фронтенде и не в репозитории | Да | только anon + user JWT через BFF |

### 3.4. Частые вопросы (ответы)

**Нужен ли TOTP / Google Authenticator?**  
Нет. В исходном ТЗ hh — только email и пароль. TOTP убран (DEC-053).

**Почему не «удаление», а архив?**  
ТЗ формулирует «удаляет», но для CRM с историей hard-delete ломает аудит. Сделано
архивирование: запись скрывается из рабочих списков, история сохраняется. Это
осознанное усиление безопасности, зафиксированное в решениях.

**Куда делись токены / почему не localStorage?**  
Access и refresh лежат в **httpOnly cookies** на том же домене, что SPA. Браузер не
ходит в Supabase напрямую: same-origin BFF (Auth + Data Gateway) подставляет
пользовательский JWT. Так токены не крадутся простым XSS через JS; CSRF закрыт
double-submit + проверкой Origin (ADR-0005 / DEC-053).

**Где хранятся данные?**  
Склад — **Supabase Postgres** (PostgREST/RPC + RLS). Сессия и периметр безопасности —
на нашем домене (BFF).

**Что сверх ТЗ hh?**  
Экран отчётов с агрегатами (read-only API), контур реплики/демо-режим отчётов,
раздел **«Команда»** (карточки загрузки исполнителей + создание менеджера с
одноразовым паролем), расширенные автотесты и runbook’и эксплуатации. На функционал
«объекты + задачи + безопасность» из hh это не влияет.

**Что такое «Команда» и почему там Анна и Пётр, а не Ирина?**  
Постановщик смотрит загрузку **исполнителей** (кому назначены задачи) и может завести
ещё одну учётку менеджера. Свою карточку постановщик на этом экране не видит —
подробности в §2.1.

**Можно ли обойти UI и писать в API напрямую?**  
Доменные данные с браузера идут только на наш `/api/data/*` при валидной cookie-сессии.
Даже с украденным сценарием права всё равно режет **RLS** в Postgres; смена статуса —
только через RPC.

## 4. Объяснение для руководителя (без жаргона)

NOVA CRM — рабочий стол стройки.

1. Руководитель заводит **объект** (например, «ЖК Северный») и **задачи** по нему,

   назначает исполнителя.
2. Исполнитель видит **только свои** задачи: берёт в работу и отправляет на проверку.
3. Руководитель **принимает** работу или возвращает **на доработку** с комментарием.
4. Каждый переход пишется в **журнал**, который нельзя тихо подчистить.
5. Вход — логин и пароль. Система **сама** проверяет права в базе: спрятать кнопку в

   интерфейсе недостаточно, «чужую» задачу через прямой запрос тоже не прочитать.
6. Отчёты считаются отдельно (агрегаты), чтобы нагрузка на отчёты не мешала работе

   с задачами.
7. В **Команде** руководитель видит, сколько задач у каждого исполнителя по статусам,

   и может выдать доступ новому менеджеру (одноразовый пароль).

## 5. Решения и допущения (где ТЗ неоднозначно)

| Тема | Решение | Почему |
|------|---------|--------|
| «Удаление» объектов/задач | Архивирование | Сохраняем историю и аудит |
| MFA / TOTP | Не используем | В hh-ТЗ только email/пароль |
| Хранение сессии | httpOnly cookies + BFF | Токены не в JS; один домен с SPA |
| Путь к данным | Data Gateway → Supabase с **user** JWT | RLS не обходится; нет `service_role` в клиенте |
| UI-кит | Tailwind + свои компоненты (Radix) | Без тяжёлых MUI/AntD |
| Дизайн | Аккуратный тёмный UI по design-notes | В hh дизайн не оценивается |
| Отчёты | Есть у постановщика | Расширение объёма, не пробел hh |
| Демо-реплика отчётов | `DEMO_STAND`: чтение через `nova_ro` без отдельного subscriber | Упрощение публичного стенда (DEC-049) |
| Команда: чьи карточки | Исполнители (`workload`), не постановщик | Заказчик смотрит загрузку команды (DEC-068) |
| Команда: новый менеджер | BFF + `service_role` только на create; пароль один раз | Без UI-админки и без ключа в клиенте (DEC-060) |

Полный журнал: [`docs/decisions.md`](docs/decisions.md), `journal/decisions/`.

## 6. Архитектура (как устроено технически)

```text
Браузер  https://arhellist.ru/crm-nova/
  │  cookies (access + refresh, HttpOnly) + CSRF
  ▼
BFF (Fastify на том же origin)
  ├─ /api/auth/login|refresh|logout|me|csrf  → Supabase Auth (GoTrue)
  ├─ /api/data/*  → PostgREST/RPC с Bearer user JWT  → Postgres + RLS
  └─ /api/reports/*  → read-only агрегаты (токен отчётов)
```

- **Запись CRM** — только через Supabase PostgREST/RPC (транспорт: BFF).
- **Смена статуса** — только `rpc.change_task_status`.
- **История** — append-only.
- Подробности: ADR-0005, `witness-done/OUTPUT/docs/03_architecture.md`.

## 7. Быстрый старт локально

Требования: Node.js 20, npm 10, Docker, Supabase CLI.

```sh
git clone <repo> && cd TestCRM
npm ci
cp .env.example .env.local    # подставить значения из `npx supabase status`
npx supabase start
npx supabase db reset         # миграции + seed
npm run dev                   # Vite + backend
```

Открыть `http://127.0.0.1:5173`, войти учётками из §1.

Для демо на `/crm-nova/`:

```sh
# SPA + отчёты (не подхватывает VITE_API_BASE_URL=127.0.0.1 из .env.local)
./scripts/release/deploy-arhellist-crm-nova.sh
# API (BFF + reports), см. scripts/release/deploy-arhellist-crm-nova-api.sh
```

Секреты не коммитятся. `service_role` не бывает в клиенте и backend data-path.
