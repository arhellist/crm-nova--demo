# Domain Spec: platform

> Системный домен: конфигурация окружения, логирование, ограничение частоты запросов, обработка
> ошибок и завершение процесса. Источник: `OUTPUT/tooling/env-vars.md`,
> `OUTPUT/tooling/verify-commands.md`, NFR5, NFR16, INV-006, INV-007, INV-010.
> Границы домена: доменной логики нет; всё, что касается объектов, задач и отчётов, — в своих доменах.

## Назначение и границы

Платформа задаёт правила, которым подчиняются все остальные домены: единственный источник
конфигурации (`src/shared/config/env.ts`), единственный логгер (`src/shared/logger.ts`), общая
обработка ошибок и rate limit. Никакой модуль MUST NOT читать `process.env` напрямую и MUST NOT
писать в stdout в обход логгера.

## Требования

### Requirement: Конфигурация валидируется Zod при старте

Система MUST читать переменные окружения только через схему Zod в `src/shared/config/env.ts` и
SHALL падать с кодом 1, если обязательная переменная отсутствует или невалидна. Сообщение об
ошибке MUST перечислять имена отсутствующих ключей и MUST NOT печатать их значения. Экспортируемый
объект конфигурации SHALL быть заморожен.

#### Scenario: happy path
- GIVEN в окружении заданы все обязательные переменные с валидными значениями
- WHEN приложение импортирует `env.ts`
- THEN конфигурация загружена один раз, объект заморожен, значения приведены к нужным типам

#### Scenario: negative — отсутствующая переменная
- GIVEN переменная `SUPABASE_URL` не задана
- WHEN модуль `env.ts` импортируется
- THEN процесс завершается с кодом 1, в stderr перечислен ключ `SUPABASE_URL`, значение других
      переменных не печатается

### Requirement: Логи не содержат секретов и всегда имеют request_id

Система MUST логировать через pino с `redact` для `authorization`, `access_token`, `refresh_token`,
`cookie` и `password` и SHALL добавлять `request_id` в каждую запись запроса, беря его из заголовка
`x-request-id` или генерируя `crypto.randomUUID()`. Production-формат — JSON, development —
`pino-pretty`. Токены MUST NOT попадать в URL и логи (INV-007, NFR16).

#### Scenario: happy path
- GIVEN запрос приходит с заголовком `x-request-id: abc`
- WHEN приложение пишет лог запроса и лог ответа
- THEN обе записи содержат `request_id: abc`, заголовок `authorization` отсутствует в выводе

#### Scenario: negative — секрет в заголовке и отсутствие request_id
- GIVEN запрос приходит с `authorization: Bearer secret-token` и без `x-request-id`
- WHEN приложение логирует запрос
- THEN значение токена не встречается в выводе ни в одном поле, `request_id` сгенерирован и
      одинаков для всех записей этого запроса

### Requirement: Ограничение частоты запросов

Система MUST ограничивать API до 60 запросов в минуту на ключ (IP для анонимных, токен для
авторизованных) и SHALL отвечать `429` с заголовком `retry-after` при превышении. Ограничитель
MUST NOT применяться к `GET /health` в объёме, который мешает мониторингу, но SHALL учитывать
повторные запросы одного клиента.

#### Scenario: happy path
- GIVEN клиент отправил 60 запросов за минуту
- WHEN приходит 61-й запрос
- THEN ответ `429`, заголовок `retry-after` содержит положительное число секунд, тело — код
      `E_RATE_LIMIT` без внутренних деталей

#### Scenario: boundary — окно восстановления
- GIVEN клиент получил `429`
- WHEN он ждёт `retry-after` секунд и повторяет запрос
- THEN запрос обслуживается нормально, счётчик окна сброшен

### Requirement: Единый формат ошибок без внутренних деталей

Система MUST отдавать ошибки в виде `{ error: { code, message } }` и MUST NOT включать в ответ
стек, SQL, имена таблиц и факт существования чужих записей (INV-007). Внутренние ошибки SHALL
логироваться с `request_id` и уровнем `error`, клиенту — нейтральное сообщение.

#### Scenario: happy path
- GIVEN запрос завершился предсказуемой ошибкой валидации
- WHEN клиент получает ответ
- THEN код `400`, `{ error: { code: 'P0400', message: 'Проверьте заполнение полей' } }`, лог
      содержит `request_id` и исходную ошибку

#### Scenario: negative — падение обработчика
- GIVEN непойманное исключение внутри маршрута
- WHEN клиент получает ответ
- THEN код `500` с `{ error: { code: 'E_INTERNAL', message: 'Не удалось получить данные, попробуйте позже' } }`,
      стек и SQL есть только в логе, наружу не уходят

### Requirement: Корректное завершение процесса

Система MUST завершать работу по `SIGTERM` и `SIGINT` не дольше 5 секунд, закрывая HTTP-сервер и
пул соединений с БД, и SHALL возвращать код 0 при штатном завершении и 1 при ошибке старта.

#### Scenario: happy path
- GIVEN сервер запущен и обслуживает запросы
- WHEN процесс получает `SIGTERM`
- THEN новые соединения не принимаются, текущие закрываются, процесс завершается с кодом 0
      не дольше 5 секунд

#### Scenario: negative — ошибка старта
- GIVEN порт занят другим процессом
- WHEN приложение пытается стартовать
- THEN пишется лог уровня `fatal` с `request_id`-независимым контекстом, процесс завершается с
      кодом 1, секреты в лог не попадают
