# Domain Spec: objects

> Домен отвечает за строительные объекты: создание, список с поиском и пагинацией, правку,
> архивирование и видимость по ролям. Источник: ТЗ §2.1 п. 4–5, `OUTPUT/specs/data-model.md`,
> `OUTPUT/specs/domain-rules.md`.
> Границы домена: задачи объекта живут в домене `tasks`; отчётные агрегаты — в `reporting`.

## Назначение и границы

Объект — корневая сущность домена: у него есть название, адрес, автор, время создания и признак
архивации. Физическое удаление объектов запрещено: удаление заменяется архивированием
(`deleted_at`). Постановщик видит все неархивированные объекты, исполнитель — только те, в которых
у него есть хотя бы одна неархивированная задача.

## Требования

### Requirement: Создание объекта постановщиком

Система MUST разрешать создание объекта только пользователю с ролью `manager`. Поля `title`
(1–200 символов) и `address` (1–300 символов) обязательны, `created_by` MUST заполняться текущим
пользователем.

#### Scenario: happy path
- GIVEN пользователь с ролью `manager` авторизован
- WHEN он отправляет название «ЖК Северный, корпус 2» и адрес «ул. Лесная, 12»
- THEN объект создан, виден в списке сразу после ответа, `created_by` равен его `auth.uid()`

#### Scenario: negative — пустое название
- GIVEN пользователь с ролью `manager` авторизован
- WHEN он отправляет название из пробелов или адрес длиной 301 символ
- THEN ограничение БД отклоняет вставку (`P0400`), объект не создаётся, пользователь видит
      «Проверьте заполнение полей»

### Requirement: Список объектов с курсорной пагинацией и поиском

Система MUST отдавать список объектов курсорной пагинацией по `(created_at, id)` с `limit`
по умолчанию 50 и максимумом 100, отсортированный по `created_at desc`. Поиск SHALL выполняться
по `lower(title)` и `lower(address)` без учёта регистра. Использование `offset` не допускается.

#### Scenario: happy path
- GIVEN в системе 120 неархивированных объектов
- WHEN клиент запрашивает первую страницу без явного `limit`
- THEN возвращается 50 объектов и курсор следующей страницы; вторая страница не повторяет и не
      пропускает записи

#### Scenario: boundary — limit за пределом
- GIVEN клиент передаёт `limit = 500`
- WHEN запрос уходит в PostgREST
- THEN `limit` ограничивается 100 (`P0400` при отрицательном значении), ответ не содержит больше
      100 строк, ошибка не раскрывает SQL

### Requirement: Видимость объектов по роли и RLS

Система MUST включать RLS на `public.objects` и SHALL разрешать исполнителю чтение только тех
неархивированных объектов, где у него есть неархивированная задача. Отсутствие подходящей политики
MUST означать отказ (INV-002). Ответ на чужой объект MUST NOT отличаться от ответа на
несуществующий.

#### Scenario: happy path
- GIVEN исполнителю назначена задача на объекте «ЖК Северный»
- WHEN исполнитель открывает список объектов
- THEN он видит «ЖК Северный» и не видит объекты, где его задач нет

#### Scenario: negative — чужой объект по прямому id
- GIVEN объект не содержит задач исполнителя
- WHEN исполнитель запрашивает его по `id` напрямую
- THEN возвращается пустой результат (или 404 на экране), факт существования объекта не
      раскрывается, `P0403` не содержит данных объекта

### Requirement: Правка объекта только постановщиком

Система MUST разрешать изменение `title` и `address` только пользователю с ролью `manager` через
PostgREST; исполнитель MUST NOT иметь грантов на обновление. `updated_at` SHALL обновляться
триггером, а не клиентом.

#### Scenario: happy path
- GIVEN менеджер открыл карточку объекта
- WHEN он меняет адрес на «ул. Лесная, 12, стр. 1» и сохраняет
- THEN адрес обновлён, `updated_at` больше прежнего, автор и `created_at` не изменились

#### Scenario: negative — исполнитель правит объект
- GIVEN исполнитель авторизован
- WHEN он отправляет `PATCH` с новым названием объекта
- THEN запрос отклонён (`P0403`), объект не изменился, в ответе нет SQL и имён таблиц

### Requirement: Архивирование вместо удаления

Система MUST заменять удаление объекта выставлением `deleted_at = now()` и SHALL делать операцию
идемпотентной: повторный вызов при уже заполненном `deleted_at` не меняет данные и не считается
ошибкой. Физический `DELETE` MUST NOT быть доступен ни одной роли приложения. Задачи
архивированного объекта MUST NOT попадать в выборки, но их строки и история SHALL сохраняться.

#### Scenario: happy path
- GIVEN у объекта есть три задачи, одна из них в статусе `accepted`
- WHEN менеджер архивирует объект
- THEN объект и его задачи исчезают из списков и карточек, строки `tasks` и `task_status_history`
      остаются в базе без изменений

#### Scenario: negative — физическое удаление или архивирование исполнителем
- GIVEN исполнитель или любой клиентский пользователь
- WHEN он пытается выполнить `DELETE` объекта или архивировать его напрямую
- THEN операция отклонена (`P0403`), запись остаётся, история переходов не затронута
