# Domain Spec: tasks

> Домен отвечает за задачи, назначение исполнителя, машину из пяти статусов, неизменяемую историю
> переходов, «Мои задачи» и архивирование. Источник: ТЗ §2.1 п. 6–10, §5.3, `OUTPUT/specs/domain-rules.md`.
> Границы домена: объект задачи создаётся в домене `objects`; агрегаты по задачам — в `reporting`.

## Назначение и границы

Задача принадлежит объекту, имеет автора (постановщик, роль `manager`) и исполнителя (роль
`executor`), название, описание и статус. Статус меняется только вызовом RPC
`change_task_status`; прямой `UPDATE status` запрещён триггером. Каждый переход фиксируется
отдельной строкой `task_status_history`, которую нельзя изменить или удалить.

## Требования

### Requirement: Создание задачи со статусом new

Система MUST создавать задачу только пользователем с ролью `manager`, с обязательными `title`
(1–200), `assignee_id` и `object_id`, статусом `new` и `author_id`, равным текущему пользователю.
Назначаемый исполнитель MUST иметь роль `executor`, а объект MUST быть неархивированным.
`description` SHALL допускать пустое значение и ограничиваться 5000 символами.

#### Scenario: happy path
- GIVEN менеджер и исполнитель существуют, объект «ЖК Северный» не архивирован
- WHEN менеджер создаёт задачу «Монтаж опалубки» на этого исполнителя
- THEN задача сохранена со статусом `new`, в истории появилась запись `null → new` с автором,
      задача видна исполнителю в «Моих задачах»

#### Scenario: negative — исполнитель или архивный объект
- GIVEN менеджер выбирает в качестве исполнителя другого менеджера либо архивный объект
- WHEN он сохраняет задачу
- THEN триггер `validate_task_actors` отклоняет вставку (`P0400`), задача не создаётся,
      история не пополняется

### Requirement: Видимость задач по роли

Система MUST включать RLS на `public.tasks`: менеджер читает все неархивированные задачи,
исполнитель — только задачи с `assignee_id = auth.uid()`. Задача архивного объекта MUST NOT быть
видима ни одной роли. Исполнитель MUST NOT иметь грантов на изменение полей задачи, кроме статуса
через RPC.

#### Scenario: happy path
- GIVEN в системе две задачи, назначенные разным исполнителям
- WHEN первый исполнитель открывает свой список
- THEN он видит только свою задачу и не видит чужую

#### Scenario: negative — правка полей исполнителем
- GIVEN исполнитель авторизован и видит свою задачу
- WHEN он отправляет `PATCH` с новым `title` или `assignee_id`
- THEN запрос отклонён из-за отсутствия колоночного гранта (`P0403`), поля не изменились,
      статус и история не затронуты

### Requirement: Машина из пяти статусов и пяти переходов

Система MUST разрешать только переходы `new → in_progress`, `in_progress → on_review`,
`on_review → accepted`, `on_review → rework`, `rework → in_progress` и SHALL выполнять их только
через RPC `change_task_status`. Любая другая пара, включая переход в тот же статус, MUST
отклоняться с `P0422` без изменения статуса и без записи в историю. Прямой `UPDATE status` MUST
отклоняться с `P0403`.

#### Scenario: happy path
- GIVEN исполнитель назначен на задачу в статусе `new`
- WHEN он вызывает `change_task_status` с `in_progress`
- THEN статус становится `in_progress`, история получает одну запись `new → in_progress`,
      автор перехода — исполнитель

#### Scenario: negative — запрещённый переход и прямой UPDATE
- GIVEN задача в статусе `new`
- WHEN клиент вызывает переход `new → accepted` либо напрямую обновляет `status`
- THEN первый запрос отклонён (`P0422`), второй (`P0403`), статус остаётся `new`,
      в `task_status_history` новых строк нет

### Requirement: Комментарий обязателен при возврате на доработку

Система MUST требовать непустой комментарий (не только пробелы) при переходе `on_review → rework`
и SHALL сохранять его в истории; комментарий SHALL ограничиваться 2000 символами. Для остальных
переходов комментарий необязателен, но если передан — MUST сохраняться в истории без изменений.

#### Scenario: happy path
- GIVEN задача находится в статусе `on_review`, менеджер — её автор
- WHEN менеджер вызывает переход в `rework` с комментарием «Поправить крепление»
- THEN статус становится `rework`, в истории одна запись с этим комментарием

#### Scenario: negative — пустой комментарий
- GIVEN задача в статусе `on_review`
- WHEN менеджер вызывает переход в `rework` с пустой строкой или строкой из пробелов
- THEN переход отклонён (`P0422`), статус остаётся `on_review`, истории не добавляется

### Requirement: Неизменяемая история переходов

Система MUST хранить историю в `public.task_status_history` как append-only: у клиента MUST NOT быть
грантов `INSERT`, `UPDATE` и `DELETE`. Строки истории SHALL создаваться только триггерами
`security definer` с `set search_path = public, pg_temp` и MUST NOT изменяться или удаляться
(INV-004, INV-008).

#### Scenario: happy path
- GIVEN задача прошла путь `new → in_progress → on_review`
- WHEN пользователь открывает карточку задачи
- THEN история показывает три записи в обратном хронологическом порядке с акторами и временем

#### Scenario: negative — попытка переписать историю
- GIVEN клиентский пользователь авторизован
- WHEN он выполняет `UPDATE` или `DELETE` строки `task_status_history`
- THEN операция отклонена отсутствием гранта и триггером `guard_history_immutable` (`P0403`),
      исходные записи не изменились

### Requirement: «Мои задачи» со счётчиками по статусам

Система MUST показывать исполнителю его неархивированные задачи и SHALL выводить счётчики по
каждому статусу (`new`, `in_progress`, `on_review`, `rework`, `accepted`), вычисленные по
видимым строкам. Счётчики MUST NOT учитывать чужие задачи и задачи архивных объектов.

#### Scenario: happy path
- GIVEN у исполнителя две задачи в `new`, одна в `in_progress` и одна в `accepted`
- WHEN он открывает «Мои задачи»
- THEN счётчики показывают 2, 1, 0, 0, 1, а список содержит четыре задачи

#### Scenario: boundary — пустой список
- GIVEN у исполнителя нет назначенных неархивированных задач
- WHEN он открывает «Мои задачи»
- THEN показывается пустое состояние, все счётчики равны нулю, ошибок не возникает

### Requirement: Смена исполнителя и архивирование задачи

Система MUST разрешать смену `assignee_id` только в статусах `new` и `rework` и MUST NOT позволять
менять `author_id`. Архивирование задачи SHALL выполняться менеджером идемпотентно через
`deleted_at`, физическое удаление MUST быть недоступно; история архивированной задачи SHALL
оставаться неизменной.

#### Scenario: happy path
- GIVEN задача в статусе `new` назначена исполнителю А
- WHEN менеджер меняет исполнителя на Б
- THEN задача видна Б и исчезает из «Моих задач» А, история не меняется

#### Scenario: negative — смена исполнителя в работе
- GIVEN задача в статусе `in_progress`
- WHEN менеджер пытается сменить исполнителя или изменить `author_id`
- THEN операция отклонена (`P0422` для смены исполнителя, `P0403` для автора), поля задачи
      остаются прежними
