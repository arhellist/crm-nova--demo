# DEC-034 — D11: SQL отчётов и состояния подписки приведены к PostgreSQL 16

| Поле | Значение |
|------|----------|
| Дата | 2026-11-04 |
| Intake | — |
| Статус | принято |
| ADR | ADR-0003 |
| Заменяет | — |

**Контекст.** Два дефекта SQL проявлялись только на живой реплике:

1. `REPLICATION_STATE_SQL` выбирал `last_error` из `pg_stat_subscription`. В PostgreSQL 16
   такого столбца нет (он появился в 17), запрос падал, `safeReplicationState` возвращал
   `broken`, и `/health/replication` отдавал 503 при работающей репликации — а отчёты
   блокировались проверкой состояния подписки.
2. Отчётные запросы возвращали `timestamptz` как `Date` (клиент `pg`), а Zod-схемы строк
   ждали строку ISO-8601. Валидация ряда падала, маршрут отвечал 500 «Не удалось
   подготовить отчёт» на любых реальных данных.

Unit-тесты этого не ловили: запросы подменялись заглушками, а строки в заглушках были
уже строками.

**Решение.** `last_error` берётся как `null::text` (текста ошибки в PG16 нет; «worker не
работает» определяется по `pid`), временные поля отчётов сериализуются `to_char` в
ISO-8601 (`YYYY-MM-DD"T"HH24:MI:SS.MS"Z"`). Добавлен `src/reporting/sql-contract.test.ts`,
который сверяет имена колонок с каталогом PG16 и требует ISO-сериализации — то есть
падает, если кто-то вернёт несуществующую колонку или сырой `timestamptz`.

**Альтернативы.** Ослабить Zod-схемы до `z.union([z.string(), z.date()])` — контракт
openapi описан строкой, и `Date` в JSON всё равно стал бы строкой другого формата.
Обновить реплику до PG17 — ADR-0003 фиксирует PostgreSQL 16 в контуре backend. Читать
`pg_stat_subscription_stats` ради счётчиков ошибок — в PG16 там нет текста, только
числа, и права роли `nova_ro` не гарантируют доступ. Принято приведение в SQL плюс
контрактный тест.

**Чем подтверждено.** Живой staging: `/health/replication` → `{"status":"streaming",...}`,
три отчёта 200 с `source: replica` и ISO-временем; `npm run test` — 32 файла / 107 тестов,
включая новый `sql-contract.test.ts`.
