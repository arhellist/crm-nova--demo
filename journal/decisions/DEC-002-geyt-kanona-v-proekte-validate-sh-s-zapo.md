# DEC-002 — Гейт канона в проекте: `./validate.sh` внутри работающей установки падает …

| Поле | Значение |
|------|----------|
| Дата | 2026-11-04 |
| Intake | 20261104-1743-razvernut-kanon-kak-project-witness-done |
| Статус | принято |
| ADR | — |
| Заменяет | — |

**Контекст.** Канон установлен внутрь проекта: `<project>/witness-done/`, прогон идёт в
`<project>/witness-done/OUTPUT/`. `validate.sh` — самопроверка **репозитория канона**: он требует,
чтобы `OUTPUT/` был пуст, `OUTPUT/MANIFEST.md` отсутствовал, `doctor --strict` проходил в корне
канона, а selftest проверяет негативный кейс «незаполненный `INPUT/TECH_SPEC.md`». В работающей
установке все четыре условия ложны по определению:

- `OUTPUT/` содержит 128 файлов прогона;
- `OUTPUT/MANIFEST.md` создан шагом 00 и обязан существовать;
- `doctor --strict` в корне канона ругается на занятый `OUTPUT/`;
- `INPUT/TECH_SPEC.md` заполнен ТЗ продукта — негативный кейс selftest даёт 0 вместо 2.

Ограничения: ТЗ продукта и артефакты прогона удалять нельзя; канон по месту не патчим — иначе
установка разойдётся с оригиналом и не переживёт обновление (`sp update`).

**Решение.** `validate.sh` считается гейтом **исходного канона**, а не работающей установки:

1. Целостность канона доказывается на чистом снимке: `git archive HEAD | tar -x -C /tmp/canon-head`
   → `./validate.sh` → `RESULT: PASS` (v1.31.0).
2. В проекте гейтами являются `sp doctor`, `sp rules --check` и `sp-verify --gate …`; их
   результаты пишутся в `OUTPUT/evidence/`.
3. `validate.sh` по месту не патчим и не запускаем как критерий приёмки прогона; его FAIL в
   установке — ожидаемое состояние, а не дефект продукта.
4. Если требуется изменить сам канон — это отдельная задача сопровождения в репозитории канона,
   с полным `./validate.sh` на чистом дереве.

**Альтернативы.** (1) Затереть `INPUT/TECH_SPEC.md` и `OUTPUT/` на время гейта — отвергнуто:
теряется вход прогона и доказательства шагов. (2) Патчить `validate.sh` в установке — отвергнуто:
локальная правка канона не переживёт обновление и создаст вторую версию правды.
(3) Считать `SP_SKIP_SELFTEST=1 ./validate.sh` доказательством — отвергнуто: структурные проверки
`OUTPUT` всё равно падают, «PASS» был бы ложью. (4) Гонять `validate.sh` только на снимке
`HEAD` — принято.

**Чем подтверждено.** `validate.sh` на снимке `HEAD` — PASS; в установке — FAIL по занятому `OUTPUT`, см. список ниже.

- `git archive HEAD | tar -x -C /tmp/canon-head && cd /tmp/canon-head && ./validate.sh` →
  `OK selftest sp.mjs (классификация, правила, doctor)` и `RESULT: PASS`.
- В установке `witness-done/validate.sh` → `RESULT: FAIL` c тремя строками:
  `OUTPUT must be empty before step 00 (found 127 file(s))`,
  `sp doctor --strict падает в корне канона`,
  `OUTPUT/MANIFEST.md must not exist (use TEMPLATES/manifest.md)`.
- `SP_SKIP_SELFTEST=1 ./validate.sh` в установке → тот же `RESULT: FAIL` (selftest не причина).
- `sp rules --check` в проекте → «Правила синхронны (13 целей)».
