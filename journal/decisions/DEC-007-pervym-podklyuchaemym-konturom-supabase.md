# DEC-007 — Первым подключаемым контуром Supabase выбран облачный проект (staging), а не …

| Поле | Значение |
|------|----------|
| Дата | 2026-11-04 |
| Intake | 20261104-2109-kak-podklyuchit-k-proektu-supabase-kakie |
| Статус | принято |
| ADR | — |
| Заменяет | — |

**Контекст.** На D01 проект дошёл без единого Supabase-контура: каталога `supabase/` нет,
CLI не установлен, `src/shared/config/env.ts` только валидирует `SUPABASE_URL`, клиента
`@supabase/supabase-js` в коде ещё нет, фронтенда (и `VITE_*`) нет. ADR-0006 фиксирует три
окружения (`local` = Supabase CLI + Docker, `staging` и `production` = отдельные облачные
проекты), но не задаёт, какой из них подключается первым. Без этого выбора нельзя ни завести
`supabase/config.toml` (PRODUCES D02), ни заполнить env: URL, ключи и способ доставки миграций
у локального и облачного контура разные, а `supabase link` пишет связь в конфиг проекта.
Ограничения, которые нельзя обойти: backend не имеет доступа к primary (INV-001), `service_role`
не попадает в клиент, backend, образы и CI-логи (INV-006), токены и пароли не логируются и не
передаются в URL (INV-007), миграции forward-only (ADR-0006).

**Решение.** Первым подключаемым контуром Supabase выбран облачный проект (staging), а не локальный CLI-стек: URL и anon-ключ берутся из Settings → API проекта, проект связывается через supabase link --project-ref, миграции уезжают только forward-only через supabase db push; локальный стек остаётся обязательным для supabase db reset и supabase test db перед push, backend по-прежнему читает только реплику (DATABASE_URL), primary в конфигурации api не появляется (INV-001), а service_role, пароль БД и JWT secret живут в менеджере секретов и GitHub Environments, не в чате, .env в git и не в логах (INV-006/INV-007)

**Альтернативы.** (1) Только локальный стек (CLI + Docker), облако позже — отвергнуто: пользователь
уже располагает облачным проектом, и развилка «два разных Auth/URL» откладывает расхождения
ключей и seed на staging до D04, где их дороже разбирать. (2) Только облако, без локального
стека — отвергнуто: без `supabase db reset` и `supabase test db` нельзя прогнать pgTAP по RLS
и переходам (D02, D03), а `install-order.md` и `product-smoke.md` опираются на локальный контур.
(3) Подключить оба контура сразу двумя наборами ключей — отвергнуто как преждевременное: второй
набор секретов нужен только после появления staging-деплоя, а сейчас удваивает конфигурацию
без проверки.

**Чем подтверждено.** `OUTPUT/tooling/env-vars.md` (колонки staging и local, правило «`VITE_*`
без секретов»); `OUTPUT/security/secrets-and-config.md` §2 (staging — отдельный проект и ключи);
ADR-0006; A02.1–A02.6 (D02) прогоняются на локальном стеке, затем те же миграции уезжают
`supabase db push` в staging; INV-001/INV-006/INV-007 проверяются гейтами `secrets-and-config.md` §5.
