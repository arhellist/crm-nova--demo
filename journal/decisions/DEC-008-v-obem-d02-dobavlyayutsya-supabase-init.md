# DEC-008 — В объём D02 добавляются supabase init (создание supabase/config.toml, который…

| Поле | Значение |
|------|----------|
| Дата | 2026-11-04 |
| Intake | 20261104-2109-kak-podklyuchit-k-proektu-supabase-kakie |
| Статус | принято |
| ADR | — |
| Заменяет | — |

**Контекст.** `OUTPUT/prompts/D02_*.md` перечисляет `supabase/config.toml` в PRODUCES с пометкой
«изменить», но файла в репозитории нет: `supabase init` в D01 не выполнялся, каталога `supabase/`
не существует. Одновременно `OUTPUT/docs/START_HERE.md` (строки 56–57) утверждает, что образец
`.env.example` появляется в D01, `install-order.md` §1 строит на нём установку (`cp .env.example
.env.local`), а в PRODUCES D01 этого файла нет — то есть контракты расходятся с фактом. По §1.8
расширять PRODUCES запрещено, по §1.17 нельзя «быстро поправить» вне задания, поэтому нужен
явный маршрут, а не молчаливая правка.

**Решение.** В объём D02 добавляются `supabase init` (создание `supabase/config.toml`, который
PRODUCES D02 сейчас только «изменяет») и корневой `.env.example` с пустыми значениями по
`OUTPUT/tooling/env-vars.md`; PRODUCES D02 расширяется правкой промпта на шаге R02 change-пакетом,
а не дожимом кода вне задания (§1.8/§1.17).

**Альтернативы.** (1) Завести `.env.example` сейчас, «пока вопрос в чате» — отвергнуто: файл вне
PRODUCES даёт `proof_debt` и провал приёмки D01/D02. (2) Отдельный change-пакет в обход D02 —
отвергнуто: файл относится к тому же срезу S1 (схема, seed, конфигурация стека), отдельный
пакет удваивает приёмку без выигрыша. (3) Считать `.env.example` частью D01 задним числом —
отвергнуто: D01 закрыт с `tax_pass: true`, акт не переписывается.

**Чем подтверждено.** Правленый `OUTPUT/prompts/D02_*.md` с `.env.example` в PRODUCES и
`supabase/config.toml` как «создать/изменить»; `install-order.md` §1 выполняется буквально
(`cp .env.example .env.local`); `sp doctor --strict` без `proof_debt` после D02.
