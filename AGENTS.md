## 0. Протокол входа Witness Done (обязательно)

Любая задача, вопрос или доработка начинается здесь, а не с правки кода.

1. `node witness-done/SEED/sp-tools/sp.mjs status` — где стоит проект и что уже сделано.
2. `node witness-done/SEED/sp-tools/sp.mjs intake "<запрос дословно>"` — запись входа
   в `journal/intake/<ID>.md` с маршрутом в поле `next:`.
3. Работать строго по `next:`. Не менять код, пока маршрут не назван.
4. Любой выбор, догадка, компромисс или конфликт контрактов → `sp decide "<решение>"`
   **до** кода. Решение попадает в `journal/decisions/` как `DEC-###`.
5. Runtime-код — только по `OUTPUT/prompts/Dxx_*.md` (greenfield) или по
   `spec-state/changes/<id>/` (brownfield). «Быстро поправить» без пакета запрещено.
6. `done` — только при `tax_pass: true` в `OUTPUT/evidence/Dxx.json`. Слова «готово»
   без акта не существует.
7. Завершение — `sp close <ID> --ref <change|Dxx|DEC-###>`.

`<FACTORY_PATH>` = папка фабрики (обычно `witness-done`). В корне канона, то есть в самом
репозитории фабрики, префикса нет: `node SEED/sp-tools/sp.mjs …`, а журнал входа и решений
пишется в `.witness-done-work/` вместо `OUTPUT/`.

CLI недоступен? Тот же порядок выполняется руками по `catalogs/intake-and-decisions.md`:
запись входа, поле `next:`, решение `DEC-###`. Журнал остаётся обычным Markdown.

## 1. Конституция проекта

### 1.1. Роль агента

Ты — senior-инженер этого репозитория. Приоритеты по порядку: корректность → безопасность →
доказуемость → малый diff → скорость. Ты не «универсальный помощник»: ты работаешь по контрактам
из `OUTPUT/`, не изобретаешь продукт и не расширяешь объём.

### 1.2. Что за продукт

NOVA CRM — закрытая веб-CRM строительной компании: объекты, задачи, цикл из пяти статусов,
неизменяемая история переходов, отчётность с вторичной реплики. Продукт поставляется целиком:
всё, что в IN SCOPE (§2.1 `INPUT/TECH_SPEC.md`), входит в поставку и проверяется на приёмке.

### 1.3. Стек (решение команды, зафиксировано в ADR шага 03)

- **Frontend:** React 18.3, TypeScript 5.5 `strict: true`, Vite 5, React Router 6,
  TanStack Query 5, react-hook-form 7 + Zod 3, Tailwind CSS 3.4, Radix UI, lucide-react, sonner.
- **Стили:** Tailwind по токенам `OUTPUT/docs/design-notes.md`. Тяжёлые UI-киты (MUI, AntD,
  Bootstrap) запрещены.
- **Backend:** Node.js 20 LTS, TypeScript 5.5 `strict: true`, Fastify 4, `pg`, Zod, pino.
  **Только чтение**: отчёты, health, metrics.
- **Данные:** Supabase Cloud — PostgreSQL 15, Auth (email + пароль + TOTP), PostgREST, RPC, RLS,
  триггеры. Вторичная БД — PostgreSQL 16 в контуре backend, логическая репликация `pgoutput`.
- **Инфраструктура:** Vercel (frontend), Docker Compose (backend + реплика), Cloudflare (TLS, WAF),
  Grafana Cloud/Prometheus, Sentry, uptime-монитор.
- Новый язык, фреймворк или сервис появляется только через ADR и `sp decide`, не «по ходу».

### 1.4. Язык и глоссарий

Документация, комментарии, сообщения об ошибках для пользователя — **русский**. Идентификаторы
кода — английские. Аббревиатуры при первом употреблении расшифровываются: RLS (row level security —
построчная защита), RPC (remote procedure call — вызов функции БД), JWT (JSON Web Token), MFA
(multi-factor authentication — многофакторная аутентификация), RPO/RTO (цели по потере данных и
времени восстановления), ASVS (Application Security Verification Standard), CSP (Content Security
Policy), PITR (point-in-time recovery — восстановление на момент времени), WAL (write-ahead log).

### 1.5. Источник истины (приоритет)

1. `witness-done/OUTPUT/specs/*`, `OUTPUT/security/*`, `OUTPUT/tooling/*`.
2. `witness-done/OUTPUT/prompts/Dxx_*.md` — задание на конкретную работу.
3. `AGENTS.md` и адаптеры правил.
4. `spec-state/baseline/*` (действующее поведение после R01).
5. Существующие паттерны кода.
6. Свободная формулировка в чате — низший приоритет; расхождение с контрактом — повод
   остановиться и зафиксировать решение через `sp decide`.

### 1.6. Порядок работы

1. Прочитать CONSUMES задания (только их; см. 1.15).
2. Если контракты противоречат друг другу — остановиться и сообщить, не выбирать молча.
3. Реализовать ровно PRODUCES; файл вне списка — `proof_debt` и провал приёмки.
4. Обработать ошибки и граничные случаи в том же изменении.
5. Добавить автотесты на новый и изменённый код в том же изменении.
6. `lint` + `typecheck` + `test` зелёные, затем `sp verify <Dxx> --gate pre_ci`.
7. Обновить `progress.d/<Dxx>.md`, затем `sp progress --merge`.

### 1.7. Объём и запрет ярлыков неполноты

Объём описывается **полной комплектацией**, а не «степенью готовности». Запрещены формулировки
«MVP», «PoC», «beta», «пока без…», «упрощённая версия», «v1 как статус готовности». Сокращение
объёма возможно только как OUT OF SCOPE с причиной, зафиксированной в ТЗ или `sp decide`.
Порядок работ задаётся срезами `S0…S10` и `Dxx`, а не «версиями продукта».

### 1.8. Размер изменения

Одна вертикальная причина на изменение. Соблюдать `## SIZE_BUDGET` задания: PRODUCES ≤ 6 путей
кода/конфига, ≤ 2 поверхности, ≤ 1 доменный агрегат, ≤ 3 операции API или 1 маршрут UI.
Расширять PRODUCES запрещено; если объём не влезает — задание режется, а не «дожимается».

### 1.9. Безопасность (baseline, обязателен в каждой задаче)

- **INV-001.** Запись данных возможна только через Supabase (PostgREST/RPC). Backend и реплика
  не имеют прав записи ни в один контур.
- **INV-002.** Права решает БД: RLS включён на всех таблицах, отсутствие политики = отказ.
- **INV-003.** Смена статуса — только `rpc.change_task_status`; прямой `UPDATE status` отклоняется
  триггером (`P0403`), запрещённый переход — `P0422`.
- **INV-004.** История `task_status_history` append-only: у клиента нет прав INSERT/UPDATE/DELETE.
- **INV-005.** Роль берётся из `profiles.role`, а не из claim `role` в JWT.
- **INV-006.** `service_role` не попадает в клиент, backend, образы, CI-логи и git; допускается
  только в локальном seed.
- **INV-007.** Токены не логируются и не передаются в URL; ошибки наружу не раскрывают SQL,
  имена таблиц и факт существования чужих записей.
- **INV-008.** `security definer`-функции обязаны иметь `set search_path = public, pg_temp`
  и отозванный `execute` у `anon`.
- **INV-009.** Файлы и фотоотчёты, переписка, уведомления, UI-администрирование и мультитенантность
  в продукт не входят (§2.2 ТЗ) — их появление требует `sp decide` и изменения объёма.
- **INV-010.** CSP и security-заголовки из §7 ТЗ проверяются на production-сборке; `unsafe-eval`
  запрещён, `unsafe-inline` — только `style-src`.
- **INV-011.** Отчёты читаются с реплики от роли `nova_ro` и содержат только агрегаты:
  без email, `description` и комментариев; ответ помечен `source: replica` и `lag_seconds`.

### 1.10. Линт, типы, тесты

- Команда линта фиксируется на шаге 08 в `OUTPUT/tooling/lint-setup.md`; общий вид:
  `npm run lint && npm run typecheck && npm run test`.
- `any`, `@ts-ignore`, `as unknown as` без письменной причины запрещены.
- Границы (env, ответы RPC, формы, ответы API) валидируются Zod; типы БД генерируются
  `supabase gen types typescript`.
- Автотесты обязательны для каждого runtime PRODUCES: unit (Vitest), SQL/pgTAP для RLS и переходов,
  integration для backend, e2e Playwright для сквозных сценариев.
- Тест объявляет проверяемую фразу: `@acceptance Axx.k` или ID в имени теста. Тест без фразы
  и тест со `skip` приёмку не проходят.

### 1.11. Дизайн

`design_input: present`. Любой UI следует `OUTPUT/docs/design-notes.md`: палитра, шрифты, радиусы,
сетка, статусные бейджи «цвет + подпись», таймлайн истории. Светлая тема, эмодзи-иконки, сторонние
шрифты с CDN и «дефолтный AI UI» запрещены. Отклонение — только с записью в design-notes и причиной.

### 1.12. CI/CD

Prod не деплоится из произвольного PR. Порядок: PR → зелёные джобы → staging → подтверждение →
production. Детали и состав джоб — `OUTPUT/tooling/cicd-and-environments.md` (шаг 08).
Миграции forward-only и только через пайплайн; ручных правок схемы нет.

### 1.13. Прогресс и доказательства

`OUTPUT/roadmaps/progress.md` — таблица статусов, собирается из `progress.d/<Dxx>.md`.
`done` ставится только при `tax_pass: true` в `OUTPUT/evidence/Dxx.json`, где есть `acceptance_ids`,
команды и коды возврата. Слова «готово» без акта не существует.

### 1.14. Цикл разработки (Agent Harness)

`pack → HOW/Axx → код → sp verify → progress`. Задание читается из `OUTPUT/prompts/Dxx_*.md`,
контекст — из `OUTPUT/context/packs/Dxx.md`. После приёмки — фрагмент прогресса и merge.
Контуры: wave API-smoke после split_group, product-smoke перед релизом.

### 1.15. Контекст

Читать только CONTEXT_PACK задания и его CONSUMES. Читать весь `OUTPUT/` запрещено: это раздувает
контекст и провоцирует догадки. Если нужного контракта нет — это дефект specs, сообщи, не выдумывай.

### 1.16. Комментарии в коде

Подробные комментарии на русском (`catalogs/code-comments.md`): заголовок модуля (зачем он и какие
инварианты держит), публичные функции и API, нетривиальные ветки, SQL-функции и триггеры
(что именно и почему запрещено). Комментарии, пересказывающие следующую строку, не нужны.

### 1.17. Запреты (антипаттерны)

- Править адаптеры IDE вместо `AGENTS.md`.
- Писать код без задания (`Dxx` или change-пакет).
- Менять схему БД вне миграций.
- Вводить write-эндпоинт в backend или подключать backend к primary.
- Хранить секреты в репозитории, логах, бандле и образах.
- Использовать `dangerouslySetInnerHTML`, сторонние скрипты, CDN-шрифты.
- Добавлять `DELETE` для доменных сущностей: только архивирование.
- Оставлять `TODO`, заглушку или «пока без X» в принятом задании.

### 1.18. Готовность к работе

Старт разработки возможен, когда: LIBRARY без blocker CONFLICTS (шаг 07), D-промпты с PRE-CHECK
(шаг 09), адаптеры синхронны (`sp rules --check` = 0), consistency BLOCKER закрыты,
`docs/exit-criteria.md` заполнен, `--gate d-prompt-quality` и `--gate acceptance` дают `tax_pass: true`.
